# SHA-3

::: {#o4 .subject cue=lead name="SHA-3"}

**SHA-3** (**Secure Hash Algorithm 3**) is the latest[^o5] member of the [Secure Hash Algorithm](https://en.wikipedia.org/wiki/Secure_Hash_Algorithm) family of standards, released by [NIST](https://en.wikipedia.org/wiki/NIST) on August 5, 2015.[^o6][^o7][^o8] Although part of the same series of standards, SHA-3 is internally different from the [MD5](wikipedia://en/18826)-like [structure](https://en.wikipedia.org/wiki/Davies-Meyer) of [SHA-1](wikipedia://en/26672) and [SHA-2](wikipedia://en/1638777).

:::

SHA-3 is a subset of the broader [cryptographic primitive](wikipedia://en/4928985) family **Keccak** ( or ),[^o24][^o9] designed by [Guido Bertoni](https://en.wikipedia.org/wiki/Guido_Bertoni), [Joan Daemen](https://en.wikipedia.org/wiki/Joan_Daemen), [Michaël Peeters](https://en.wikipedia.org/wiki/Michaël_Peeters), and [Gilles Van Assche](https://en.wikipedia.org/wiki/Gilles_Van_Assche), building upon [RadioGatún](wikipedia://en/8625699). Keccak's authors have proposed additional uses for the function, not (yet) standardized by [NIST](https://en.wikipedia.org/wiki/National_Institute_of_Standards_and_Technology), including a [stream cipher](wikipedia://en/49007), an [authenticated encryption](wikipedia://en/2244296) system, a "tree" hashing scheme for faster hashing on certain architectures,[^o10][^o11] and [AEAD](https://en.wikipedia.org/wiki/AEAD) ciphers Keyak and Ketje.[^o12][^o13]

Keccak is based on a novel approach called [sponge construction](wikipedia://en/37217701).[^o41] The sponge construction is based on a [pseudorandom permutation](wikipedia://en/4681949), and allows inputting ("absorbing" in sponge terminology) any amount of data, and outputting ("squeezing") any amount of data, while acting as a pseudorandom function with regard to all previous inputs. This leads to great flexibility.

2022 NIST does not plan to withdraw SHA-2 or remove it from the revised Secure Hash Standard.[^o14] The purpose of SHA-3 is that it can be directly substituted for SHA-2 in current applications if necessary, and to significantly improve the robustness of NIST's overall hash algorithm toolkit.[^o15]

For small message sizes, the creators of the Keccak algorithms and the SHA-3 functions suggest using the faster function KangarooTwelve with adjusted parameters and a new tree hashing mode without extra overhead.

## History {#History}

The Keccak algorithm is the work of Guido Bertoni, [Joan Daemen](https://en.wikipedia.org/wiki/Joan_Daemen) (who also co-designed the [Rijndael](https://en.wikipedia.org/wiki/Rijndael) cipher with [Vincent Rijmen](https://en.wikipedia.org/wiki/Vincent_Rijmen)), Michaël Peeters, and [Gilles Van Assche](https://en.wikipedia.org/wiki/Gilles_Van_Assche). It is based on earlier hash function designs [PANAMA](https://en.wikipedia.org/wiki/PANAMA) and [RadioGatún](wikipedia://en/8625699). PANAMA was designed by Daemen and Craig Clapp in 1998. RadioGatún, a successor of PANAMA, was designed by Daemen, Peeters, and Van Assche, and was presented at the NIST Hash Workshop in 2006.[^o17] The [reference implementation](https://en.wikipedia.org/wiki/Reference_implementation) was released to the [public domain](https://en.wikipedia.org/wiki/Public_domain).[^o18]

In 2006, [NIST](https://en.wikipedia.org/wiki/NIST) started to organize the [NIST hash function competition](wikipedia://en/20051952) to create a new hash standard, SHA-3. SHA-3 is not meant to replace [SHA-2](wikipedia://en/1638777), as no significant attack on SHA-2 has been publicly demonstrated. Because of the successful attacks on [MD5](wikipedia://en/18826), [SHA-0](https://en.wikipedia.org/wiki/SHA-0) and [SHA-1](wikipedia://en/26672),[^o19][^o20] NIST perceived a need for an alternative, dissimilar cryptographic hash, which became SHA-3.

After a setup period, admissions were to be submitted by the end of 2008. Keccak was accepted as one of the 51 candidates. In July 2009, 14 algorithms were selected for the second round. Keccak advanced to the last round in December 2010.[^o21]

During the competition, entrants were permitted to "tweak" their algorithms to address issues that were discovered. Changes that have been made to Keccak are:[^o22][^o23]

- The number of [rounds](wikipedia://en/73297602) was increased from 12 + ℓ to 12 + 2ℓ to be more conservative about security.
- The message padding was changed from a more complex scheme to the simple 10<sup>\*</sup>1 pattern described below.
- The rate *r* was increased to the security limit, rather than rounding down to the nearest power of 2.

On October 2, 2012, Keccak was selected as the winner of the competition.[^o24]

In 2014, the NIST published a draft [FIPS](https://en.wikipedia.org/wiki/Federal_Information_Processing_Standards) 202 "SHA-3 Standard: Permutation-Based Hash and Extendable-Output Functions".[^o25] FIPS 202 was approved on August 5, 2015.[^o26]

On August 5, 2015, NIST announced that SHA-3 had become a hashing standard.[^o27]

### Weakening controversy {#Weakening_controversy}

In early 2013 NIST announced they would select different values for the "capacity", the overall strength vs. speed parameter, for the SHA-3 standard, compared to the submission.[^o29][^o30] The changes caused some turmoil.

The hash function competition called for hash functions at least as secure as the SHA-2 instances. It means that a *d*-bit output should have *d*/2-bit resistance to [collision attacks](wikipedia://en/969624) and *d*-bit resistance to [preimage attacks](wikipedia://en/969477), the maximum achievable for *d* bits of output. Keccak's security proof allows an adjustable level of security based on a "capacity" *c*, providing *c*/2-bit resistance to both collision and preimage attacks. To meet the original competition rules, Keccak's authors proposed *c* = 2*d*. The announced change was to accept the same *d*/2-bit security for all forms of attack and standardize *c* = *d*. This would have sped up Keccak by allowing an additional *d* bits of input to be hashed each iteration. However, the hash functions would not have been drop-in replacements with the same preimage resistance as SHA-2 any more; it would have been cut in half, making it vulnerable to advances in quantum computing, which effectively would cut it in half once more.[^o74]

In September 2013, [Daniel J. Bernstein](wikipedia://en/198983) suggested on the [NIST](https://en.wikipedia.org/wiki/NIST) hash-forum mailing list[^o31] to strengthen the security to the 576-bit capacity that was originally proposed as the default Keccak, in addition to and not included in the SHA-3 specifications.[^o32] This would have provided at least a SHA3-224 and SHA3-256 with the same preimage resistance as their SHA-2 predecessors, but SHA3-384 and SHA3-512 would have had significantly less preimage resistance than their SHA-2 predecessors. In late September, the Keccak team responded by stating that they had proposed 128-bit security by setting *c* = 256 as an option already in their SHA-3 proposal.[^o33] Although the reduced capacity was justifiable in their opinion, in the light of the negative response, they proposed raising the capacity to *c* = 512 bits for all instances. This would be as much as any previous standard up to the 256-bit security level, while providing reasonable efficiency,[^o34] but not the 384-/512-bit preimage resistance offered by SHA2-384 and SHA2-512. The authors stated that "claiming or relying on [security strength](https://en.wikipedia.org/wiki/Security_strength) levels above 256 bits is meaningless".

In early October 2013, [Bruce Schneier](wikipedia://en/36732) criticized NIST's decision on the basis of its possible detrimental effects on the acceptance of the algorithm, saying: There is too much mistrust in the air. NIST risks publishing an algorithm that no one will trust and no one (except those forced) will use.[^o35] He later retracted his earlier statement, saying: I misspoke when I wrote that NIST made "internal changes" to the algorithm. That was sloppy of me. The Keccak permutation remains unchanged. What NIST proposed was reducing the hash function's capacity in the name of performance. One of Keccak's nice features is that it's highly tunable.[^o35]

Paul Crowley, a cryptographer and senior developer at an independent software development company, expressed his support of the decision, saying that Keccak is supposed to be tunable and there is no reason for different security levels within one primitive. He also added:

Yes, it's a bit of a shame for the competition that they demanded a certain security level for entrants, then went to publish a standard with a different one. But there's nothing that can be done to fix that now, except re-opening the competition. Demanding that they stick to their mistake doesn't improve things for anyone.[^o36]

There was some confusion that internal changes may have been made to Keccak, which were cleared up by the original team, stating that NIST's proposal for SHA-3 is a subset of the Keccak family, for which one can generate test vectors using their reference code submitted to the contest, and that this proposal was the result of a series of discussions between them and the NIST hash team.[^o37]

In response to the controversy, in November 2013 John Kelsey of NIST proposed to go back to the original *c* = 2*d* proposal for all SHA-2 drop-in replacement instances.[^o38] The reversion was confirmed in subsequent drafts[^o39] and in the final release.[^o6]

## Design {#Design}

*Image: SpongeConstruction.svg.* The sponge construction for hash functions. *P<sub>i</sub>* are input, *Z<sub>i</sub>* are hashed output. The capacity *c* should be twice the desired resistance to [collision](wikipedia://en/969624) or [preimage attacks](wikipedia://en/969477).

SHA-3 uses the [sponge construction](wikipedia://en/37217701),[^o41] in which data is "absorbed" into the sponge, then the result is "squeezed" out. In the absorbing phase, message blocks are [XORed](wikipedia://en/105979) into a subset of the state, which is then transformed as a whole using a [permutation function](wikipedia://en/4681949) (or [transformation](https://en.wikipedia.org/wiki/Pseudorandom_function)) $f$. In the "squeeze" phase, output blocks are read from the same subset of the state, alternated with the state transformation function $f$. The size of the part of the state that is written and read is called the "rate" (denoted $r$), and the size of the part that is untouched by input/output is called the "capacity" (denoted $c$). The capacity determines the security of the scheme. The maximum [security level](wikipedia://en/52729212) is half the capacity.

Given an input bit string $N$, a padding function $pad$, a permutation function $f$ that operates on bit blocks of width $b$, a rate $r$ and an output length $d$, we have capacity $c = b - r$ and the sponge construction $Z = \text{sponge}[f,pad,r](N,d)$. This yields a bit string $Z$ of length $d$ as follows:[^o7]

- pad the input *N* using the pad function, yielding a padded bit string *P* with a length divisible by $r$ (such that $n = \text{len}(P)/r$ is an integer)
- break *P* into *n* consecutive *r*-bit pieces *P*<sub>0</sub>, ..., *P*<sub>*n*−1</sub>
- initialize the state *S* to a string of *b* zero bits
- absorb the input into the state: for each block *P*<sub>*i*</sub>:
  - extend *P*<sub>*i*</sub> at the end by a string of *c* zero bits, yielding one of length *b*
  - XOR that with *S*
  - apply the block permutation *f* to the result, yielding a new state *S*
- initialize *Z* to be the empty string
- while the length of *Z* is less than *d*:
  - append the first *r* bits of *S* to *Z*
  - if *Z* is still less than *d* bits long, apply *f* to *S*, yielding a new state *S*
- truncate *Z* to *d* bits

The fact that the internal state *S* contains *c* additional bits of information in addition to what is output to *Z* prevents the [length extension attacks](wikipedia://en/36667216) that SHA-2, SHA-1, MD5 and other hashes based on the [Merkle–Damgård construction](wikipedia://en/4076217) are susceptible to.

In SHA-3, the state *S* consists of a 5 × 5 array of *w*-bit words (with *w* = 64), *b* = 5 × 5 × *w* = 5 × 5 × 64 = 1600 bits total. Keccak is also defined for smaller power-of-2 word sizes *w* down to 1 bit (total state of 25 bits). Small state sizes can be used to test cryptanalytic attacks, and intermediate state sizes (from *w* = 8, 200 bits, to *w* = 32, 800 bits) can be used in practical, lightweight applications.[^o12][^o13]

For SHA3-224, SHA3-256, SHA3-384, and SHA3-512 instances, *r* is greater than *d*, so there is no need for additional block permutations in the squeezing phase; the leading *d* bits of the state are the desired hash. However, SHAKE128 and SHAKE256 allow an arbitrary output length, which is useful in applications such as [optimal asymmetric encryption padding](wikipedia://en/1579249).

## Padding {#Padding}

To ensure the message can be evenly divided into *r*-bit blocks, padding is required. SHA-3 uses the pattern 10...01 in its padding function: a 1 bit, followed by zero or more 0 bits (maximum $r - 1$) and a final 1 bit.

The maximum of $r - 1$ zero bits occurs when the last message block is $r - 1$ bits long. Then another block is added after the initial 1 bit, containing $r - 1$ zero bits before the final 1 bit.

The two 1 bits will be added even if the length of the message is already divisible by *r*.[^o7] In this case, another block is added to the message, containing a 1 bit, followed by a block of $r - 2$ zero bits and another 1 bit. This is necessary so that a message with length divisible by *r* ending in something that looks like padding does not produce the same hash as the message with those bits removed.

The initial 1 bit is required so messages differing only in a few additional 0 bits at the end do not produce the same hash.

The position of the final 1 bit indicates which rate *r* was used (multi-rate padding), which is required for the security proof to work for different hash variants. Without it, different hash variants of the same short message would be the same up to truncation.

## The block permutation {#The_block_permutation}

The block transformation *f*, which is Keccak-f\[1600\] for SHA-3, is a permutation that uses [XOR](wikipedia://en/264399#XOR), [AND](https://en.wikipedia.org/wiki/Binary_AND) and [NOT](https://en.wikipedia.org/wiki/Binary_NOT) operations, and is designed for easy implementation in both software and hardware.

It is defined for any power-of-two [word](https://en.wikipedia.org/wiki/Word_%28computer_architecture%29) size, $w = 2^{\ell}$ bits. The main SHA-3 submission uses 64-bit words, $\ell = 6$.

The state can be considered to be a $5 \times 5 \times w$ array of bits. Let $a[i][\,j][k]$ be bit $(5i + j) \times w + k$ of the input, using a [little-endian](https://en.wikipedia.org/wiki/Little-endian) bit numbering convention and [row-major](https://en.wikipedia.org/wiki/Row-major) indexing. I.e. $i$ selects the row, $j$ the column, and $k$ the bit.

Index arithmetic is performed modulo 5 for the first two dimensions and modulo *w* for the third.

The basic block permutation function consists of $12 + 2\ell$ rounds of five steps:

**$\theta$ (theta)**

Compute the [parity](wikipedia://en/143135) of each of the $5w$ (320, when $w = 64$) 5-bit columns, and exclusive-or that into two nearby columns in a regular pattern. To be precise, $a[i][\,j][k] \leftarrow a[i][\,j][k] \oplus$ $\operatorname{parity}(a[0...4][j-1][k]) \oplus$ $\operatorname{parity}(a[0...4][j+1][k-1]$)

**$\rho$ (rho)**

[Bitwise rotate](wikipedia://en/1917276) each of the 25 words by a different [triangular number](wikipedia://en/213915) 0, 1, 3, 6, 10, 15, .... To be precise, *a*\[0\]\[0\] is not rotated, and for all $0 \le t < 24$, $a[i][\,j][k] \leftarrow a[i][\,j][k-(t+1)(t+2)/2]$, where $\begin{pmatrix} i \\ j \end{pmatrix} = \begin{pmatrix} 3 & 2 \\ 1 & 0 \end{pmatrix}^t \begin{pmatrix} 0 \\ 1 \end{pmatrix}$.

**$\pi$ (pi)**

Permute the 25 words in a fixed pattern. $a[3i+2j][i] \leftarrow a[\,i][j]$.

**$\chi$ (chi)**

Bitwise combine along rows, using $x \leftarrow x \oplus (\neg y \& z)$. To be precise, $a[i][\,j][k] \leftarrow a[i][\,j][k] \oplus (\neg a[i][\,j+1][k] \& a[i][\,j+2][k])$. This is the only non-linear operation in SHA-3.

**$\iota$ (iota)**

Exclusive-or a round constant into one word of the state. To be precise, in round $n$, for $0 \le m \le \ell$, $a[0][0][2^{m}-1]$ is XORed with bit $m + 7n$ of a degree-8 [LFSR](https://en.wikipedia.org/wiki/LFSR) sequence. This breaks the symmetry that is preserved by the other steps.

## Speed {#Speed}

The speed of SHA-3 hashing of long messages is dominated by the computation of *f* = Keccak-f\[1600\] and XORing *S* with the extended *P*<sub>i</sub>, an operation on *b* = 1600 bits. However, since the last *c* bits of the extended *P*<sub>i</sub> are 0 anyway, and XOR with 0 is a NOP, it is sufficient to perform XOR operations only for *r* bits (*r* = 1600 − 2 × 224 = 1152 bits for SHA3-224, 1088 bits for SHA3-256, 832 bits for SHA3-384 and 576 bits for SHA3-512). The lower *r* is (and, conversely, the higher *c* = *b* − *r* = 1600 − *r*), the less efficient but more secure the hashing becomes since fewer bits of the message can be XORed into the state (a quick operation) before each application of the computationally expensive *f*. The authors report the following speeds for software implementations of Keccak-f\[1600\] plus XORing 1024 bits,[^o45] which roughly corresponds to SHA3-256:

- \57.4 [cpb](https://en.wikipedia.org/wiki/Cycles_per_byte) on IA-32, Intel Pentium 3[^o46]
- 41 cpb on IA-32+MMX, Intel Pentium 3
- 20 cpb on IA-32+SSE, Intel Core 2 Duo or AMD Athlon 64
- \12.6 cpb on a typical x86-64-based machine
- 6–7 cpb on [IA-64](https://en.wikipedia.org/wiki/IA-64)[^o45]

For the exact SHA3-256 on x86-64, Bernstein measures 11.7–12.25 cpb depending on the CPU.[^o47] SHA-3 has been criticized for being slow on instruction set architectures (CPUs) which do not have instructions meant specially for computing Keccak functions faster – SHA2-512 is more than twice as fast as SHA3-512, and SHA-1 is more than three times as fast on an Intel Skylake processor clocked at 3.2 GHz.[^o48] The authors have reacted to this criticism by suggesting to use SHAKE128 and SHAKE256 instead of SHA3-256 and SHA3-512[^o48], at the expense of cutting the preimage resistance in half (but while keeping the collision resistance). With this, performance is on par with SHA2-256 and SHA2-512.

However, in [hardware implementations](https://en.wikipedia.org/wiki/Application-specific_integrated_circuit), SHA-3 is notably faster than all other finalists,[^o49] and also faster than SHA-2 and SHA-1.[^o48]

As of 2018, ARM's ARMv8[^o50] architecture includes special instructions which enable Keccak algorithms to execute faster and IBM's [z/Architecture](https://en.wikipedia.org/wiki/Z/Architecture)[^o51] includes a complete implementation of SHA-3 and SHAKE in a single instruction. There have also been extension proposals for [RISC-V](https://en.wikipedia.org/wiki/RISC-V) to add Keccak-specific instructions.[^o52]

SHA-3 instances are drop-in replacements for SHA-2, intended to have identical security properties.

SHAKE will generate as many bits from its sponge as requested, thus being [extendable-output functions](https://en.wikipedia.org/wiki/Extendable-output_function) (XOFs). For example, SHAKE128(M, 256) can be used as a hash function with a 256 character bitstream with 128-bit security strength. Arbitrarily large lengths can be used as pseudo-random number generators. Alternately, SHAKE256(M, 128) can be used as a hash function with a 128-bit length and 128-bit resistance.[^o7]

All instances append some bits to the message, the rightmost of which represent the [domain separation](https://en.wikipedia.org/wiki/Domain_separation_%28cryptography%29) suffix. The purpose of this is to ensure that it is not possible to construct messages that produce the same hash output for different applications of the Keccak hash function. ## Later developments {#Later_developments}

::: {#o62 .pointer-item cue=pointer name="Kangaroo Twelve"}

### KangarooTwelve {#KangarooTwelve}

In 2016 the same team that made the SHA-3 functions and the Keccak algorithm introduced faster reduced-rounds (reduced to 12 and 14 rounds, from the 24 in SHA-3) alternatives which can exploit the availability of parallel execution by using [tree hashing](wikipedia://en/2497388): KangarooTwelve and MarsupilamiFourteen.[^o65]

These functions differ from ParallelHash, the FIPS standardized Keccak-based parallelizable hash function, with regard to the parallelism, in that they are faster than ParallelHash for small message sizes.

The reduced number of rounds is justified by the huge cryptanalytic effort focused on Keccak which did not produce practical attacks on anything close to twelve-round Keccak. These higher-speed algorithms are not part of SHA-3 (as they are a later development), and thus are not FIPS compliant; but because they use the same Keccak permutation they are secure for as long as there are no attacks on SHA-3 reduced to 12 rounds.[^o65]

KangarooTwelve is a higher-performance reduced-round (from 24 to 12 rounds) version of Keccak which claims to have 128 bits of security[^o66] while having performance as high as 0.55 [cycles per byte](https://en.wikipedia.org/wiki/Cycles_per_byte) on a [Skylake](https://en.wikipedia.org/wiki/Skylake_%28microarchitecture%29) CPU.[^o67] This algorithm is specified in [IETF](https://en.wikipedia.org/wiki/Internet_Engineering_Task_Force) [RFC](https://en.wikipedia.org/wiki/Request_for_Comments) 9861.[^o68]

MarsupilamiFourteen, a slight variation on KangarooTwelve, uses 14 rounds of the Keccak permutation and claims 256 bits of security. Note that 256-bit security is not more useful in practice than 128-bit security, but may be required by some standards.[^o66] 128 bits are already sufficient to defeat brute-force attacks on current hardware, so having 256-bit security does not add practical value, unless the user is worried about significant advancements in the speed of *classical* computers. For resistance against *quantum* computers, see below.

KangarooTwelve and MarsupilamiFourteen are Extendable-Output Functions, similar to SHAKE, therefore they generate closely related output for a common message with different output length (the longer output is an extension of the shorter output). Such property is not exhibited by hash functions such as SHA-3 or ParallelHash (except of XOF variants).[^o7]

:::

### The Farfalle construction {#The_Farfalle_construction}

In 2016, the Keccak team released a different construction called [Farfalle construction](https://en.wikipedia.org/wiki/Farfalle_construction), and Kravatte, an instance of Farfalle using the Keccak-p permutation,[^o70] as well as two authenticated encryption algorithms Kravatte-SANE and Kravatte-SANSE[^o71]

### Sakura tree hashing {#Sakura_tree_hashing}

RawSHAKE is the basis for the Sakura coding for tree hashing, which has not been standardized yet. Sakura uses a suffix of 1111 for single nodes, equivalent to SHAKE, and other generated suffixes depending on the shape of the tree.[^o54]

## Security against quantum attacks {#Security_against_quantum_attacks}

There is a general result ([Grover's algorithm](wikipedia://en/58498)) that quantum computers can perform a structured [preimage attack](wikipedia://en/969477) in $\sqrt{2^d} = 2^{d/2}$, while a classical [brute-force attack](wikipedia://en/53784) needs 2<sup>*d*</sup>. A structured preimage attack implies a second preimage attack[^o74] and thus a [collision attack](wikipedia://en/969624). A quantum computer can also perform a [birthday attack](wikipedia://en/189369), thus break collision resistance, in $\sqrt[3]{2^d} = 2^{d/3}$[^o75] (although that is disputed).[^o76] Noting that the maximum strength can be $c/2$, this gives the following upper[^o77] bounds on the quantum security of SHA-3:

It has been shown that the [Merkle–Damgård construction](wikipedia://en/4076217), as used by SHA-2, is collapsing and, by consequence, quantum collision-resistant,[^o78] but for the sponge construction used by SHA-3, the authors provide proofs only for the case when the block function *f* is not efficiently invertible; Keccak-f\[1600\], however, is efficiently invertible, and so their proof does not apply.[^o79]

## Hardware acceleration {#Hardware_acceleration}

[Apple A13](https://en.wikipedia.org/wiki/Apple_A13) ARMv8 six-core [SoC](https://en.wikipedia.org/wiki/System_on_a_chip) CPU cores have support[^o92] for accelerating SHA-3 (and SHA-512) using specialized instructions from ARMv8.2-SHA crypto extension set.[^o93] These instructions do not implement the full SHA3 procedure; instead, they implement smaller operations: EOR3 (three-way XOR), RAX (rotate and XOR), XAR (XOR and rotate), BCAX (Bit-clear and XOR).

[OpenSSL](wikipedia://en/438819) includes various assembly-language implementations of SHA-3 (or rather, the Keccak-f\[1600\] sponge function). Most improvement comes from optimization of [scalar](https://en.wikipedia.org/wiki/Single_instruction,_single_data) code and not much is gained from [SIMD](https://en.wikipedia.org/wiki/SIMD).

- On 32-bit x86, only a [MMX](wikipedia://en/55364) implementation is provided as "non-MMX-capable processors is an extinct breed". Comments note that it runs at about twice the speed as the scalar x86 code generated by gcc-5.x.[^o94]
- On 64-bit x86, there are generic, AVX2, AVX-512, and AVX-512VL implementations. The plain version is about 15% faster than code generated by gcc-5.x, the AVX2 version another 15% faster than the generic version on Intel processors (while being much slower on Ryzen). The AVX-512 versions show about 50% improvement over generic on Skylake-X.[^o95]
- On ARMv4 and above, the handwritten scalar code provides a doubling to tripling of performance over compiler output. The Thumb-2 scalar code provides about 10% benefit. The NEON code provides another doubling of performance, though even in the best case (Snapdragon S4) it takes 24 cycles for each byte processed.[^o96] On ARMv8, using NEON instructions do not provide any benefit, except in the case of ARMv8.2-SHA where vector registers are lightly used for the hardware-assisted instructions.[^o97]
- On PowerPC, the scalar assembly version is about twice as fast as gcc-4.x code (newer compilers do much better). [POWER8](https://en.wikipedia.org/wiki/POWER8) has a 2x64-bit vector rotate which is helpful, but in POWER9 the faster scalar issue capacity makes the scalar version once again faster.[^o98]

The IBM [z/Architecture](https://en.wikipedia.org/wiki/Z/Architecture) supports SHA-3 since 2017 as part of the Message-Security-Assist Extension 6. The processors support a complete implementation of the entire SHA-3 and SHAKE algorithms via the KIMD and KLMD instructions using a hardware assist engine built into each core.[^o99]

### Parallel variants {#Parallel_variants}

It is easier to accelerate parallel variants of SHA-3 such as ParallelHash128. One such implementation for [SSSE3](wikipedia://en/4698729) is found in Crypto++.[^o101]

## Usage in protocols {#Usage_in_protocols}

[Ethereum](https://en.wikipedia.org/wiki/Ethereum) uses the Keccak-256 hash function (as per version 3 of the winning entry to the SHA-3 contest by Bertoni et al., which is different from the final SHA-3 specification).[^n1]
