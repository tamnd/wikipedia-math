# ChaCha20-Poly1305

::: {#o1 .subject cue=lead name="ChaCha20-Poly1305"}

**ChaCha20-Poly1305** is an [authenticated encryption with associated data (AEAD)](wikipedia://en/2244296) algorithm, that combines the [ChaCha20](wikipedia://en/2701329#ChaCha_variant) stream cipher with the [Poly1305](wikipedia://en/2017690) message authentication code.8439 It has fast software performance, and, without hardware acceleration, is usually faster than [AES-GCM](wikipedia://en/5897139).8439

:::

## History {#History}

The two building blocks of the construction, the algorithms Poly1305 and ChaCha20, were both independently designed, in 2005 and 2008, by [Daniel J. Bernstein](wikipedia://en/198983).[^o3][^o4]

In March 2013, a proposal was made to the IETF TLS working group to include [Salsa20](wikipedia://en/2701329), a winner of the [eSTREAM](wikipedia://en/2287686) competition[^o5] to replace the aging RC4-based ciphersuites. A discussion followed in the IETF TLS mailing list with various enhancement suggestions, including using Chacha20 instead of Salsa20 and using a universal hashing based MAC for performance. The outcome of this process was the adoption of Adam Langley's proposal for a variant of the original ChaCha20 algorithm (using 32-bit counter and 96-bit nonce) and a variant of the original Poly1305 (authenticating 2 strings) being combined in an IETF draft[^o6][^o7] to be used in [TLS](wikipedia://en/187813) and [DTLS](wikipedia://en/1500599),[^o8] and chosen, for security and performance reasons, as a newly supported cipher.[^o9] Shortly after the IETF's adoption of ChaCha20 and Poly1305 for TLS, the combined AEAD mode was added to [OpenSSH](wikipedia://en/25490426) via the`chacha20-poly1305@openssh.com` authenticated encryption cipher[^o10][^o11] but kept the original 64-bit counter and 64-bit nonce for the ChaCha20 algorithm.

In 2015, the AEAD algorithm was standardized in RFC 75397539 and in RFC 76347634 to be used in IPsec. The same year, it was integrated by Cloudflare as an alternative ciphersuite.[^o12]

In 2016 RFC 79057905 describes how to use it in the TLS 1.2 and DTLS 1.2 protocols.

In June 2018, RFC 7539 was updated and replaced by RFC 8439.8439

## Description {#Description}

The ChaCha20-Poly1305 algorithm takes as input a 256-bit key and a 96-bit [nonce](wikipedia://en/6988390) to encrypt a plaintext,8439 with a ciphertext expansion of 128-bit (the tag size). In the ChaCha20-Poly1305 construction, ChaCha20 is used to derive a key stream that is [XORed](wikipedia://en/264399#XOR) with the plaintext. The ciphertext and the associated data is then authenticated using a variant of Poly1305 that first encodes the two strings into one. The way that a cipher and a one time authenticator are combined is precisely identical to [AES-GCM](wikipedia://en/5897139) construction in how the first block is used to seed the authenticator and how the ciphertext is then authenticated with a 16-byte tag.

The main external difference with ChaCha20 is its 64 byte (512 bit) block size, in comparison to 16 bytes (128 bit) with both AES-128 and AES-256. The larger block size enables higher performance on modern CPUs and allows for larger streams before the 32 bit counter overflows.

## Variants {#Variants}

### XChaCha20-Poly1305 – extended nonce variant {#XChaCha20-Poly1305_–_extended_nonce_variant}

The XChaCha20-Poly1305 construction is an extended 192-bit nonce variant of the ChaCha20-Poly1305 construction, using [XChaCha20](wikipedia://en/2701329#XChaCha) instead of [ChaCha20](wikipedia://en/2701329#ChaCha_variant). When choosing nonces at random, the XChaCha20-Poly1305 construction allows for better security than the original construction. The draft attempt to standardize the construction expired in July 2020.[^o17]

::: {#o19 .pointer-item cue=pointer name="Salsa20-Poly1305"}

### Salsa20-Poly1305 and XSalsa20-Poly1305 {#Salsa20-Poly1305_and_XSalsa20-Poly1305}

Salsa20-Poly1305 and XSalsa20-Poly1305 are variants of the ChaCha20-Poly1305 and XChaCha20-Poly1305 algorithms, using [Salsa20](wikipedia://en/2701329) and [XSalsa20](wikipedia://en/2701329#XSalsa20_with_192-bit_nonce) in place of ChaCha20 and XChaCha20. They are implemented in [NaCl](https://en.wikipedia.org/wiki/NaCl_%28software%29)[^o20] and libsodium[^o21] but not standardized. The variants using ChaCha are preferred in practice as they provide better [diffusion](wikipedia://en/537555#Diffusion) per round than Salsa.[^o3]

:::

### Reduced-round variants {#Reduced-round_variants}

ChaCha20 can be replaced with its reduced-round variants ChaCha12 and ChaCha8, yielding ChaCha12-Poly1305 and ChaCha8-Poly1305. The same modification can be applied to XChaCha20-Poly1305. These are implemented by the RustCrypto team and not standardized.[^o23]

:::

## Use {#Use}

ChaCha20-Poly1305 is used in [IPsec](https://en.wikipedia.org/wiki/IPsec),8439 [SSH](https://en.wikipedia.org/wiki/SSH),9001 [TLS 1.2](wikipedia://en/187813#TLS_1.2), [DTLS](wikipedia://en/1500599) 1.2, [TLS 1.3](wikipedia://en/187813#TLS_1.3),79059001 [WireGuard](https://en.wikipedia.org/wiki/WireGuard),[^o26] [S/MIME 4.0](https://en.wikipedia.org/wiki/S/MIME),8103 [OTR](https://en.wikipedia.org/wiki/Off-the-record_messaging)v4[^o27] and multiple other protocols and implemented in [OpenSSL](wikipedia://en/438819) and [libsodium](https://en.wikipedia.org/wiki/Libsodium). Additionally, the algorithm is used in the backup software [Borg](https://en.wikipedia.org/wiki/Borg_%28backup_software%29)[^o28] in order to provide standard data encryption and in the [copy-on-write](https://en.wikipedia.org/wiki/Copy-on-write) filesystem [Bcachefs](https://en.wikipedia.org/wiki/Bcachefs) for the purpose of optional whole filesystem encryption.[^o29] It's also one of the encryption traffic methods of [V2Ray](https://en.wikipedia.org/wiki/V2Ray).

:::

## Performance {#Performance}

ChaCha20-Poly1305 usually offers better performance than the more prevalent [AES](wikipedia://en/1260)-[GCM](wikipedia://en/5897139) algorithm, except on systems where the CPU(s) have the [AES-NI instruction set](wikipedia://en/23095336) extension8439. As a result, ChaCha20-Poly1305 is sometimes preferred over AES-GCM due to its similar levels of security and in certain use cases involving [mobile devices](https://en.wikipedia.org/wiki/Mobile_device), which mostly use [ARM](https://en.wikipedia.org/wiki/ARM_architecture)-based CPUs. Because ChaCha20-Poly1305 has less overhead than AES-GCM, ChaCha20-Poly1305 on mobile devices may consume less power than AES-GCM.

## Security {#Security}

The ChaCha20-Poly1305 construction is generally secure in the [standard model](wikipedia://en/4488342) and the [ideal permutation model](wikipedia://en/451286#Ideal_Permutation), for the single- and multi-user setting.[^o32] However, similarly to [GCM](wikipedia://en/5897139), the security relies on choosing a unique [nonce](wikipedia://en/6988390) for every message encrypted. Compared to AES-GCM, implementations of ChaCha20-Poly1305 are less vulnerable to [timing attacks](https://en.wikipedia.org/wiki/Timing_attacks).

To be noted, when the [SSH](wikipedia://en/28814) protocol uses ChaCha20-Poly1305 as underlying primitive, it is vulnerable to the [Terrapin attack](https://en.wikipedia.org/wiki/Terrapin_attack).
