# Conjunctive query

::: {#o1 .subject cue=lead name="Conjunctive query"}

In [database theory](https://en.wikipedia.org/wiki/Database_theory), a **conjunctive query** is a restricted form of [first-order](wikipedia://en/10983) queries using the [logical conjunction](wikipedia://en/18152) operator. Many first-order queries can be written as conjunctive queries. In particular, a large part of queries issued on [relational databases](https://en.wikipedia.org/wiki/Relational_database) can be expressed in this way. Conjunctive queries also have a number of desirable theoretical properties that larger classes of queries (e.g., the [relational algebra](wikipedia://en/175285) queries) do not share.

:::

::: {#o3 .definition cue=heading name="Definition"}

## Definition {#Definition}

The conjunctive queries are the fragment of (domain independent) [first-order logic](wikipedia://en/10983) given by the set of formulae that can be constructed from [atomic formulae](wikipedia://en/4472066) using [conjunction](wikipedia://en/18152) ∧ and [existential quantification](wikipedia://en/91420) ∃, but not using [disjunction](https://en.wikipedia.org/wiki/Disjunction) ∨, [negation](wikipedia://en/161019) ¬, or [universal quantification](wikipedia://en/76174) ∀. Each such formula can be rewritten (efficiently) into an equivalent formula in [prenex normal form](wikipedia://en/421068), thus this form is usually simply assumed.

Thus conjunctive queries are of the following general form:

$$(x_1, \ldots, x_k).\exists x_{k+1}, \ldots x_m. A_1 \wedge \ldots \wedge A_r,$$

with the [free variables](wikipedia://en/147460) $x_1, \ldots, x_k$ being called distinguished variables, and the [bound variables](wikipedia://en/147460) $x_{k+1}, \ldots, x_m$ being called undistinguished variables. $A_1, \ldots, A_r$ are [atomic formulae](wikipedia://en/4472066).

As an example of why the restriction to domain independent first-order logic is important, consider $x_1.\exists x_2. R(x_2)$, which is not domain independent; see [Codd's theorem](wikipedia://en/18900634). This formula cannot be implemented in the select-project-join fragment of relational algebra, and hence should not be considered a conjunctive query.

Conjunctive queries can express a large proportion of queries that are frequently issued on [relational databases](https://en.wikipedia.org/wiki/Relational_database). To give an example, imagine a relational database for storing information about students, their address, the courses they take and their gender. Finding all male students and their addresses who attend a course that is also attended by a female student is expressed by the following conjunctive query:

(student, address) . ∃ (student2, course) . attends(student, course) ∧ gender(student, 'male') ∧ attends(student2, course) ∧ gender(student2, 'female') ∧ lives(student, address)

Note that since the only entity of interest is the male student and his address, these are the only distinguished variables, while the variables `course`, `student2` are only [existentially quantified](wikipedia://en/91420), i.e. undistinguished.

:::

## Fragments {#Fragments}

Conjunctive queries without distinguished variables are called [boolean conjunctive queries](https://en.wikipedia.org/wiki/Boolean_conjunctive_query). Conjunctive queries where all variables are distinguished (and no variables are bound) are called **equi-join queries**,[^o5] because they are the equivalent, in the [relational calculus](https://en.wikipedia.org/wiki/Relational_calculus), of the [equi-join](https://en.wikipedia.org/wiki/Equi-join) queries in the [relational algebra](wikipedia://en/175285) (when selecting all columns of the result).

## Relationship to other query languages {#Relationship_to_other_query_languages}

Conjunctive queries also correspond to select-project-join queries in [relational algebra](wikipedia://en/175285) (i.e., relational algebra queries that do not use the operations union or difference) and to select-from-where queries in [SQL](wikipedia://en/29004) in which the where-condition uses exclusively conjunctions of atomic equality conditions, i.e. conditions constructed from column names and constants using no comparison operators other than "=", combined using "and". Notably, this excludes the use of aggregation and subqueries. For example, the above query can be written as an SQL query of the conjunctive query fragment as

```sql
select l.student, l.address
from   attends a1, gender g1,
       attends a2, gender g2,
       lives l
where  a1.student = g1.student and
       a2.student = g2.student and
       l.student = g1.student and
       a1.course = a2.course and
       g1.gender = 'male' and
       g2.gender = 'female';
```

## Datalog {#Datalog}

Besides their logical notation, conjunctive queries can also be written as [Datalog](https://en.wikipedia.org/wiki/Datalog) rules. Many authors in fact prefer the following Datalog notation for the query above:

```prolog
 result(student, address) :- attends(student, course),  gender(student, male),
                             attends(student2, course), gender(student2, female),
                             lives(student, address).
```

Although there are no quantifiers in this notation, variables appearing in the head of the rule are still implicitly [universally quantified](wikipedia://en/76174), while variables only appearing in the body of the rule are still implicitly existentially quantified.

While any conjunctive query can be written as a Datalog rule, not every Datalog program can be written as a conjunctive query. In fact, only single rules over extensional predicate symbols can be easily rewritten as an equivalent conjunctive query. The problem of deciding whether for a given Datalog program there is an equivalent [nonrecursive program](wikipedia://en/25407) (corresponding to a positive relational algebra query, or, equivalently, a formula of positive existential [first-order logic](wikipedia://en/10983), or, as a special case, a conjunctive query) is known as the [Datalog boundedness](https://en.wikipedia.org/wiki/Datalog_boundedness) problem and is undecidable.[^o8]

## Extensions {#Extensions}

Extensions of conjunctive queries capturing more [expressive power](https://en.wikipedia.org/wiki/Expressive_power_%28computer_science%29) include:

- **unions of conjunctive queries**, which are equivalent to positive (i.e., [negation](wikipedia://en/161019)-free) [relational algebra](wikipedia://en/175285)
- **conjunctive queries extended by union and [negation](wikipedia://en/161019)**, which by [Codd's theorem](wikipedia://en/18900634) correspond to [relational algebra](wikipedia://en/175285) and [first-order logic](wikipedia://en/10983)
- conjunctive queries with **built-in predicates**, e.g., arithmetic predicates
- conjunctive queries with **[aggregate functions](https://en.wikipedia.org/wiki/Aggregate_function)**.

The formal study of all of these extensions is justified by their application in [relational databases](https://en.wikipedia.org/wiki/Relational_databases) and is in the realm of [database theory](https://en.wikipedia.org/wiki/Database_theory).

:::

## Complexity {#Complexity}

For the study of the [computational complexity](wikipedia://en/2230) of evaluating conjunctive queries, two problems have to be distinguished. The first is the problem of evaluating a conjunctive query on a [relational database](https://en.wikipedia.org/wiki/Relational_database) where both the query and the database are considered part of the input. The complexity of this problem is usually referred to as **combined complexity**, while the complexity of the problem of evaluating a query on a relational database, where the query is assumed fixed, is called **data complexity**.[^o12]

Conjunctive queries are [NP-complete](https://en.wikipedia.org/wiki/NP-complete) with respect to [combined complexity](https://en.wikipedia.org/wiki/Combined_complexity),[^o13] while the data complexity of conjunctive queries is very low, in the parallel complexity class [AC0](wikipedia://en/7400698), which is contained in [LOGSPACE](https://en.wikipedia.org/wiki/LOGSPACE) and thus in [polynomial time](https://en.wikipedia.org/wiki/Polynomial_time). The [NP-hardness](https://en.wikipedia.org/wiki/NP-hard) of conjunctive queries may appear surprising, since [relational algebra](wikipedia://en/175285) and [SQL](wikipedia://en/29004) strictly subsume the conjunctive queries and are thus at least as hard (in fact, relational algebra is [PSPACE](wikipedia://en/39351)-complete with respect to combined complexity and is therefore even harder under widely held complexity-theoretic assumptions). However, in the usual application scenario, databases are large, while queries are very small, and the data complexity model may be appropriate for studying and describing their difficulty.

The problem of listing all answers to a non-Boolean conjunctive query has been studied in the context of [enumeration algorithms](https://en.wikipedia.org/wiki/Enumeration_algorithm), with a characterization (under some [computational hardness assumptions](wikipedia://en/6158383)) of the queries for which enumeration can be performed with [linear time](https://en.wikipedia.org/wiki/Linear_time) preprocessing and [constant](https://en.wikipedia.org/wiki/Constant_time) delay between each solution. Specifically, these are the acyclic conjunctive queries which also satisfy a *free-connex* condition.[^o14]

## Formal properties {#Formal_properties}

Conjunctive queries are one of the great success stories of [database theory](https://en.wikipedia.org/wiki/Database_theory) in that many interesting problems that are computationally hard or [undecidable](wikipedia://en/15631055) for larger classes of queries are feasible for conjunctive queries.[^o16] For example, consider the [query containment problem](https://en.wikipedia.org/wiki/Query_containment_problem). We write $R \subseteq S$ for two [database relations](https://en.wikipedia.org/wiki/Database_relation) $R, S$ of the same [schema](https://en.wikipedia.org/wiki/Database_schema) if and only if each tuple occurring in $R$ also occurs in $S$. Given a query $Q$ and a [relational database](https://en.wikipedia.org/wiki/Relational_database) instance $I$, we write the result relation of evaluating the query on the instance simply as $Q(I)$. Given two queries $Q_1$ and $Q_2$ and a [database schema](https://en.wikipedia.org/wiki/Database_schema), the query containment problem is the problem of deciding whether for all possible database instances $I$ over the input database schema, $Q_1(I) \subseteq Q_2(I)$. The main application of query containment is in query optimization: Deciding whether two queries are equivalent is possible by simply checking mutual containment.

The query containment problem is undecidable for [relational algebra](wikipedia://en/175285) and [SQL](wikipedia://en/29004) but is decidable and [NP-complete](https://en.wikipedia.org/wiki/NP-complete)[^o17] for conjunctive queries. In fact, it turns out that the query containment problem for conjunctive queries is exactly the same problem as the query evaluation problem.[^o16] Since queries tend to be small, [NP-completeness](wikipedia://en/23385892) here is usually considered acceptable. The query containment problem for conjunctive queries is also equivalent to the [constraint satisfaction problem](wikipedia://en/211652).[^o18]

An important class of conjunctive queries that have polynomial-time combined complexity are the **acyclic** conjunctive queries.[^o19] The query evaluation, and thus query containment, is [LOGCFL](wikipedia://en/4734121)-complete and thus in [polynomial time](https://en.wikipedia.org/wiki/Polynomial_time).[^o20] Acyclicity of conjunctive queries is a structural property of queries that is defined with respect to the query's [hypergraph](wikipedia://en/232535):[^o16] a conjunctive query is acyclic if and only if it has hypertree-width 1. For the special case of conjunctive queries in which all relations used are binary, this notion corresponds to the treewidth of the [dependency graph](wikipedia://en/5021549) of the variables in the query (i.e., the graph having the variables of the query as nodes and an undirected edge $\{x,y\}$ between two variables if and only if there is an atomic formula $R(x,y)$ or $R(y,x)$ in the query) and the conjunctive query is acyclic if and only if its dependency graph is [acyclic](wikipedia://en/325806).

An important generalization of acyclicity is the notion of [bounded hypertree-width](https://en.wikipedia.org/wiki/Hypertree_decomposition), which is a measure of how close to acyclic a hypergraph is, analogous to bounded [treewidth](wikipedia://en/3987086) in [graphs](wikipedia://en/325806). Conjunctive queries of bounded tree-width have [LOGCFL](wikipedia://en/4734121) combined complexity.[^o21]

Unrestricted conjunctive queries over tree data (i.e., a relational database consisting of a binary child relation of a tree as well as unary relations for labeling the tree nodes) have polynomial time combined complexity.[^o22]
