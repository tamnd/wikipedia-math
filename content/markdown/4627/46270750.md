# DNS Certification Authority Authorization

::: {#o1 .subject cue=lead name="DNS Certification Authority Authorization"}

**DNS Certification Authority Authorization** (**CAA**) is an [Internet security](https://en.wikipedia.org/wiki/Internet_security) policy mechanism for [domain name](https://en.wikipedia.org/wiki/Domain_name) registrants to indicate to [certificate authorities](https://en.wikipedia.org/wiki/Certificate_authorities) whether they are authorized to issue [digital certificates](https://en.wikipedia.org/wiki/Digital_certificates) for a particular [domain name](https://en.wikipedia.org/wiki/Domain_name). Registrants publish a "CAA" [Domain Name System](https://en.wikipedia.org/wiki/Domain_Name_System) (DNS) [resource record](https://en.wikipedia.org/wiki/Resource_record) which compliant certificate authorities check for before issuing digital certificates.

:::

CAA was drafted by computer scientists [Phillip Hallam-Baker](https://en.wikipedia.org/wiki/Phillip_Hallam-Baker) and Rob Stradling in response to increasing concerns about the security of publicly trusted certificate authorities. It is an [Internet Engineering Task Force](https://en.wikipedia.org/wiki/Internet_Engineering_Task_Force) (IETF) [proposed standard](https://en.wikipedia.org/wiki/Internet_Standard#Proposed_Standard).

## Background {#Background}

A [series of incorrectly issued certificates](wikipedia://en/296370#CA_compromise) from 2001 onwards[^o4][^o5] damaged trust in publicly trusted certificate authorities,[^o6] and accelerated work on various security mechanisms, including [Certificate Transparency](wikipedia://en/41061790) to track misissuance, [HTTP Public Key Pinning](wikipedia://en/45619411) and [DANE](wikipedia://en/38213001) to block misissued certificates on the [client side](https://en.wikipedia.org/wiki/Client_side), and CAA to block misissuance on the certificate authority side.[^o13]

The first draft of CAA was written by [Phillip Hallam-Baker](https://en.wikipedia.org/wiki/Phillip_Hallam-Baker) and Rob Stradling, and submitted as an [IETF Internet Draft](https://en.wikipedia.org/wiki/IETF_Internet_Draft) in October 2010.[^o7] This was progressively improved by the [PKIX Working Group](https://en.wikipedia.org/wiki/X.509#PKIX_Working_Group),[^o8] and approved by the [IESG](https://en.wikipedia.org/wiki/IESG) as 6844, a [Proposed Standard](https://en.wikipedia.org/wiki/Internet_Standard#Proposed_Standard), in January 2013.[^o9] [CA/Browser Forum](https://en.wikipedia.org/wiki/CA/Browser_Forum) discussion began shortly afterward,[^o13] and in March 2017 they voted in favor of making CAA implementation mandatory for all certificate authorities by September 2017.[^o10][^o11] At least one certificate authority, [Comodo](https://en.wikipedia.org/wiki/Comodo_Group), failed to implement CAA before the deadline.[^o12] A 2017 study by the [Technical University of Munich](https://en.wikipedia.org/wiki/Technical_University_of_Munich) found many instances where certificate authorities failed to correctly implement some part of the standard.[^o13]

In September 2017, Jacob Hoffman-Andrews submitted an Internet Draft intended to simplify the CAA standard. This was improved by the LAMPS Working Group, and approved as 8659, a Proposed Standard, in November 2019.[^o14]

, [Qualys](https://en.wikipedia.org/wiki/Qualys) reports that only 15.4% of the 150,000 most popular [TLS](wikipedia://en/187813)-supporting websites use CAA records.[^o15]

## Record {#Record}

Certificate authorities implementing CAA perform a [DNS](https://en.wikipedia.org/wiki/Domain_Name_System) lookup for CAA [resource records](https://en.wikipedia.org/wiki/Resource_record), and if any are found, ensure that the authority is listed as an authorized party in at least one of the CAA records before issuing a [digital certificate](https://en.wikipedia.org/wiki/Digital_certificate). Each CAA resource record consists of the following components:[^o14]

**flag**

A [flags byte](https://en.wikipedia.org/wiki/Flag_%28computing%29) which implements an [extensible](https://en.wikipedia.org/wiki/Extensible) signaling system for future use. , only the *issuer critical* flag has been defined, which instructs certificate authorities that they must understand the corresponding property tag before issuing a certificate.[^o14] This flag allows the protocol to be extended in the future with mandatory extensions,[^o13] similar to [critical extensions in X.509 certificates](https://en.wikipedia.org/wiki/X.509#Structure_of_a_certificate).

**tag**

One of the following properties from the [IANA](https://en.wikipedia.org/wiki/Internet_Assigned_Numbers_Authority) Certification Authority Restriction Properties registry:

**issue**

This property authorizes the holder of the domain specified in the associated property value to issue certificates for the domain for which the property is published.

**issuewild**

This property acts like *issue* but only authorizes the issuance of [wildcard certificates](https://en.wikipedia.org/wiki/Wildcard_certificate), and takes precedence over the *issue* property for wildcard certificate requests.

**issuemail**

This property authorizes the holder of the domain specified in the associated property value to issue [S/MIME](https://en.wikipedia.org/wiki/S/MIME) certificates for the domain for which the property is published.[^o17] An absent property does not prevent S/MIME certificate issuance.

**issuevmc**

This property authorizes the holder of the domain specified in the associated property value to issue [BIMI](https://en.wikipedia.org/wiki/Brand_Indicators_for_Message_Identification) certificates for the domain for which the property is published.[^o18] An absent property does not prevent BIMI certificate issuance.

**iodef**

This property specifies a method for certificate authorities to report invalid certificate requests to the domain name holder using the [Incident Object Description Exchange Format](https://en.wikipedia.org/wiki/Incident_Object_Description_Exchange_Format). , not all certificate authorities support this tag, so there is no guarantee that all certificate issuances will be reported.

**contactemail**

Increasingly, contact information is not available in WHOIS due to concerns about potential GDPR violations. This property allows domain holders to publish contact information in DNS.[^o19][^o20]

**contactphone**

As above, for phone numbers.[^o21]

**value**

The value associated with the chosen property tag.

The lack of any CAA records authorizes normal unrestricted issuance, and the presence of a single *issue* tag without a specific issuer domain name disallows all issuance.[^o14][^o11][^o22]

Third parties monitoring certificate authority behavior might check newly issued certificates against the domain's CAA records. 8659 states: CAA records MAY be used by Certificate Evaluators as a possible indicator of a security policy violation. Such use SHOULD take into account the possibility that published CAA records changed between the time a certificate was issued and the time at which the certificate was observed by the Certificate Evaluator.[^o14]

## Extensions {#Extensions}

8657 specifies `"accounturi"` and `"validationmethods"` parameters which allow users to specify desired methods of domain control validation (DCV) as defined in [ACME protocol](https://en.wikipedia.org/wiki/Automated_Certificate_Management_Environment). For example, website administrators can bind a domain they control to a particular account registered with their desired Certification Authority.

### History {#History}

A draft of the first extension to the CAA standard was published on October 26, 2016, proposing a new *account-uri* token to the end of the *issue* property, which ties a domain to a specific [Automated Certificate Management Environment](https://en.wikipedia.org/wiki/Automated_Certificate_Management_Environment) account.[^o26] This was amended on August 30, 2017, to also include a new *validation-methods* token, which ties a domain to a specific validation method,[^o27] and then further amended on June 21, 2018, to remove the hyphen in *account-uri* and *validation-methods* making them instead *accounturi* and *validationmethods*.[^o28]

:::

## Examples {#Examples}

To indicate that only the certificate authority identified by *ca.example.net* is authorized to issue certificates for [example.com](https://en.wikipedia.org/wiki/Example.com) and all subdomains, one may use this CAA record:[^o14]

example.com. IN CAA 0 issue "ca.example.net"

To indicate that *ca.example.net* and *ca.example.org* are both authorized to issue certificates for [example.com](https://en.wikipedia.org/wiki/Example.com) and all subdomains, two CAA records are needed:[^o14]

example.com. IN CAA 0 issue "ca.example.net" example.com. IN CAA 0 issue "ca.example.org"

To disallow any certificate issuance, a semicolon may be used:

example.com. IN CAA 0 issue ";"

To indicate that certificate authorities should report invalid certificate requests to an [email address](https://en.wikipedia.org/wiki/Email_address) and a [Real-time Inter-network Defense](https://en.wikipedia.org/wiki/Real-time_Inter-network_Defense) endpoint:

example.com. IN CAA 0 iodef "mailto:security@example.com" example.com. IN CAA 0 iodef "http://iodef.example.com/"

To use a future extension of the protocol, for example, one which defines a new *future* property, which needs to be understood by the certificate authority before they can safely proceed, one may set the *issuer critical* flag:

example.com. IN CAA 0 issue "ca.example.net" example.com. IN CAA 128 future "value"

:::

## Incidents {#Incidents}

In 2017, Camerfirma was found to improperly validate CAA records. Camerfirma claimed to have misunderstood the [CA/Browser Forum](https://en.wikipedia.org/wiki/CA/Browser_Forum) Baseline Requirements describing CAA validation.[^o32][^o13]

In early 2020, [Let's Encrypt](https://en.wikipedia.org/wiki/Let's_Encrypt) disclosed that their software improperly queried and validated CAA records potentially affecting over 3 million certificates.[^o33] Let's Encrypt worked with customers and site operators to replace over 1.7 million certificates, but decided not to revoke the rest to avoid client downtime since the affected certificates would expire in less than 90 days.[^o34]
