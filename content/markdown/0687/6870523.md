# Distributed key generation

::: {#o1 .subject cue=lead name="Distributed key generation"}

**Distributed key generation** (DKG) is a cryptographic process in which multiple parties contribute to the calculation of a shared public and private key set. Unlike most [public key encryption](wikipedia://en/194112) models, distributed key generation does not rely on [Trusted Third Parties](wikipedia://en/584651).[^o16] Instead, the participation of a [threshold](wikipedia://en/6866642) of honest parties determines whether a key pair can be computed successfully.[^o19] Distributed key generation prevents single parties from having access to a private key. The involvement of many parties requires Distributed key generation to ensure secrecy in the presence of [malicious](wikipedia://en/789126) contributions to the key calculation.[^o16]

:::

Distributed key generation is commonly used to decrypt shared [ciphertexts](wikipedia://en/175560) or create group [digital signatures](wikipedia://en/59644).[^o19]

## History {#History}

Distributed key generation protocol was first specified by Torben Pedersen in 1991. This first model depended on the security of the Joint-Feldman Protocol for [verifiable secret sharing](wikipedia://en/4311169) during the secret sharing process.[^o3]

In 1999, Rosario Gennaro, Stanislaw Jarecki, Hugo Krawczyk, and [Tal Rabin](https://en.wikipedia.org/wiki/Tal_Rabin) produced a series of security proofs demonstrating that Feldman verifiable secret sharing was vulnerable to malicious contributions to Pedersen's distributed key generator that would leak information about the shared private key.[^o4][^o5] The same group also proposed an updated distributed key generation scheme preventing malicious contributions from impacting the value of the private key.

::: {#o7 .definition kind=definition/construction cue=heading name="Methods"}

## Methods {#Methods}

The distributed key generation protocol specified by Gennaro, Jarecki, Krawczyk, and Rabin assumes that a group of players has already been established by an honest party prior to the key generation. It also assumes the communication between parties is [synchronous](https://en.wikipedia.org/wiki/Synchronization_%28computer_science%29).[^o5]

1. All parties use Pedersen's [verifiable secret sharing](wikipedia://en/4311169) protocol to share the results of two random [polynomial functions](wikipedia://en/23000#Polynomial_functions).
1. Every party then verifies all the shares they received. If verification fails, the recipient broadcasts a complaint for the party whose share failed. Each accused party then [broadcasts](https://en.wikipedia.org/wiki/Broadcasting_%28networking%29) their shares. Each party then has the opportunity to verify the broadcast shares or disqualify accused parties. All parties generate a common list of non-disqualified parties.
1. Each non-disqualified party broadcasts a set of values constructed by raising a common [generator](wikipedia://en/24873145#Subring_generated_by_a_set) to the power of each value used in one polynomial in **Part 1**.
1. These broadcast values are verified by each party similarly to as in **Part 2**. When a verification fails, the party now broadcasts both the values received in **Part 1** and the values received in **Part 3**. For each party with verifiable complaints, all other parties reconstruct their own value sets in order to eliminate disqualified contributions.
1. The group computes the private key as the product of every qualified contribution (each qualified party's random polynomial evaluated at 0).[^o5]

:::

## Avoiding the synchrony assumption {#Avoiding_the_synchrony_assumption}

In 2009, Aniket Kate and Ian Goldberg presented a Distributed key generation protocol suitable for use over the Internet.[^o9] Unlike earlier constructions, this protocol does not require a broadcast channel or the synchronous communication assumption, and a [ready-to-use library](https://crysp.uwaterloo.ca/software/DKG/) is available.

## Robustness {#Robustness}

In many circumstances, a [robust](https://en.wikipedia.org/wiki/Robustness_%28computer_science%29) distributed key generator is necessary. Robust generator protocols can reconstruct public keys in order to remove malicious shares even if malicious parties still remain in the qualified group during the reconstruction phase.[^o5] For example, robust multi-party digital signatures can tolerate a number of malicious users roughly proportionate to the length of the modulus used during key generation.[^o11]

## Sparse-evaluated DKG {#Sparse-evaluated_DKG}

Distributed key generators can implement a sparse evaluation matrix in order to improve efficiency during verification stages. Sparse evaluation can improve run time from $O(nt)$ (where $n$ is the number of parties and $t$ is the threshold of malicious users) to $O(log^3n)$. Instead of robust verification, sparse evaluation requires that a small set of the parties verify a small, randomly picked set of shares. This results in a small probability that the key generation will fail in the case that a large number of malicious shares are not chosen for verification.[^o13]

::: {#o15 .application cue=heading name="Applications"}

## Applications {#Applications}

Distributed key generation and distributed key cryptography are rarely applied over the internet because of the reliance on synchronous communication.[^o5]

Distributed key cryptography is useful in [key escrow](wikipedia://en/17114) services where a company can meet a threshold to decrypt a ciphertext version of private key. This way a company can require multiple employees to recover a private key without giving the escrow service a plaintext copy.[^o16]

Distributed key generation is also useful in [server-side](https://en.wikipedia.org/wiki/Server-side) password [authentication](https://en.wikipedia.org/wiki/Authentication_protocol). If [password hashes](wikipedia://en/439526#Password_verification) are stored on a single server, a breach in the server would result in all the password hashes being available for attackers to [analyze](wikipedia://en/5715) offline. Variations of distributed key generation can authenticate user passwords across multiple servers and eliminate [single points of failure](https://en.wikipedia.org/wiki/Single_point_of_failure#Computing).[^o17][^o18]

Distributed key generation is more commonly used for group digital signatures. This acts as a form of voting, where a threshold of group members would have to participate in order for the group to digitally sign a document.[^o19]
