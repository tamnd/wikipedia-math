# Model checking

*Image: Two One G (cropped).jpg.* [Elevator](https://en.wikipedia.org/wiki/Elevator) control software can be model-checked to verify both safety properties, like *"The cabin never moves with its door open"*,[^o1] and liveness properties, like *"Whenever the n<sup>th</sup> floor's*call*button is pressed, the cabin will eventually stop at the n<sup>th</sup> floor and open the door"*.

::: {#o2 .subject cue=lead name="Model checking"}

In [computer science](https://en.wikipedia.org/wiki/Computer_science), **model checking** or **property checking** is a method for checking whether a [finite-state model](wikipedia://en/10931) of a system meets a given [specification](https://en.wikipedia.org/wiki/Formal_specification) (also known as [correctness](https://en.wikipedia.org/wiki/Correctness_%28computer_science%29)). This is typically associated with [hardware](https://en.wikipedia.org/wiki/Computer_hardware) or [software systems](https://en.wikipedia.org/wiki/Software_system), where the specification contains liveness requirements (such as avoidance of [livelock](https://en.wikipedia.org/wiki/Livelock)) as well as safety requirements (such as avoidance of states representing a [system crash](https://en.wikipedia.org/wiki/System_crash)).

:::

In order to solve such a problem [algorithmically](wikipedia://en/775), both the model of the system and its specification are formulated in some precise mathematical language. To this end, the problem is formulated as a task in [logic](wikipedia://en/46426065), namely to check whether a [structure](wikipedia://en/4055928) satisfies a given logical formula. This general concept applies to many kinds of logic and many kinds of structures. A simple model-checking problem consists of verifying whether a formula in the [propositional logic](wikipedia://en/18154) is satisfied by a given structure.

## Overview {#Overview}

Property checking is used for [verification](https://en.wikipedia.org/wiki/Software_verification) when two descriptions are not equivalent. During [refinement](https://en.wikipedia.org/wiki/Refinement_%28computing%29), the specification is complemented with details that are [unnecessary](https://en.wikipedia.org/wiki/Don't-care_term) in the higher-level specification. There is no need to verify the newly introduced properties against the original specification since this is not possible. Therefore, the strict bi-directional equivalence check is relaxed to a one-way property check. The implementation or design is regarded as a model of the system, whereas the specifications are properties that the model must satisfy.[^o4]

An important class of model-checking methods has been developed for checking models of [hardware](https://en.wikipedia.org/wiki/Computer_hardware) and [software](https://en.wikipedia.org/wiki/Software) designs where the specification is given by a [temporal logic](wikipedia://en/321481) formula. Pioneering work in temporal logic specification was done by [Amir Pnueli](https://en.wikipedia.org/wiki/Amir_Pnueli), who received the 1996 Turing award for "seminal work introducing temporal logic into computing science".[^o5] Model checking began with the pioneering work of [E. M. Clarke](https://en.wikipedia.org/wiki/E._M._Clarke), [E. A. Emerson](https://en.wikipedia.org/wiki/E._A._Emerson),[^o6][^o7][^o8] by J. P. Queille, and [J. Sifakis](https://en.wikipedia.org/wiki/J._Sifakis).[^o9] Clarke, Emerson, and Sifakis shared the 2007 [Turing Award](https://en.wikipedia.org/wiki/Turing_Award) for their seminal work founding and developing the field of model checking.[^o10][^o11]

Model checking is most often applied to hardware designs. For software, because of undecidability (see [computability theory](wikipedia://en/155414)) the approach cannot be fully algorithmic, apply to all systems, and always give an answer; in the general case, it may fail to prove or disprove a given property. In [embedded-systems](https://en.wikipedia.org/wiki/Embedded_system) hardware, it is possible to validate a specification delivered, e.g., by means of [UML activity diagrams](https://en.wikipedia.org/wiki/UML_activity_diagram)[^o12] or control-interpreted [Petri nets](wikipedia://en/225192).[^o13]

The structure is usually given as a source code description in an industrial [hardware description language](https://en.wikipedia.org/wiki/Hardware_description_language) or a special-purpose language. Such a program corresponds to a [finite-state machine](wikipedia://en/10931) (FSM), i.e., a [directed graph](wikipedia://en/19721986) consisting of nodes (or [vertices](wikipedia://en/638899)) and [edges](https://en.wikipedia.org/wiki/Edge_%28graph_theory%29). A set of atomic propositions is associated with each node, typically stating which memory elements are one. The [nodes](https://en.wikipedia.org/wiki/Node_%28computer_science%29) represent states of a system, the edges represent possible transitions that may alter the state, while the atomic propositions represent the basic properties that hold at a point of execution.[^o14]

Formally, the problem can be stated as follows: given a desired property, expressed as a temporal logic formula $p$, and a structure $M$ with initial state $s$, decide if $M,s \models p$. If $M$ is finite, as it is in hardware, model checking reduces to a [graph search](https://en.wikipedia.org/wiki/Graph_search).

## Symbolic model checking {#Symbolic_model_checking}

Instead of enumerating reachable states one at a time, the state space can sometimes be traversed more efficiently by considering large numbers of states at a single step. When such state-space traversal is based on representations of a set of states and transition relations as logical formulas, [binary decision diagrams](https://en.wikipedia.org/wiki/Binary_decision_diagrams) (BDD) or other related data structures, the model-checking method is *symbolic*.

Historically, the first symbolic methods used [BDDs](wikipedia://en/576855). After the success of [propositional satisfiability](https://en.wikipedia.org/wiki/Propositional_satisfiability) in solving the [planning](wikipedia://en/1505641) problem in [artificial intelligence](https://en.wikipedia.org/wiki/Artificial_intelligence) (see [satplan](https://en.wikipedia.org/wiki/Satplan)) in 1996, the same approach was generalized to model checking for [linear temporal logic](wikipedia://en/710307) (LTL): the planning problem corresponds to model checking for safety properties. This method is known as bounded model checking.[^o16] The success of [Boolean satisfiability solvers](wikipedia://en/4715) in bounded model checking led to the widespread use of satisfiability solvers in symbolic model checking.[^o17]

::: {#o19 .example cue=heading name="Example"}

### Example {#Example}

One example of such a system requirement: *Between the time an elevator is called at a floor and the time it opens its doors at that floor, the elevator can arrive at that floor at most twice*. The authors of "Patterns in Property Specification for Finite-State Verification" translate this requirement into the following LTL formula:[^o20]

$$\begin{aligned}\Box\Big((\texttt{call} \land \Diamond \texttt{open}) \to & \big((\lnot \texttt{atfloor} \land \lnot \texttt{open}) ~\mathcal{U} \\ & (\texttt{open} \lor ((\texttt{atfloor} \land \lnot \texttt{open}) ~\mathcal{U}\\ & (\texttt{open} \lor ((\lnot \texttt{atfloor} \land \lnot \texttt{open}) ~\mathcal{U} \\ & (\texttt{open} \lor ((\texttt{atfloor} \land \lnot \texttt{open}) ~\mathcal{U} \\ & (\texttt{open} \lor (\lnot \texttt{atfloor} ~\mathcal{U}~ \texttt{open}))))))))\big)\Big)\end{aligned}$$

Here, $\Box$ should be read as "always", $\Diamond$ as "eventually", $\mathcal{U}$ as "until" and the other symbols are standard logical symbols, $\lor$ for "or", $\land$ for "and" and $\lnot$ for "not".

:::

## Techniques {#Techniques}

Model-checking tools face a combinatorial blow up of the state-space, commonly known as the [state explosion problem](https://en.wikipedia.org/wiki/State_explosion_problem), that must be addressed to solve most real-world problems.[^o22] There are several approaches to combat this problem.

1. Symbolic algorithms avoid ever explicitly constructing the graph for the FSM; instead, they represent the graph implicitly using a formula in quantified propositional logic. The use of binary decision diagrams (BDDs) was made popular by the work of Ken McMillan,[^o23] as well as of Olivier Coudert and Jean-Christophe Madre,[^o24] and the development of open-source BDD manipulation libraries such as CUDD[^o25] and BuDDy.[^o26]
1. Bounded model-checking algorithms unroll the FSM for a fixed number of steps, $k$, and check whether a property violation can occur in $k$ or fewer steps. This typically involves encoding the restricted model as an instance of [SAT](wikipedia://en/4715). The process can be repeated with larger and larger values of $k$ until all possible violations have been ruled out (cf. [Iterative deepening depth-first search](wikipedia://en/433326)).
1. [Abstraction](https://en.wikipedia.org/wiki/Abstract_interpretation) attempts to prove properties of a system by first simplifying it. The simplified system usually does not satisfy exactly the same properties as the original one so that a process of refinement may be necessary. Generally, one requires the abstraction to be *sound* (the properties proved on the abstraction are true of the original system); however, sometimes the abstraction is not *complete* (not all true properties of the original system are true of the abstraction). An example of abstraction is to ignore the values of non-Boolean variables and to only consider Boolean variables and the control flow of the program; such an abstraction, though it may appear coarse, may, in fact, be sufficient to prove e.g. properties of [mutual exclusion](https://en.wikipedia.org/wiki/Mutual_exclusion).
1. Counterexample-guided abstraction refinement (CEGAR) begins checking with a coarse (i.e. imprecise) abstraction and iteratively refines it. When a violation (i.e. [counterexample](wikipedia://en/143151)) is found, the tool analyzes it for feasibility (i.e., is the violation genuine or the result of an incomplete abstraction?). If the violation is feasible, it is reported to the user. If it is not, the proof of infeasibility is used to refine the abstraction and checking begins again.[^o27]

Model-checking tools were initially developed to reason about the logical correctness of [discrete state](https://en.wikipedia.org/wiki/Discrete_system) systems, but have since been extended to deal with real-time and limited forms of [hybrid systems](wikipedia://en/564719).

## First-order logic {#First-order_logic}

Model checking is also studied in the field of [computational complexity theory](wikipedia://en/7543). Specifically, a [first-order logical](wikipedia://en/10983) formula is fixed without [free variables](https://en.wikipedia.org/wiki/Free_variable) and the following [decision problem](wikipedia://en/8336) is considered:

*Given a finite [interpretation](wikipedia://en/14511671), for instance, one described as a [relational database](https://en.wikipedia.org/wiki/Relational_database), decide whether the interpretation is a model of the formula.*

This problem is in the [circuit class](https://en.wikipedia.org/wiki/Circuit_class) **[AC<sup>0</sup>](https://en.wikipedia.org/wiki/AC0_%28complexity%29)**. It is [tractable](wikipedia://en/7543#Intractability) when imposing some restrictions on the input structure: for instance, requiring that it has [treewidth](wikipedia://en/3987086) bounded by a constant (which more generally implies the tractability of model checking for [monadic second-order logic](wikipedia://en/14650395)), bounding the [degree](wikipedia://en/1374448) of every domain element, and more general conditions such as [bounded expansion](wikipedia://en/47843724), locally bounded expansion, and nowhere-dense structures.[^o29] These results have been extended to the task of [enumerating](https://en.wikipedia.org/wiki/Enumeration_algorithm) all solutions to a first-order formula with free variables.

## Tools {#Tools}

Here is a list of significant model-checking tools:

- Afra: a model checker for [Rebeca](https://en.wikipedia.org/wiki/Rebeca_%28programming_language%29) which is an actor-based language for modeling concurrent and reactive systems
- [Alloy](https://en.wikipedia.org/wiki/Alloy_%28specification_language%29) (Alloy Analyzer)
- [BLAST](https://en.wikipedia.org/wiki/BLAST_model_checker) (Berkeley Lazy Abstraction Software Verification Tool)
- [CADP](https://en.wikipedia.org/wiki/CADP) (Construction and Analysis of Distributed Processes) a toolbox for the design of communication protocols and distributed systems
- [CPAchecker](https://en.wikipedia.org/wiki/CPAchecker): an open-source software model checker for C programs, based on the CPA framework
- [ECLAIR](https://en.wikipedia.org/wiki/ECLAIR): a platform for the automatic analysis, verification, testing, and transformation of C and C++ programs
- [FDR2](https://en.wikipedia.org/wiki/FDR2): a model checker for verifying real-time systems modelled and specified as [CSP](https://en.wikipedia.org/wiki/Communicating_sequential_processes) Processes
- [FizzBee](https://en.wikipedia.org/wiki/FizzBee): an easier to use alternative to TLA+, that uses Python-like specification language, that has both behavioral modeling like TLA+ and probabilistic modeling like PRISM
- [ISP](https://en.wikipedia.org/wiki/ISP_Formal_Verification_Tool) code level verifier for [MPI](https://en.wikipedia.org/wiki/Message_Passing_Interface) programs
- [Java Pathfinder](https://en.wikipedia.org/wiki/Java_Pathfinder): an open-source model checker for Java programs
- [Libdmc](https://en.wikipedia.org/wiki/Libdmc): a framework for distributed model checking
- [mCRL2](https://en.wikipedia.org/wiki/MCRL2) Toolset, [Boost Software License](https://en.wikipedia.org/wiki/Boost_Software_License), Based on [ACP](https://en.wikipedia.org/wiki/Algebra_of_Communicating_Processes)
- [NuSMV](https://en.wikipedia.org/wiki/NuSMV): a new symbolic model checker
- [PAT](https://en.wikipedia.org/wiki/PAT_%28model_checker%29): an enhanced simulator, model checker and refinement checker for concurrent and real-time systems
- [Prism](https://en.wikipedia.org/wiki/PRISM_%28model_checker%29): a probabilistic symbolic model checker
- [Roméo](https://en.wikipedia.org/wiki/Romeo_Model_Checker): an integrated tool environment for modelling, simulation, and verification of real-time systems modelled as parametric, time, and stopwatch Petri nets
- [SPIN](https://en.wikipedia.org/wiki/SPIN_model_checker): a general tool for verifying the correctness of distributed software models in a rigorous and mostly automated fashion
- [Storm](https://en.wikipedia.org/wiki/STORM_%28model_checker%29):[^o31] A model checker for probabilistic systems.
- [TAPAs](https://en.wikipedia.org/wiki/TAPAs_model_checker): a tool for the analysis of process algebra
- [TAPAAL](https://en.wikipedia.org/wiki/TAPAAL): an integrated tool environment for modelling, validation, and verification of Timed-Arc [Petri Nets](https://en.wikipedia.org/wiki/Petri_Nets)
- [TLA+](https://en.wikipedia.org/wiki/TLA+) model checker by [Leslie Lamport](https://en.wikipedia.org/wiki/Leslie_Lamport)
- [UPPAAL](https://en.wikipedia.org/wiki/UPPAAL): an integrated tool environment for modelling, validation, and verification of real-time systems modelled as networks of timed automata
- [Zing](https://en.wikipedia.org/wiki/Zing_%28model-checker%29)[^o32] – experimental tool from [Microsoft](https://en.wikipedia.org/wiki/Microsoft) to validate state models of software at various levels: high-level protocol descriptions, work-flow specifications, web services, device drivers, and protocols in the core of the operating system. Zing is currently being used for developing drivers for Windows.
