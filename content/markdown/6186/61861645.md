# CECPQ2

::: {#o1 .subject cue=lead name="CECPQ2"}

In [cryptography](wikipedia://en/18934432), **Combined Elliptic-Curve and Post-Quantum 2** (**CECPQ2**) is a [quantum-secure](wikipedia://en/26605226) modification to [Transport Layer Security](wikipedia://en/187813) (TLS) 1.3 developed by [Google](https://en.wikipedia.org/wiki/Google). It is intended to be used experimentally, to help evaluate the performance of post-quantum [key-exchange algorithms](https://en.wikipedia.org/wiki/Key-exchange_algorithm) on actual users' devices.[^o2]

:::

## Details {#Details}

Similarly to its predecessor [CECPQ1](wikipedia://en/51628519), CECPQ2 aims to provide confidentiality against an attacker with a large scale [quantum computer](https://en.wikipedia.org/wiki/Quantum_computer). It is essentially a plugin for the TLS [key-agreement](wikipedia://en/63944) part. CECPQ2 combines two key exchange mechanisms: the classical [X25519](https://en.wikipedia.org/wiki/X25519) and [HRSS](https://en.wikipedia.org/wiki/HRSS_%28cryptography%29) (Hülsing, Rijneveld, Schanck, and Schwabe) scheme (an instantiation of the [NTRU](wikipedia://en/481661) [lattice based](wikipedia://en/18657553) [key exchange](wikipedia://en/578092) primitive).[^o2] Additionally, Kris Kwiatkowski has implemented and deployed an alternative version of post-quantum key-exchange algorithm, titled *CECPQ2b*. Similarly to CECPQ2, this is also a hybrid post-quantum key exchange scheme, that is based on [supersingular isogeny key exchange](wikipedia://en/42674727) (SIKE) instead of HRSS. [^o4]

CECPQ2 uses 32 bytes of shared secret material derived from the classical [X25519](https://en.wikipedia.org/wiki/X25519) mechanism, and 32 bytes of shared secret material derived from the quantum-secure HRSS mechanism. The resulting bytes are concatenated and used as secret key. Concatenation is meant to assure that the protocol provides at least the same security level as widely used X25519, should HRSS be found insecure.

The algorithm was to be deployed on both the server side using [Cloudflare](https://en.wikipedia.org/wiki/Cloudflare)'s infrastructure, and the client side using [Google Chrome](https://en.wikipedia.org/wiki/Google_Chrome) Canary.[^o5] Since both parties need to support the algorithm for it to be chosen, this experiment is available only to Chrome Canary users accessing websites hosted by Cloudflare.

It was estimated that the experiment started mid-2019.[^o6] It was considered a step in a general program at [Cloudflare](https://en.wikipedia.org/wiki/Cloudflare) to transition to [post-quantum safe](wikipedia://en/26605226) cryptographic primitives.[^o7]

Support for CECPQ2 was removed from [BoringSSL](https://en.wikipedia.org/wiki/BoringSSL) in April 2023.
