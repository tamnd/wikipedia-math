# PBKDF2

::: {#o1 .subject cue=lead name="PBKDF2"}

In [cryptography](wikipedia://en/18934432), **PBKDF1** and **PBKDF2** (**Password-Based Key Derivation Function 1** and **2**) are [key derivation functions](wikipedia://en/449781) with a sliding computational cost, used to reduce vulnerability to [brute-force attacks](wikipedia://en/53784).[^o5]

:::

PBKDF2 is part of [RSA Laboratories](https://en.wikipedia.org/wiki/RSA_Laboratories)' [Public-Key Cryptography Standards](https://en.wikipedia.org/wiki/Public-Key_Cryptography_Standards) (PKCS) series, specifically PKCS #5 v2.0, also published as [Internet Engineering Task Force](https://en.wikipedia.org/wiki/Internet_Engineering_Task_Force)'s RFC 2898. It supersedes PBKDF1, which could only produce derived keys up to 160 bits long.[^o2] RFC 8018 (PKCS #5 v2.1), published in 2017, recommends PBKDF2 for password hashing.[^o3]

## Purpose and operation {#Purpose_and_operation}

PBKDF2 applies a [pseudorandom function](https://en.wikipedia.org/wiki/Pseudorandom_function), such as [hash-based message authentication code](https://en.wikipedia.org/wiki/Hash-based_message_authentication_code) (HMAC), to the input [password](wikipedia://en/24304) or [passphrase](https://en.wikipedia.org/wiki/Passphrase) along with a [salt](wikipedia://en/701756) value and repeats the process many times to produce a *derived key*, which can then be used as a [cryptographic key](wikipedia://en/53039) in subsequent operations. The added computational work makes [password cracking](wikipedia://en/477981) much more difficult, and is known as [key stretching](wikipedia://en/4266286).

While the recommended minimum number of iterations was 1,000 when the standard was written in the year 2000, the parameter is intended to be increased over time as CPU speeds increase. A [Kerberos](wikipedia://en/16947) standard in 2005 recommended 4,096 iterations;[^o5] [Apple](https://en.wikipedia.org/wiki/Apple_Inc.) reportedly used 2,000 for [iOS 3](https://en.wikipedia.org/wiki/IOS_3), and 10,000 for [iOS 4](https://en.wikipedia.org/wiki/IOS_4);[^o6] while [LastPass](https://en.wikipedia.org/wiki/LastPass) in 2011 used 5,000 iterations for [JavaScript](https://en.wikipedia.org/wiki/JavaScript) clients and 100,000 iterations for server-side hashing.[^o7] In 2023, [OWASP](https://en.wikipedia.org/wiki/OWASP) recommended to use 600,000 iterations for PBKDF2-HMAC-SHA256 and 220,000 for PBKDF2-HMAC-SHA512.[^o8]

*Image: Pbkdf2 nist.png.* Algorithmic representation of the iterative process of PBKDF2.

Having a salt added to the password reduces the ability to use precomputed hashes ([rainbow tables](https://en.wikipedia.org/wiki/Rainbow_tables)) for attacks, and means that multiple passwords have to be tested individually, not all at once. The public key cryptography standard recommends a salt length of at least 64 bits.[^o9] The US [National Institute of Standards and Technology](https://en.wikipedia.org/wiki/National_Institute_of_Standards_and_Technology) recommends a salt length of at least 128 bits.[^o10]

## Key derivation process {#Key_derivation_process}

PBKDF2 has five input parameters:[^o12]

$$\operatorname{DK} = \operatorname{PBKDF}2(\operatorname{PRF}, Password, Salt, c, dkLen)$$

where:

- $\operatorname{PRF}$ is a pseudorandom function of two parameters with output length $hLen$ (e.g., a keyed HMAC)
- $Password$ is the master password from which a derived key is generated
- $Salt$ is a sequence of bits, known as a [cryptographic salt](wikipedia://en/701756)
- $c$ is the number of iterations desired
- $dkLen$ is the desired bit-length of the derived key
- $DK$ is the generated derived key

Each $hLen$-bit block $T_{i}$ of derived key $DK$, is computed as follows (with $+$ marking string concatenation):

$$DK = T_{1} + T_{2} + \cdots + T_{dkLen/hLen}$$

$$T_{i} = F(Password, Salt, c, i)$$

The function $F$ is the [xor](https://en.wikipedia.org/wiki/Xor) ($\hat{}$) of *c* iterations of chained PRFs. The first iteration of PRF uses *Password* as the PRF key and *Salt* concatenated with $i$ encoded as a big-endian 32-bit integer as the input. (Note that *i* is a 1-based index.) Subsequent iterations of PRF use *Password* as the PRF key and the output of the previous PRF computation as the input:

$$F(Password, Salt, c, i) = U_{1} \hat{} U_{2} \hat{} \cdots \hat{} U_{c}$$

where:

$$U_{1} = \operatorname{PRF}(Password, Salt + \operatorname{INT}\_32\_\operatorname{BE}(i))$$

$$U_{2} = \operatorname{PRF}(Password, U_{1})$$

$$\vdots$$

$$U_{c} = \operatorname{PRF}(Password, U_{c-1})$$

For example, [WPA2](https://en.wikipedia.org/wiki/WPA2) uses:

$$\operatorname{DK} = \operatorname{PBKDF}2(\operatorname{HMAC}-\operatorname{SHA}1, passphrase, ssid, 4096, 256)$$

PBKDF1 had a simpler process: the initial *U* (called *T* in this version) is created by $\operatorname{PRF}(Password + Salt)$, and the following ones are simply $\operatorname{PRF}(U_{\operatorname{previous}})$. The key is extracted as the first *dkLen* bits of the final hash, which is why there is a size limit.[^o12]

## HMAC collisions {#HMAC_collisions}

PBKDF2 has an interesting property when using HMAC as its pseudo-random function. It is possible to trivially construct any number of different password pairs with collisions within each pair.[^o14] If a supplied password is longer than the block size of the underlying HMAC hash function, the password is first pre-hashed into a digest, and that digest is instead used as the password. For example, the following password is too long:

- **Password:** `{{not a typo|plnlrtfpijpuhqylxbgqiiyipieyxvfsavzgxbbcfusqkozwpngsyejqlmjsytrmd}}`

therefore, when using HMAC-SHA1, it is pre-hashed using SHA-1 into:

- **SHA1** (hex): `65426b585154667542717027635463617226672a`

Which can be represented in ASCII as:

- **SHA1** (ASCII): `eBkXQTfuBqp'cTcar&g*`

This means regardless of the salt or iterations, PBKDF2-HMAC-SHA1 will generate the same key bytes for the passwords:

- "plnlrtfpijpuhqylxbgqiiyipieyxvfsavzgxbbcfusqkozwpngsyejqlmjsytrmd"
- "eBkXQTfuBqp'cTcar&g\*"

For example, using:

- **PRF**: HMAC-SHA1
- **Salt:** A009C1A485912C6AE630D3E744240B04
- **Iterations:** 1,000
- **Derived key length:** 16 bytes

The following two function calls:

```python
PBKDF2-HMAC-SHA1("plnlrtfpijpuhqylxbgqiiyipieyxvfsavzgxbbcfusqkozwpngsyejqlmjsytrmd", ...)
PBKDF2-HMAC-SHA1("eBkXQTfuBqp'cTcar&g*", ...) 
```

will generate the same derived key bytes (`17EB4014C8C461C300E9B61518B9A18B`). These derived key collisions do not represent a security vulnerability – as one still must know the original password in order to generate the *hash* of the password.[^o15]

## Alternatives to PBKDF2 {#Alternatives_to_PBKDF2}

One weakness of PBKDF2 is that while its number of iterations can be adjusted to make it take an arbitrarily large amount of computing time, it can be implemented with a small circuit and very little RAM, which makes brute-force attacks using [application-specific integrated circuits](https://en.wikipedia.org/wiki/Application-specific_integrated_circuit) or [graphics processing units](https://en.wikipedia.org/wiki/Graphics_processing_unit) relatively cheap.[^o17] The [bcrypt](wikipedia://en/21564294) password hashing function requires a larger amount of RAM (but still not tunable separately, i.e. fixed for a given amount of CPU time) and is significantly stronger against such attacks,[^o18] while the more modern [scrypt](https://en.wikipedia.org/wiki/Scrypt) key derivation function can use arbitrarily large amounts of memory and is therefore more resistant to ASIC and GPU attacks.[^o17]

In 2013, the [Password Hashing Competition](https://en.wikipedia.org/wiki/Password_Hashing_Competition) (PHC) was held to develop a more resistant approach. On 20 July 2015 [Argon2](wikipedia://en/48963187) was selected as the final PHC winner, with special recognition given to four other password hashing schemes: Catena, [Lyra2](wikipedia://en/49892678), [yescrypt](wikipedia://en/55569844) and Makwa.[^o19] Another alternative is [Balloon hashing](wikipedia://en/61677905), which is recommended in [NIST password guidelines](https://en.wikipedia.org/wiki/Password_policy#NIST_guidelines).[^o20]

To limit a [brute-force attack](wikipedia://en/53784), it is possible to make each password attempt require an online interaction, without harming the confidentiality of the password. This can be done using an [oblivious pseudorandom function](wikipedia://en/75933806) to perform [password hardening](wikipedia://en/75933806#Password-based_key_derivation).[^o21] This can be done as alternative to, or as an additional step in, a PBKDF.
