# OpenSSL

::: {#o4 .subject cue=lead name="OpenSSL"}

**OpenSSL** is a software [library](https://en.wikipedia.org/wiki/Library_%28computing%29) for applications that provide secure communications over [computer networks](https://en.wikipedia.org/wiki/Computer_network) against eavesdropping, and identify the party at the other end. It is widely used by [Internet](https://en.wikipedia.org/wiki/Internet) [servers](https://en.wikipedia.org/wiki/Server_%28computing%29), including the majority of [HTTPS](wikipedia://en/13586) [websites](https://en.wikipedia.org/wiki/Website).

:::

OpenSSL contains an [open-source](https://en.wikipedia.org/wiki/Open-source_software) implementation of the [SSL and TLS](wikipedia://en/187813) protocols. The core [library](https://en.wikipedia.org/wiki/Library_%28computer_science%29), written in the [C programming language](https://en.wikipedia.org/wiki/C_%28programming_language%29), implements basic [cryptographic](wikipedia://en/18934432) functions and provides various utility functions. Wrappers allowing the use of the OpenSSL library in a variety of computer languages are available.

The OpenSSL Software Foundation (OSF) represents the OpenSSL project in most legal capacities including contributor license agreements, managing donations, and so on. OpenSSL Software Services (OSS) also represents the OpenSSL project for support contracts.

OpenSSL is available for most [Unix-like](https://en.wikipedia.org/wiki/Unix-like) [operating systems](https://en.wikipedia.org/wiki/Operating_system) (including [Linux](https://en.wikipedia.org/wiki/Linux), [macOS](https://en.wikipedia.org/wiki/MacOS), and [BSD](https://en.wikipedia.org/wiki/Berkeley_Software_Distribution)), [Microsoft Windows](https://en.wikipedia.org/wiki/Microsoft_Windows) and [OpenVMS](https://en.wikipedia.org/wiki/OpenVMS).

## Project history {#Project_history}

The OpenSSL project was founded in 1998 to provide a free set of encryption tools for the code used on the Internet. It is based on a fork of [SSLeay](wikipedia://en/3881085) by Eric Andrew Young and Tim Hudson, which unofficially ended development on December 17, 1998, when Young and Hudson both went to work for [RSA Security](wikipedia://en/301240). The initial founding members were Mark Cox, Ralf Engelschall, Stephen Henson, [Ben Laurie](https://en.wikipedia.org/wiki/Ben_Laurie), and Paul Sutton.[^o6]

In 2018 OpenSSL [version numbering](https://en.wikipedia.org/wiki/Version_numbering) skipped from 1.1.1 to 3.0.0, omitting 2 as a major version number to avoid a conflict with one of OpenSSL's modules.[^o27] Version 3.0.0 was the first to use the [Apache License](https://en.wikipedia.org/wiki/Apache_License).

,[^o7] the OpenSSL management committee consisted of seven people[^o8] and there are seventeen developers[^o9] with commit access (many of whom are also part of the OpenSSL management committee). There were only two full-time employees (fellows) and the remainder were volunteers.

By 2024, there were fourteen employees.

The project had a total income of US\$5.5 million in 2024.[^o10] Development of TLS 1.3 was sponsored by [Akamai](https://en.wikipedia.org/wiki/Akamai_Technologies).[^o11]

## FIPS 140 validation {#FIPS_140_validation}

[FIPS 140](wikipedia://en/1539324) is a U.S. Federal program for the testing and certification of cryptographic modules. An early FIPS 140-1 certificate for OpenSSL's FOM 1.0 was revoked in July 2006 "when questions were raised about the validated module's interaction with outside software." The module was re-certified in February 2007 before giving way to FIPS 140-2.[^o44] OpenSSL 1.0.2 supported the use of the OpenSSL FIPS Object Module (FOM), which was built to deliver FIPS approved algorithms in a FIPS 140-2 validated environment.[^o45][^o46] OpenSSL controversially decided to categorize the 1.0.2 architecture as 'end of life' or 'EOL', effective December 31, 2019, despite objections that it was the only version of OpenSSL that was currently available with support for FIPS mode.[^o47] As a result of the EOL, many users were unable to properly deploy the FOM 2.0 and fell out of compliance because they did not secure extended support for the 1.0.2 architecture, although the FOM itself remained validated for eight months further.

The FIPS Object Module 2.0 remained FIPS 140-2 validated in several formats until September 1, 2020, when NIST deprecated the usage of FIPS 186-2 for [Digital Signature Standard](https://en.wikipedia.org/wiki/Digital_Signature_Standard) and designated all non-compliant modules as 'Historical'. This designation includes a caution to federal agencies that they should not include the module in any new procurements. All three of the OpenSSL validations were included in the deprecation – the OpenSSL FIPS Object Module (certificate #1747),[^o48] OpenSSL FIPS Object Module SE (certificate #2398),[^o49] and OpenSSL FIPS Object Module RE (certificate #2473).[^o50] Many 'private label' OpenSSL-based validations and clones created by consultants were also moved to the Historical List, although some FIPS validated modules with replacement compatibility avoided the deprecation, such as BoringCrypto from Google[^o51] and CryptoComply from SafeLogic.[^o52]

The OpenSSL Management Committee announced a change in the versioning scheme.

Due to this change, the major number of the next major version would have been doubled, since the OpenSSL FIPS module already occupied this number. Therefore, the decision was made to skip the OpenSSL 2.0 version number and continue with OpenSSL 3.0 .

OpenSSL 3.0 restored FIPS mode and underwent FIPS 140-2 testing, but with significant delays: The effort was first kicked off in 2016 with support from SafeLogic[^o53][^o54][^o55] and further support from Oracle in 2017,[^o56][^o57] but the process has been challenging.[^o58]

On October 20, 2020, the OpenSSL FIPS Provider 3.0 was added to the CMVP Implementation Under Test List, which reflected an official engagement with a testing lab to proceed with a FIPS 140-2 validation. This resulted in a slew of certifications in the following months.[^o59]

## Licensing {#Licensing}

OpenSSL was dual-licensed under the OpenSSL License and the SSLeay License, which means that the terms of either licenses can be used.[^o62] The OpenSSL License is [Apache License](https://en.wikipedia.org/wiki/Apache_License) 1.0 and SSLeay License bears some similarity to a 4-clause [BSD License](https://en.wikipedia.org/wiki/BSD_License). As the OpenSSL License was [Apache License](https://en.wikipedia.org/wiki/Apache_License) 1.0, but not Apache License 2.0, it requires the phrase "this product includes software developed by the OpenSSL Project for use in the OpenSSL Toolkit" to appear in advertising material and any redistributions (Sections 3 and 6 of the OpenSSL License). Due to this restriction, the OpenSSL License and the Apache License 1.0 are incompatible with the [GNU GPL](https://en.wikipedia.org/wiki/GNU_General_Public_License).[^o63] Some GPL developers have added an *OpenSSL exception* to their licenses that specifically permits using OpenSSL with their system. GNU [Wget](https://en.wikipedia.org/wiki/Wget) and [climm](https://en.wikipedia.org/wiki/Climm) both use such exceptions.[^o64][^o65] Some packages (like [Deluge](https://en.wikipedia.org/wiki/Deluge_%28software%29)) explicitly modify the GPL license by adding an extra section at the beginning of the license documenting the exception.[^o66] Other packages use the [LGPL](https://en.wikipedia.org/wiki/GNU_Lesser_General_Public_License)-licensed [GnuTLS](wikipedia://en/949758), [BSD](https://en.wikipedia.org/wiki/BSD_licenses)-licensed [Botan](https://en.wikipedia.org/wiki/Botan_%28programming_library%29), or [MPL](https://en.wikipedia.org/wiki/Mozilla_Public_License)-licensed [NSS](wikipedia://en/5137674), which perform the same task.

OpenSSL announced in August 2015 that it would require most contributors to sign a [Contributor License Agreement](https://en.wikipedia.org/wiki/Contributor_License_Agreement) (CLA), and that OpenSSL would eventually be [relicensed](https://en.wikipedia.org/wiki/Software_relicensing) under the terms of [Apache License&nbsp;2.0](https://en.wikipedia.org/wiki/Apache_License&nbsp;2.0).[^o67] This process commenced in March 2017,[^o68] and was complete in 2018.[^o69]

On 7 September 2021, OpenSSL 3.0.0 was released under the Apache License 2.0.[^o70]

## Notable vulnerabilities {#Notable_vulnerabilities}

### Denial of service (DOS): ASN.1 parsing {#Denial_of_service_(DOS):_ASN.1_parsing}

OpenSSL 0.9.6k has a bug where certain [ASN.1](https://en.wikipedia.org/wiki/ASN.1) sequences triggered a large number of recursions on Windows machines, discovered on November 4, 2003. Windows could not handle large recursions correctly, so OpenSSL would crash as a result. Being able to send arbitrary large numbers of ASN.1 sequences would cause OpenSSL to crash as a result.

### OCSP stapling vulnerability {#OCSP_stapling_vulnerability}

When creating a handshake, the client could send an incorrectly formatted ClientHello message, leading to OpenSSL parsing more than the end of the message. Assigned the identifier 2011-0014 by the CVE project, this affected all OpenSSL versions 0.9.8h to 0.9.8q and OpenSSL 1.0.0 to 1.0.0c. Since the parsing could lead to a read on an incorrect memory address, it was possible for the attacker to cause a [DoS](https://en.wikipedia.org/wiki/Denial-of-service_attack). It was also possible that some applications expose the contents of parsed [OCSP](https://en.wikipedia.org/wiki/OCSP) extensions, leading to an attacker being able to read the contents of memory that came after the ClientHello.[^o74]

### ASN.1 BIO vulnerability {#ASN.1_BIO_vulnerability}

When using Basic Input/Output (BIO)[^o76] or FILE based functions to read untrusted [DER](https://en.wikipedia.org/wiki/Distinguished_Encoding_Rules) format data, OpenSSL is vulnerable. This vulnerability was discovered on April 19, 2012, and was assigned the CVE identifier 2012-2110. While not directly affecting the SSL/TLS code of OpenSSL, any application that was using ASN.1 functions (particularly d2i\_X509 and d2i\_PKCS12) were also not affected.[^o77]

### SSL, TLS and DTLS plaintext recovery attack {#SSL,_TLS_and_DTLS_plaintext_recovery_attack}

In handling CBC cipher-suites in SSL, TLS, and DTLS, OpenSSL was found vulnerable to a timing attack during the MAC processing. Nadhem Alfardan and Kenny Paterson discovered the problem, and published their findings[^o79] on February 5, 2013. The vulnerability was assigned the CVE identifier 2013-0169.

::: {#o81 .pointer-item cue=pointer name="CVE-2008-0166"}

### Predictable private keys (Debian-specific) {#Predictable_private_keys_(Debian-specific)}

OpenSSL's pseudo-[random number generator](https://en.wikipedia.org/wiki/Random_number_generator) acquires entropy using complex programming methods. To keep the [Valgrind](https://en.wikipedia.org/wiki/Valgrind) analysis tool from issuing associated warnings, a maintainer of the [Debian](https://en.wikipedia.org/wiki/Debian) distribution applied a [patch](https://en.wikipedia.org/wiki/Patch_%28computing%29) to Debian's variant of the OpenSSL suite, which inadvertently broke its random number generator by limiting the overall number of private keys it could generate to 32,768.[^o82][^o83] The broken version was included in the Debian release of September 17, 2006 (version 0.9.8c-1), also compromising other Debian-based distributions, for example [Ubuntu](https://en.wikipedia.org/wiki/Ubuntu_%28operating_system%29). Ready-to-use [exploits](https://en.wikipedia.org/wiki/Exploit_%28computer_security%29) are easily available.[^o84]

The error was reported by Debian on May 13, 2008. On the Debian 4.0 distribution (etch), these problems were fixed in version 0.9.8c-4etch3, while fixes for the Debian 5.0 distribution (lenny) were provided in version 0.9.8g-9.[^o85]

:::

### Heartbleed {#Heartbleed}

*Image: Heartbleed.svg.* A logo representing the Heartbleed bug

OpenSSL versions 1.0.1 through 1.0.1f have a severe memory handling [bug](https://en.wikipedia.org/wiki/Software_bug) in their implementation of the [TLS](wikipedia://en/187813) Heartbeat Extension that could be used to reveal up to 64 [KB](https://en.wikipedia.org/wiki/Kibibyte) of the application's memory with every [heartbeat](wikipedia://en/38838486)[^o87][^o88] (2014-0160). By reading the memory of the web server, attackers could access sensitive data, including the server's [private key](wikipedia://en/24222).[^o89] This could allow attackers to decode earlier [eavesdropped](https://en.wikipedia.org/wiki/Eavesdropping) communications if the encryption protocol used does not ensure [perfect forward secrecy](https://en.wikipedia.org/wiki/Perfect_forward_secrecy). Knowledge of the private key could also allow an attacker to mount a [man-in-the-middle attack](wikipedia://en/144676) against any future communications. The vulnerability might also reveal unencrypted parts of other users' sensitive requests and responses, including [session cookies](https://en.wikipedia.org/wiki/Session_cookie) and passwords, which might allow attackers to [hijack the identity](https://en.wikipedia.org/wiki/Session_hijacking) of another user of the service.[^o90]

At its disclosure on April 7, 2014, around 17% or half a million of the Internet's secure [web servers](https://en.wikipedia.org/wiki/Web_servers) certified by [trusted authorities](wikipedia://en/296370) were believed to have been vulnerable to the attack.[^o91] However, Heartbleed can affect both the server and client.

::: {#o93 .pointer-item cue=pointer name="CVE-2014-0224"}

### CCS injection vulnerability {#CCS_injection_vulnerability}

The CCS Injection Vulnerability (2014-0224) is a security bypass vulnerability that results from a weakness in OpenSSL methods used for keying material.[^o94]

This vulnerability can be exploited through the use of a man-in-the-middle attack,[^o95] where an attacker may be able to decrypt and modify traffic in transit. A remote unauthenticated attacker could exploit this vulnerability by using a specially crafted handshake to force the use of weak keying material. Successful exploitation could lead to a security bypass condition where an attacker could gain access to potentially sensitive information. The attack can only be performed between a vulnerable client *and* server.

OpenSSL clients are vulnerable in all versions of OpenSSL before the versions 0.9.8za, 1.0.0m and 1.0.1h. Servers are only known to be vulnerable in OpenSSL 1.0.1 and 1.0.2-beta1. Users of OpenSSL servers earlier than 1.0.1 are advised to upgrade as a precaution.[^o96]

:::

### ClientHello sigalgs DoS {#ClientHello_sigalgs_DoS}

This vulnerability (2015-0291) allows anyone to take a certificate, read its contents and modify it accurately to abuse the vulnerability causing a certificate to crash a client or server. If a client connects to an OpenSSL 1.0.2 server and renegotiates with an invalid signature algorithms extension, a null-pointer dereference occurs. This can cause a DoS attack against the server.

A Stanford Security researcher, David Ramos, had a private exploit and presented it to the OpenSSL team, which then patched the issue.

OpenSSL classified the bug as a high-severity issue, noting version 1.0.2 was found vulnerable.[^o98]

### Key recovery attack on Diffie–Hellman small subgroups {#Key_recovery_attack_on_Diffie–Hellman_small_subgroups}

This vulnerability (2016-0701) allows, when some particular circumstances are met, to recover the OpenSSL server's private Diffie–Hellman key. An Adobe System Security researcher, Antonio Sanso, privately reported the vulnerability.

OpenSSL classified the bug as a high-severity issue, noting only version 1.0.2 was found vulnerable.[^o100]

## Forks {#Forks}

### Agglomerated SSL {#Agglomerated_SSL}

In 2009, after frustrations with the original OpenSSL API, Marco Peereboom, an OpenBSD developer at the time, forked the original API by creating Agglomerated SSL (assl),[^o103] which reuses OpenSSL API under the hood, but provides a much simpler external interface.[^o104] It has since been deprecated in light of the [LibreSSL](wikipedia://en/42552765) fork circa 2015.

### LibreSSL {#LibreSSL}

In April 2014 in the wake of [Heartbleed](https://en.wikipedia.org/wiki/Heartbleed), members of the [OpenBSD](https://en.wikipedia.org/wiki/OpenBSD) project [forked](https://en.wikipedia.org/wiki/Fork_%28software_development%29) OpenSSL starting with the 1.0.1g branch, to create a project named [LibreSSL](wikipedia://en/42552765).[^o106] In the first week of pruning the OpenSSL's [codebase](https://en.wikipedia.org/wiki/Codebase), more than 90,000 lines of C code had been removed from the fork.[^o107]

::: {#o109 .pointer-item cue=pointer name="BoringSSL"}

### BoringSSL {#BoringSSL}

In June 2014, [Google](https://en.wikipedia.org/wiki/Google) announced its own fork of OpenSSL dubbed BoringSSL.[^o110] Google plans to co-operate with OpenSSL and LibreSSL developers.[^o111][^o112][^o113] Google has since developed a new library, Tink, based on BoringSSL.[^o114] [Chromium](https://en.wikipedia.org/wiki/Chromium_%28web_browser%29) based browsers, including [Microsoft Edge](https://en.wikipedia.org/wiki/Microsoft_Edge), have implemented BoringSSL.

:::

### AWS-LC {#AWS-LC}

In September 2020, it was released as a general-purpose cryptographic library maintained by the [Amazon Web Services](https://en.wikipedia.org/wiki/Amazon_Web_Services) Cryptography team to be used in the AWS cloud computing platform. It іs based on code from the OpenSSL and BoringSSL projects.[^o116]

### QuicTLS {#QuicTLS}

QuicTLS is a collaborative fork between [Akamai](https://en.wikipedia.org/wiki/Akamai) and [Microsoft](https://en.wikipedia.org/wiki/Microsoft), based on OpenSSL 3.3 release. Some features and fixes are cherry-picked from the current OpenSSL repo.[^o118]

## Criticisms {#Criticisms}

### Backwards compatibility {#Backwards_compatibility}

Among developers communities, OpenSSL is often cited for introducing API compatibility breakage with each new major version,[^o121][^o122][^o123][^o124] which requires software adaptations that tend to delay new version adoptions.[^o125] This, combined with the fact that previous releases are generally maintained for no more than two years after a new major one is released[^o25] tends to force some vendors to anticipate software migrations very early while still having little time left[^o126] to update to a new release, sometimes at the risk of losing some compatibility with existing software[^o127][^o128] or risking regressions.[^o129][^o130]

### Delay between releases {#Delay_between_releases}

While [long-term support](https://en.wikipedia.org/wiki/Long-term_support) (LTS) releases are maintained for 5 years,[^o16] accumulated delays in release time frames tend to force operating system vendors to stay on the last supported release longer, leaving less margin when the new version is available. For example, OpenSSL 3.0 was initially expected for Q4 2019[^o47] and was finally issued 21 months later[^o25] without extending the expected end of support for previously supported version 1.1.1, and this despite the significant changes that required adaptations to existing software.

### Significant performance regressions {#Significant_performance_regressions}

The reduced support delay of version 1.1.1 mentioned above causes further concerns to users whose workloads are sensitive to performance. Some time after general availability of 3.0, some users started to report serious performance regressions affecting this version in multi-threaded environments, many citing the inefficient use of locks in frequent low-level operations, citing slowdowns from 80 to 400 times.[^o133][^o134][^o135][^o136][^o137][^o138][^o139][^o140] The OpenSSL team has created a meta-issue to try to centralize reports of such massive performance regressions.[^o141] About half of these reporters indicate the impossibility for them to upgrade to 3.0 from earlier versions, adding to the trouble caused by the limited support time left on previous version 1.1.1.

### Consideration for users' requirements {#Consideration_for_users'_requirements}

While the [QUIC](https://en.wikipedia.org/wiki/QUIC) transport layer was being worked on to support the third version of the [HTTP](https://en.wikipedia.org/wiki/HTTP) protocol, it was proposed to use TLS to provide security,[^o143] and identified that some adaptations to TLS libraries would be needed. Such modifications were brought to BoringSSL[^o144] which was the library being primarily used by QUIC developers by then, and later ported to other libraries.[^o145] A port of this work was quickly proposed to OpenSSL.[^o146] While some discussion started the same day, it quickly stalled and was first blocked on license considerations,[^o146] then kept on hold once these concerns were cleared. Finally 10 months later the OpenSSL Management Committee announced on a blog post[^o147] that this patch set would not be adopted for 3.0 on the fear that the API would change over time. Finally more than one year after planned release of 3.0 which was still not coming, a team of volunteers from [Akamai](https://en.wikipedia.org/wiki/Akamai) and [Microsoft](https://en.wikipedia.org/wiki/Microsoft) decided to fork the project as QuicTLS[^o148] and support these patches on top of the OpenSSL code in order to unblock QUIC development. This action was generally welcomed by the community. Finally after OpenSSL 3.0 was finally released, the QUIC patch set was reconsidered and decided against,[^o149] causing tens to hundreds of reactions of disappointment among the community.[^o146] The pull request was closed, while users felt the need to publicly express their disappointment,[^o150] or beg operating system vendors to support the alternative QuicTLS fork,[^o151][^o152] or seek for alternative solutions.[^o153] Finally Rich Salz, co-founder of the QuicTLS fork, announced[^o153] his interest in seeing an Apache project forked from QuicTLS. As of 25 February 2023 there is still no QUIC-compatible long-term supported TLS library available by default in operating systems without requiring end-users to rebuild it themselves from sources.
