# CRAM-MD5

::: {#o1 .subject cue=lead name="CRAM-MD5"}

In [cryptography](wikipedia://en/18934432), **CRAM-MD5** is a [challenge–response authentication](wikipedia://en/412627) mechanism (CRAM) based on the [HMAC-MD5](https://en.wikipedia.org/wiki/HMAC-MD5) algorithm. As one of the mechanisms supported by the [Simple Authentication and Security Layer](https://en.wikipedia.org/wiki/Simple_Authentication_and_Security_Layer) (SASL), it is often used in email software as part of [SMTP Authentication](https://en.wikipedia.org/wiki/SMTP_Authentication) and for the authentication of [POP](https://en.wikipedia.org/wiki/Post_Office_Protocol) and [IMAP](https://en.wikipedia.org/wiki/Internet_Message_Access_Protocol) users, as well as in applications implementing [LDAP](https://en.wikipedia.org/wiki/LDAP), [XMPP](https://en.wikipedia.org/wiki/XMPP), [BEEP](https://en.wikipedia.org/wiki/BEEP), and other protocols.

:::

When such software requires authentication over unencrypted connections, CRAM-MD5 is preferred over mechanisms that transmit passwords "in the clear," such as *`LOGIN`* and *`PLAIN`*. However, it can't prevent derivation of a password through a [brute-force attack](wikipedia://en/53784), so it is less effective than alternative mechanisms that avoid passwords or that use connections encrypted with [Transport Layer Security](wikipedia://en/187813) (TLS).

## Protocol {#Protocol}

The CRAM-MD5 protocol involves a single challenge and response cycle, and is initiated by the server:

1. Challenge: The server sends a [base64](https://en.wikipedia.org/wiki/Base64)-encoded string to the client. Before encoding, it could be any random string, but the standard that currently defines CRAM-MD5 says that it is in the format of a *`[[Message-ID]]`* email header value (including [angle brackets](https://en.wikipedia.org/wiki/Angle_bracket)) and includes an arbitrary string of random digits, a [timestamp](https://en.wikipedia.org/wiki/Timestamp), and the server's [fully qualified domain name](https://en.wikipedia.org/wiki/Fully_qualified_domain_name).
1. Response: The client responds with a string created as follows.
   1. The challenge is base64-decoded.
   1. The decoded challenge is hashed using [HMAC-MD5](wikipedia://en/17112), with a [shared secret](wikipedia://en/7111246) (typically, the user's password, or a hash thereof) as the secret key.
   1. The hashed challenge is converted to a string of lowercase hex digits.
   1. The [username](https://en.wikipedia.org/wiki/Username) and a space character are prepended to the hex digits.
   1. The concatenation is then base64-encoded and sent to the server
1. Comparison: The server uses the same method to compute the expected response. If the given response and the expected response match, then authentication was successful.

## Strengths {#Strengths}

The one-way hash and the fresh random challenge provide three types of security:

- Others cannot duplicate the hash without knowing the password. This provides authentication.
- Others cannot replay the hash—it is dependent on the unpredictable challenge. This is variously called freshness or [replay prevention](wikipedia://en/614094).
- Observers do not learn the password; this is called secrecy.

## Weaknesses {#Weaknesses}

- No [mutual authentication](wikipedia://en/3064285): the client does not verify the server. However, SASL authentication is usually done over a [TLS](https://en.wikipedia.org/wiki/Transport_layer_security) connection, which verifies the server's identity.
- Weak password storage: some implementations require access to the users' plain text passwords, while others (e.g. [Dovecot](https://en.wikipedia.org/wiki/Dovecot_%28software%29)) use the intermediate step of the HMAC process to store the [MD5](wikipedia://en/18826)-hash of the password (strictly speaking of HMAC's internal variables i\_key\_pad and o\_key\_pad).[^o5][^o6] Such implementations leverage that for computing md5(something\_with\_64\_bytes || something\_else), only md5\_internal(something\_with\_64\_bytes) and something\_else are needed to know (because of [Merkle–Damgård](wikipedia://en/4076217) usage in MD5; md5\_internal is md5 without the final block). As i\_key\_pad and o\_key\_pad are at the start of the inner and outer hash of HMAC, and have a length of 64 bytes, this fact can be used.
- Threat of reversibility: an offline [dictionary attack](wikipedia://en/53785) to recover the password is feasible after capturing a successful CRAM-MD5 protocol exchange (e.g., using [Cain & Abel](https://en.wikipedia.org/wiki/Cain_and_Abel_%28software%29)). This threat is unavoidable in any password hashing scheme, but more modern algorithms use [key stretching](wikipedia://en/4266286) for increasing the cost of an attack by a factor of one thousand or more. Conversely, CRAM-MD5 digests can be calculated using very few computational resources on dedicated hardware, or even just standard [CPUs](https://en.wikipedia.org/wiki/CPU).
- Proxy-ability: Unlike a [password-authenticated key agreement](https://en.wikipedia.org/wiki/Password-authenticated_key_agreement) (PAKE) scheme, CRAM-MD5 does not establish a secret shared between the two endpoints but unknown to an eavesdropper. An active [man in the middle](wikipedia://en/144676) can therefore open a connection to the server, get a challenge, offer that challenge to the client, receive the client's response, and forward that response to the server. It can now drop the client's further messages while impersonating the client to the server.

## Standards {#Standards}

CRAM-MD5 is defined by the [IETF standards-track document](https://en.wikipedia.org/wiki/Request_for_Comments) RFC 2195, which supersedes RFC 2095, from earlier in 1997. These [*de facto* standards](https://en.wikipedia.org/wiki/De_facto_standard) define CRAM-MD5 as an authentication method for the email mailbox-management protocols [POP](https://en.wikipedia.org/wiki/Post_Office_Protocol) and [IMAP](https://en.wikipedia.org/wiki/Internet_Message_Access_Protocol).

CRAM-MD5 is one of the authentication methods supported by [Simple Authentication and Security Layer](https://en.wikipedia.org/wiki/Simple_Authentication_and_Security_Layer) (SASL), defined in 2006 by RFC 4422, which supersedes the 1997 standard RFC 2222.

The [Internet Assigned Numbers Authority](https://en.wikipedia.org/wiki/Internet_Assigned_Numbers_Authority) (IANA) maintains a registry of SASL mechanisms,[^o8] including CRAM-MD5, for limited use.

CRAM-MD5 is required for [On-Demand Mail Relay](https://en.wikipedia.org/wiki/On-Demand_Mail_Relay) (ODMR), defined in RFC 2645.

## Obsolete {#Obsolete}

It was recommended to deprecate the standard in 20 November 2008. As an alternative it recommends e.g. [SCRAM](https://en.wikipedia.org/wiki/Salted_Challenge_Response_Authentication_Mechanism) or [SASL](https://en.wikipedia.org/wiki/Simple_Authentication_and_Security_Layer) Plain protected by [TLS](wikipedia://en/187813) instead.[^o10]
