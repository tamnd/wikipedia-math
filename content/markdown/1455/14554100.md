# Substructural type system

::: {#o1 .subject cue=lead name="Substructural type system"}

**Substructural type systems** are a family of [type systems](wikipedia://en/199701) analogous to [substructural logics](wikipedia://en/412909) where one or more of the [structural rules](wikipedia://en/697666) are absent or only allowed under controlled circumstances. Such systems can constrain access to [system resources](https://en.wikipedia.org/wiki/System_resource) such as [files](https://en.wikipedia.org/wiki/Computer_file), [locks](https://en.wikipedia.org/wiki/Lock_%28computer_science%29), and [memory](https://en.wikipedia.org/wiki/Computer_memory) by keeping track of changes of state and prohibiting invalid states.[^o2]p. 4

:::

## Different substructural type systems {#Different_substructural_type_systems}

Several type systems have emerged by discarding some of the [structural rules](wikipedia://en/697666) of exchange, weakening, and contraction:

::: {#o4 .table cue=table}

| Type systems | Exchange | Weakening | Contraction | Use |
|---|---|---|---|---|
| \\| Ordered |  |  |  | Exactly once, in the order it was introduced |
| \\|Linear | Allowed |  |  | Exactly once |
| \\|Affine | Allowed | Allowed |  | At most once |
| \\|Relevant | Allowed |  | Allowed | At least once |
| \\|Normal | Allowed | Allowed | Allowed | Arbitrarily |

:::

::: {#o6 .pointer-item cue=pointer name="Ordered type"}

### Ordered type system {#Ordered_type_system}

*Ordered types* correspond to [noncommutative logic](wikipedia://en/693282) where exchange, contraction and weakening are discarded. This can be used to model [stack-based memory allocation](https://en.wikipedia.org/wiki/Stack-based_memory_allocation) (contrast with linear types which can be used to model [heap-based memory allocation](https://en.wikipedia.org/wiki/Heap-based_memory_allocation)).[^o2]p. 30–31 Without the exchange property, an object may only be used when at the top of the modelled stack, after which it is popped off, resulting in every variable being used exactly once in the order it was introduced.

:::

::: {#o8 .pointer-item cue=pointer name="Linear type"}

### Linear type systems {#Linear_type_systems}

*Linear types* correspond to [linear logic](wikipedia://en/579675) and ensure that objects are used exactly once. This allows the system to safely [deallocate](https://en.wikipedia.org/wiki/Memory_management) an object after its use,[^o2]p. 6 or to design [software interfaces](https://en.wikipedia.org/wiki/API) that guarantee a resource cannot be used once it has been closed or transitioned to a different state.[^o9]

The [Clean programming language](https://en.wikipedia.org/wiki/Clean_%28programming_language%29) makes use of [uniqueness types](https://en.wikipedia.org/wiki/Uniqueness_type) (a variant of linear types) to help support concurrency, [input/output](https://en.wikipedia.org/wiki/Input/output), and in-place update of [arrays](https://en.wikipedia.org/wiki/Array_%28data_structure%29).[^o2]p. 43

Linear type systems allow [references](https://en.wikipedia.org/wiki/Reference_%28computer_science%29) but not [aliases](https://en.wikipedia.org/wiki/Aliasing_%28computing%29). To enforce this, a reference goes out of [scope](https://en.wikipedia.org/wiki/Scope_%28programming%29) after appearing on the right-hand side of an [assignment](https://en.wikipedia.org/wiki/Assignment_%28computer_science%29), thus ensuring that only one reference to any object exists at once. Note that passing a reference as an [argument](https://en.wikipedia.org/wiki/Parameter_%28computer_programming%29) to a [function](https://en.wikipedia.org/wiki/Function_%28computer_programming%29) is a form of assignment, as the function parameter will be assigned the value inside the function, and therefore such use of a reference also causes it to go out of scope.

The single-reference property makes linear type systems suitable as programming languages for [quantum computing](wikipedia://en/25220), as it reflects the [no-cloning theorem](wikipedia://en/22035) of quantum states. From the [category theory](wikipedia://en/5869) point of view, no-cloning is a statement that there is no [diagonal functor](wikipedia://en/4606683) which could duplicate states; similarly, from the [combinatory logic](wikipedia://en/149848) point of view, there is no K-combinator which can destroy states. From the [lambda calculus](wikipedia://en/1986011) point of view, a variable `x` can appear exactly once in a term.[^o10]

Linear type systems are the [internal language](https://en.wikipedia.org/wiki/Internal_language) of [closed symmetric monoidal categories](wikipedia://en/1396924), much in the same way that [simply typed lambda calculus](wikipedia://en/1986011) is the language of [Cartesian closed categories](https://en.wikipedia.org/wiki/Cartesian_closed_categories). More precisely, one may construct [functors](wikipedia://en/10987) between the category of linear type systems and the category of closed symmetric monoidal categories.[^o11]

:::

::: {#o13 .pointer-item cue=pointer name="Affine type"}

### Affine type systems {#Affine_type_systems}

*Affine types* are a version of linear types allowing to *discard* (i.e. *not use*) a resource, corresponding to [affine logic](wikipedia://en/693233). An affine resource *can* be used *at most* once, while a linear one *must* be used *exactly* once.

:::

::: {#o15 .pointer-item cue=pointer name="Relevant type"}

### Relevant type system {#Relevant_type_system}

*Relevant types* correspond to [relevant logic](https://en.wikipedia.org/wiki/Relevant_logic) which allows exchange and contraction, but not weakening, which translates to every variable being used at least once.

:::

## The resource interpretation {#The_resource_interpretation}

Linear logic#The resource interpretation

The nomenclature offered by substructural type systems is useful to characterize [resource management](https://en.wikipedia.org/wiki/Resource_management_%28computing%29) aspects of a language. Resource management is the aspect of language safety concerned with ensuring that each [allocated resource](https://en.wikipedia.org/wiki/System_resource) is deallocated exactly once. Thus, **the resource interpretation** is only concerned with uses that transfer ownership – *moving*, where ownership is the responsibility to free the resource.

Uses that don't transfer ownership – *borrowing* – are not in scope of this interpretation, but *lifetime semantics* further restrict these uses to be between allocation and deallocation.

::: {#o17 .table cue=table}

| Type | Disowning move | Obligatory move | Move quantification | Enforcible function call state machine |
|---|---|---|---|---|
| \\| Normal |  |  | number of times | [Topological](https://en.wikipedia.org/wiki/Topological_sort) ordering |
| \\| Affine |  |  | At most once | Ordering |
| \\| Linear |  |  | Exactly once | Ordering and completion |

:::

### Resource-affine types {#Resource-affine_types}

Under the resource interpretation, an *affine* type cannot be spent more than once.

As an example, the same variant of [Hoare's vending machine](wikipedia://en/579675#The_resource_interpretation) can be expressed in English, logic and in [Rust](https://en.wikipedia.org/wiki/Rust_%28programming_language%29):

*Vending machine*

::: {#o19 .table cue=table name="Vending machine"}

| English | Logic | Rust |
|---|---|---|
| A coin can buy you a piece of candy, a drink, or go out of scope. | Coin ⊸ Candy Coin ⊸ Drink Coin ⊸ ⊤ | ```rust fn buy_candy(_: Coin) -> Candy { Candy{} } fn buy_drink(_: Coin) -> Drink { Drink{} } ``` |

:::

What it means for Coin to be an affine type in this example (which it is unless it implements the Copy trait) is that trying to spend the same coin twice is an invalid program that the compiler is entitled to reject:

```rust
let coin = Coin {};
let candy = buy_candy(coin); // The lifetime of the coin variable ends here.
let drink = buy_drink(coin); // Compilation error: Use of moved variable that does not possess the Copy trait.
```

In other words, an affine type system can express the [typestate pattern](https://en.wikipedia.org/wiki/Typestate_analysis): Functions can consume and return an object wrapped in different types, acting like state transitions in a [state machine](https://en.wikipedia.org/wiki/State_machine) that stores its state as a type in the caller's context – a *typestate*. An [API](https://en.wikipedia.org/wiki/API) can exploit this to statically enforce that its functions are called in a correct order.

What it doesn't mean, however, is that a variable can't be used without using it up:

```rust
// This function just borrows a coin: The ampersand means borrow.
fn validate(_: &Coin) -> Result<(), ()> { Ok(()) }

// The same coin variable can be used infinitely many times
// as long as it is not moved.
let coin = Coin {};
loop {
    validate(&coin)?;
}
```

What Rust is not able to express is a coin type that cannot go out of scope – that would take a linear type.

### Resource-linear types {#Resource-linear_types}

Under the resource interpretation, a *linear* type not only *can* be moved, like an affine type, but *must* be moved – going out of scope is an invalid program.

```rust
{
    // Must be passed on, not dropped.
    let token = HotPotato {};

    // Suppose not every branch does away with it:
    if !queue.is_full() {
        queue.push(token);
    }

    // Compilation error: Holding an undroppable object as the scope ends.
}
```

An attraction with linear types is that destructors become regular functions that can take arguments, can fail and so on.[^o21] This may for example avoid the need to keep state that is only used for destruction. A general advantage of passing function dependencies explicitly is that the order of function calls – destruction order – becomes statically verifiable in terms of the arguments' lifetimes. Compared to internal references, this does not require lifetime annotations as in Rust.

As with manual resource management, a practical problem is that any [early return](https://en.wikipedia.org/wiki/Return_early), as is typical of error handling, must achieve the same cleanup. This becomes pedantic in languages that have [stack unwinding](https://en.wikipedia.org/wiki/Stack_unwinding), where every function call is a potential early return. However, as a close analogy, the semantic of implicitly inserted destructor calls can be restored with deferred function calls.[^o22]

### Resource-normal types {#Resource-normal_types}

Under the resource interpretation, a *normal* type does not restrict how many times a variable can be moved from. [C++](https://en.wikipedia.org/wiki/C++) (specifically nondestructive move semantics) falls in this category.

```C++
auto coin = std::unique_ptr<Coin>();
auto candy = buy_candy(std::move(coin));
auto drink = buy_drink(std::move(coin)); // This is valid C++.
```

## Programming languages {#Programming_languages}

The following programming languages support linear or affine types:

- [ATS](https://en.wikipedia.org/wiki/ATS_%28programming_language%29)
- [Clean](https://en.wikipedia.org/wiki/Clean_%28programming_language%29)
- [Idris](https://en.wikipedia.org/wiki/Idris_%28programming_language%29)
- [Mercury](https://en.wikipedia.org/wiki/Mercury_%28programming_language%29)
- [F\*](wikipedia://en/38420593)
- [LinearML](https://github.com/pikatchu/LinearML)
- [Alms](http://users.eecs.northwestern.edu/~jesse/pubs/alms/)
- [Haskell](https://en.wikipedia.org/wiki/Haskell) with [Glasgow Haskell Compiler](https://en.wikipedia.org/wiki/Glasgow_Haskell_Compiler) (GHC) 9.0.1 or above[^o25]
- [Granule](https://granule-project.github.io/)
- [Rust](https://en.wikipedia.org/wiki/Rust_%28programming_language%29)
- [Swift](https://en.wikipedia.org/wiki/Swift_%28programming_language%29) 5.9 and above[^o26]
