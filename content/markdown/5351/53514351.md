# List of bitcoin forks

::: {#o1 .subject cue=lead name="List of bitcoin forks"}

[Bitcoin](wikipedia://en/28249265) forks are defined variantly as changes in the protocol of the [Bitcoin network](https://en.wikipedia.org/wiki/Bitcoin_network) or as the situations that occur "when two or more blocks have the same block height".[^o2] A fork influences the validity of the [rules](https://en.wikipedia.org/wiki/Communication_protocol). Forks are typically conducted in order to add new [features](https://en.wikipedia.org/wiki/Software_feature) to a blockchain, to reverse the effects of [hacking](https://en.wikipedia.org/wiki/Computer_hacking) or catastrophic [bugs](https://en.wikipedia.org/wiki/Software_bug). Forks require consensus to be resolved or else a permanent split emerges.

:::

According to BIP 123 specifications, there are 3 main categories of Bitcoin forks:[^o3]

- Soft Forks within Bitcoin: These don't split the network. These are consensus rule changes where some previously-valid blocks are now invalid.
- Hard Forks within Bitcoin: These cause a permanent chain split between the 2 versions. These are consensus rule changes where some previously-invalid blocks are now valid.
- Hard Forks that created alternative blockchains and cryptocurrencies.

There is also another subcategory of consensus rule changes that had a chance to cause a hard fork and chain split. However, because they were never exploited, they technically never resulted in a hard fork.

## Soft Forks within Bitcoin {#Soft_Forks_within_Bitcoin}

These are consensus rule changes that did not cause a split in the network. These are the result of consensus rule changes where previously-valid blocks are now invalid in newer clients.[^o3] Client nodes both with and without the update can still build on the same chain. Two of the most well-known Bitcoin soft forks are Segwit and Taproot.

### Taproot {#Taproot}

Taproot is an agreed soft fork in the transaction format. The fork adds support for [Schnorr signatures](wikipedia://en/450536), and improves functionality of [smart contracts](https://en.wikipedia.org/wiki/Smart_contract) and the [Lightning Network](https://en.wikipedia.org/wiki/Lightning_Network). The fork was installed in November 2021.[^o7] The upgrade adds privacy features.[^o8][^o9][^o10][^o11] Taproot includes BIP numbers 340,[^o12] 341,[^o13] 342.[^o14]

Advantages:[^o10][^o11]

- Complex transactions, such as those requiring multiple signatures or those with delayed release, are indistinguishable from simple transactions in terms of on-chain data.
- Reduced transaction costs: The data size of complex Bitcoin transactions is reduced, which leads to lower transaction fees.
- Support for more complicated conditions for a transaction via Schnorr signatures.

::: {#o15 .entry cue=list-entry name="Lightning Network"}

- Benefits for the [Lightning Network](https://en.wikipedia.org/wiki/Lightning_Network): More flexibility, privacy enhancement, lower costs.

:::

## Hard Forks within Bitcoin {#Hard_Forks_within_Bitcoin}

These are Hard Forks within Bitcoin that caused a chain split but did not create an alternative network or cryptocurrency. These are consensus rule changes where some previously-invalid blocks are now valid in newer clients.[^o3]

- v0.3.6: The addition of OP\_NOP functions eventually caused a chain split. Clients prior to 0.3.6 can no longer sync with the current Bitcoin blockchain after block 163,685.

::: {#o17 .entry cue=list-entry name="double-spend"}

- March 2013 Chain Fork. The migration from BerkeleyDB to LevelDB in v0.8 caused a chain split. Miners reorged 24-blocks by switching back to v0.7.2. At least one [double-spend](https://en.wikipedia.org/wiki/Double-spending) occurred during this event. This bug was later fixed in v0.8.1.[^o18]

:::

## Hard Forks that created alternative blockchains and cryptocurrencies {#Hard_Forks_that_created_alternative_blockchains_and_cryptocurrencies}

These are Hard Forks created via consensus rule changes that created an alternative blockchain and cryptocurrency. They share a transaction history with Bitcoin up to a certain time and date. The first hard fork splitting bitcoin happened on 1 August 2017, resulting in the creation of [Bitcoin Cash](wikipedia://en/54679407).

The following is a list of notable hard forks splitting bitcoin by date and/or block:

## Software forks of Bitcoin Core without a blockchain {#Software_forks_of_Bitcoin_Core_without_a_blockchain}

The following are proposed [software forks](https://en.wikipedia.org/wiki/Software_fork) of the Bitcoin Core [software client](https://en.wikipedia.org/wiki/Software_client) that did not successfully launch a blockchain:

**Bitcoin XT**

A fork initiated by [Mike Hearn](https://en.wikipedia.org/wiki/Mike_Hearn). The current reference implementation for bitcoin contains a computational [bottleneck](https://en.wikipedia.org/wiki/Bottleneck_%28production%29).[^o28] The actual fork was preceded by Mike Hearn publishing BIP 64 on June 10, 2014, calling for the addition of "a small P2P protocol extension that performs [UTXO](https://en.wikipedia.org/wiki/UTXO) lookups given a set of outpoints."[^o29] On December 27, 2014 Hearn released version 0.10 of the forked client XT, with the BIP 64 changes.[^o30] It achieved significant attention within the bitcoin community in mid-2015 amid a contentious debate among core developers over increasing the block size cap.[^o31][^o32]

On June 22, 2015, [Gavin Andresen](https://en.wikipedia.org/wiki/Gavin_Andresen) published BIP 101 calling for an increase in the maximum block size. The changes would activate a fork allowing eight MB blocks (doubling in size every two years) once 75% of a stretch of 1,000 mined blocks is achieved after the beginning of 2016.[^o33] The new maximum transaction rate under XT would have been 24 transactions per second.[^o34]

On August 6, 2015 Andresen's BIP 101 proposal was merged into the XT [codebase](https://en.wikipedia.org/wiki/Codebase).[^o35][^o36] BIP 101 was reverted[^o37] and the 2-MB block size bump of [Bitcoin Classic](https://en.wikipedia.org/wiki/Bitcoin_Classic) was applied instead.

The August 2015 release of XT received widespread media coverage. *[The Guardian](https://en.wikipedia.org/wiki/The_Guardian)* wrote that "bitcoin is facing civil war".[^o31]

*[Wired](https://en.wikipedia.org/wiki/Wired_%28magazine%29)* wrote that "Bitcoin XT exposes the extremely social—extremely democratic—underpinnings of the open source idea, an approach that makes open source so much more powerful than technology controlled by any one person or organization."[^o38] Developer [Adam Back](wikipedia://en/10348688) was critical of the 75% activation threshold being too low and that some of the changes were insecure.[^o39]

On August 25, 2017, Bitcoin XT published *Release G*, which was a [Bitcoin Cash](wikipedia://en/54679407) client by default.[^o40] Subsequently, *Release H* was published, which supported the November 2017 Bitcoin Cash protocol upgrade, followed by *Release I*, which supported the May 2018 Bitcoin Cash protocol upgrade.

## Potential hard forks that were never exploited {#Potential_hard_forks_that_were_never_exploited}

These are client consensus updates that could have potentially caused a hard fork. They were either never exploited before being patched, or were reverted by a reorg before they were patched.

- CVE-2010-5139: There was a value overflow bug that was exploited when a transaction minted 184B bitcoins. Miners reorged the blockchain to remove the minting transaction, causing a chain split. Because the reorg occurred before wxBitcoin v0.3.11 was released to fix the bug, it technically was not a hard fork.[^o42][^o43]
- CVE-2018-17144: Bitcoin 0.15 had a critical inflation bug that allowed double spending certain inputs in the same block. This was not exploited before being patched.[^o44]
