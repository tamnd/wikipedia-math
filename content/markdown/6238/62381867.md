# ALTS

::: {#o1 .subject cue=lead name="ALTS"}

**Application Layer Transport Security** (**ALTS**) is a [Google](https://en.wikipedia.org/wiki/Google)-developed [authentication](https://en.wikipedia.org/wiki/Authentication_protocol) and transport [encryption](wikipedia://en/10294) system used for securing [remote procedure call](https://en.wikipedia.org/wiki/Remote_procedure_call) (RPC) within Google machines.[^o2] Google started its development in 2007, as a tailored modification of [TLS](wikipedia://en/187813).[^o3]

:::

## Background {#Background}

ALTS, similar to TLS, was designed specifically for Google’s data centers and relies on two protocols, Handshake and Record.[^o5] Google began developing ALTS in 2007 in order to create a security system solution for the company’s infrastructure.[^o6]

The ALTS whitepaper[^o3] was published in December 2017. At that time the dominant [Application layer](https://en.wikipedia.org/wiki/Application_layer) protocols were SSL and TLS 1.1 (TLS 1.2 was only published as an [RFC](https://en.wikipedia.org/wiki/Request_for_Comments) in 2008[^o7]), those supported many legacy algorithms and had poor security standards. As [Google](https://en.wikipedia.org/wiki/Google) was in full control over the machines that needed secure transport of RPCs, deployment of systems was relatively easy, and so Google developers could afford designing their own system from scratch.

Another requirement that deemed a new system necessary is different [trust](wikipedia://en/18715559) models: in [TLS](wikipedia://en/187813), the server side is committed to its own [domain name](https://en.wikipedia.org/wiki/Domain_name) (and corresponding naming scheme), while Google needed the same identity (i.e. RPC) to be used with multiple naming schemes, in order to simplify microservice replication, [load balancing](https://en.wikipedia.org/wiki/Load_balancing_%28computing%29) and rescheduling between hosts.

## Details {#Details}

### Handshake protocol {#Handshake_protocol}

The ALTS [handshake](https://en.wikipedia.org/wiki/Handshake_%28computing%29) protocol is based on authenticated [Diffie–Hellman key exchange](wikipedia://en/7903) scheme, and supports both [perfect forward secrecy](https://en.wikipedia.org/wiki/Perfect_forward_secrecy) (access to current keys does not compromise future security) and session resumption (noticeable speedups in the protocol after the first session between the parties).

Unlike TLS, in ALTS both parties — server and client — have a [certificate](wikipedia://en/223796) proving their respective identities. The certificate chains to a trusted signing service verification key, with the leaf being an [Elliptic-curve Diffie–Hellman](wikipedia://en/3357958) key, that is eventually used for key exchange. The [elliptic curve](wikipedia://en/10225) used in the key exchange is [Curve25519](wikipedia://en/17935444).[^o10]

The handshake protocol consists of four messages, sent in plaintext:

- *ClientInit*, initiated by the client, and contains the client's certificate, list of available [cipher suites](wikipedia://en/25149718), and a session resumption attempt;
- *ServerInit*, sent by the server as a response, and contains its own certificate, chosen cipher suite, and optionally an encrypted resumption ticket;
- *ServerFinished*, sent by the server (concatenated to the previous message in ALTS default implementation), and contains a handshake authenticator, i.e. [HMAC](wikipedia://en/17112) over a known bitstring using the calculated session key;
- *ClientFinished*, sent by the client, and contains a handshake authenticator, similarly to the one in *ServerFinished*.

Once both parties computed the session key (*record protocol* in the whitepaper), they can start encrypting traffic with the symmetric encryption algorithm 128-bit [AES](wikipedia://en/1260), using mostly [GCM](wikipedia://en/5897139) as its [mode of operation](https://en.wikipedia.org/wiki/Unblock_cipher_mode_of_operation). On older machines, a Google developed VCM[^o11] was used.[^o12]

The handshake protocol was verified using the [ProVerif](https://en.wikipedia.org/wiki/ProVerif) formal verification tool.[^o13]

### Session resumption {#Session_resumption}

In order to avoid repeating computationally expensive operations, ALTS supports session resumption. The resumption tickets are created by either the server or the client, and may be used in the handshake protocol, if both parties hold the same resumption ticket, indexed by a *resumption identifier*. The *resumption secret* is used to derive the next session key, authenticator and encapsulated (independent) resumption ticket/identifier.

### Perfect forward secrecy {#Perfect_forward_secrecy}

[Perfect forward secrecy](https://en.wikipedia.org/wiki/Perfect_forward_secrecy) (PFS) is not enabled by default in ALTS; however, it is supported. Instead of using an inherent PFS algorithm, ALTS achieves PFS by frequently rotating the certificates, which have a short lifespan ( 20, or 48 minutes; see [^o12]). Moreover, if PFS is enabled, it is also enabled for session resumption, by deriving the encryption keys from the resumption ticket using a [pseudorandom function](https://en.wikipedia.org/wiki/Pseudorandom_function).
