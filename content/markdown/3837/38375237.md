# Server-based signatures

::: {#o1 .subject cue=lead name="Server-based signatures"}

In [cryptography](wikipedia://en/18934432), **server-based signatures**are [digital signatures](wikipedia://en/59644) in which a publicly available server participates in the signature creation process. This is in contrast to conventional digital signatures that are based on [public-key cryptography](wikipedia://en/24222) and [public-key infrastructure](https://en.wikipedia.org/wiki/Public-key_infrastructure). With that, they assume that signers use their personal [trusted computing bases](https://en.wikipedia.org/wiki/Trusted_computing_base) for generating signatures without any communication with servers.

:::

Four different classes of server based signatures have been proposed:

\1. **Lamport One-Time Signatures.** Proposed in 1979 by [Leslie Lamport](https://en.wikipedia.org/wiki/Leslie_Lamport).[^o2] [Lamport one-time signatures](wikipedia://en/3200486) are based on [cryptographic hash functions](https://en.wikipedia.org/wiki/Cryptographic_hash_functions). For signing a message, the signer just sends a list of hash values (outputs of a hash function) to a publishing server and therefore the signature process is very fast, though the size of the signature is many times larger, compared to ordinary public-key signature schemes.

\2. **On-line/off-line Digital Signatures.** First proposed in 1989 by [Even](https://en.wikipedia.org/wiki/Shimon_Even), [Goldreich](https://en.wikipedia.org/wiki/Oded_Goldreich) and [Micali](https://en.wikipedia.org/wiki/Silvio_Micali)[^o3][^o4][^o5] in order to speed up the signature creation procedure, which is usually much more time-consuming than verification. In case of [RSA](wikipedia://en/25385), it may be one thousand times slower than verification. On-line/off-line digital signatures are created in two phases. The first phase is performed [off-line](https://en.wikipedia.org/wiki/Online_and_offline), possibly even before the message to be signed is known. The second (message-dependent) phase is performed on-line and involves communication with a server. In the first (off-line) phase, the signer uses a conventional public-key digital signature scheme to sign a public key of the Lamport one-time signature scheme. In the second phase, a message is signed by using the Lamport signature scheme. Some later works [^o6][^o7][^o8][^o9][^o10][^o11][^o12] have improved the efficiency of the original solution by Even et al.

\3. **Server-Supported Signatures (SSS).** Proposed in 1996 by [Asokan](https://en.wikipedia.org/wiki/N._Asokan), [Tsudik](https://en.wikipedia.org/wiki/Gene_Tsudik) and [Waidner](https://en.wikipedia.org/wiki/Michael_Waidner)[^o13][^o14] in order to delegate the use of time-consuming operations of [asymmetric cryptography](https://en.wikipedia.org/wiki/Asymmetric_cryptography) from clients (ordinary users) to a server. For ordinary users, the use of asymmetric cryptography is limited to signature verification, i.e. there is no pre-computation phase like in the case of on-line/off-line signatures. The main motivation was the use of low-performance mobile devices for creating digital signatures, considering that such devices could be too slow for creating ordinary public-key digital signatures, such as [RSA](https://en.wikipedia.org/wiki/RSA_Cryptosystem). Clients use [hash chain](wikipedia://en/7386159) based [authentication](wikipedia://en/47967)[^o15] to send their messages to a signature server in an [authenticated](wikipedia://en/47967) way and the server then creates a digital signature by using an ordinary public-key [digital signature](wikipedia://en/59644) scheme. In SSS, signature servers are not assumed to be [Trusted Third Parties](wikipedia://en/584651) (TTPs) because the transcript of the hash chain authentication phase can be used for [non repudiation](wikipedia://en/52491) purposes. In SSS, servers cannot create signatures in the name of their clients.

\4. **Delegate Servers (DS).** Proposed in 2002 by Perrin, Bruns, Moreh and Olkin[^o16] in order to reduce the problems and costs related to individual [private keys](https://en.wikipedia.org/wiki/Private_key). In their solution, clients (ordinary users) delegate their private cryptographic operations to a Delegation Server (DS). Users authenticate to DS and request to sign messages on their behalf by using the server's own private key. The main motivation behind DS was that private keys are difficult for ordinary users to use and easy for attackers to abuse. Private keys are not memorable like [passwords](wikipedia://en/24304) or derivable from persons like [biometrics](https://en.wikipedia.org/wiki/Biometrics), and cannot be entered from [keyboards](https://en.wikipedia.org/wiki/Keyboard_%28computing%29) like passwords. Private keys are mostly stored as [files](https://en.wikipedia.org/wiki/Computer_file) in [computers](https://en.wikipedia.org/wiki/Computer) or on [smart-cards](https://en.wikipedia.org/wiki/Smart-card), that may be stolen by attackers and abuse off-line. In 2003, Buldas and Saarepera[^o17] proposed a two-level architecture of delegation servers that addresses the trust issue by replacing trust with threshold trust via the use of [threshold cryptosystems](wikipedia://en/6866642).
