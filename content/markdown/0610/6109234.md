# CryptGenRandom

::: {#o1 .subject cue=lead name="CryptGenRandom"}

**CryptGenRandom** is a [cryptographically secure pseudorandom number generator](https://en.wikipedia.org/wiki/CSPRNG) function that is included in [Microsoft CryptoAPI](wikipedia://en/3302413). In [Win32](https://en.wikipedia.org/wiki/Win32) programs, Microsoft recommended its use anywhere random number generation is needed (it has since been replaced by **BCryptGenRandom**, see below). The [kernel32](https://en.wikipedia.org/wiki/Kernel32) equivalent is **RtlGenRandom**.

:::

A 2007 paper from Hebrew University suggested security problems in the [Windows 2000](https://en.wikipedia.org/wiki/Windows_2000) implementation of [CryptGenRandom](wikipedia://en/6109234) (assuming the attacker has control of the machine). Microsoft later acknowledged that the same problems exist in [Windows XP](https://en.wikipedia.org/wiki/Windows_XP), but not in [Vista](https://en.wikipedia.org/wiki/Windows_Vista). Microsoft released a fix for the bug with Windows XP Service Pack 3 in mid-2008.[^o2]

CryptGenRandom is deprecated as it belongs to the deprecated Windows CryptoAPI. The modern Cryptography API: Next Generation (CNG) replacement is **BCryptGenRandom** (and the underlying functions ProcessPrng and SystemPrng).[^o3]

## Background {#Background}

The [Win32](https://en.wikipedia.org/wiki/Win32) [API](https://en.wikipedia.org/wiki/API) includes comprehensive support for cryptography through the [Microsoft CryptoAPI](wikipedia://en/3302413), a set of cryptographic primitives provided by Microsoft for use in Windows applications. Windows technologies such as [TLS](wikipedia://en/187813) support (via the [Schannel](https://en.wikipedia.org/wiki/Security_Support_Provider_Interface#Providers) API) and [code signing](wikipedia://en/3768009) rely on these primitives, which in turn rely on a [cryptographically secure pseudorandom number generator](https://en.wikipedia.org/wiki/CSPRNG) (CSPRNG). CryptGenRandom is the standard CSPRNG supplied with the Microsoft CryptoAPI.

## Method of operation {#Method_of_operation}

### Before Windows Vista {#Before_Windows_Vista}

Microsoft-provided [cryptography](wikipedia://en/18934432) providers share the same implementation of CryptGenRandom, currently based on an internal [function](https://en.wikipedia.org/wiki/Function_%28computer_science%29) called RtlGenRandom.[^o7] Only a general outline of the [algorithm](wikipedia://en/775) had been published :

> \[*RtlGenRandom*\] generates as specified in [FIPS](https://en.wikipedia.org/wiki/Federal_Information_Processing_Standard) 186-2 appendix 3.1 with [SHA-1](wikipedia://en/26672) as the G function. And with entropy from:
>
> The current process ID (GetCurrentProcessID).
>
> The current thread ID (GetCurrentThreadID).
>
> The tick count since boot time (GetTickCount).
>
> The current time (GetLocalTime).
>
> Various high-precision performance counters (QueryPerformanceCounter).
>
> An [MD4](wikipedia://en/578106) hash of the user's environment block, which includes username, computer name, and search path. \[...\]
>
> High-precision internal CPU counters, such as RDTSC, RDMSR, RDPMC \[*omitted: long lists of low-level system information fields and performance counters*\] [^o8]

### Windows Vista and above {#Windows_Vista_and_above}

Microsoft has documented the implementation of the [Windows 10](https://en.wikipedia.org/wiki/Windows_10) random number generator in some detail, in a whitepaper published in 2019.[^o10] In Windows 10:

- There exists a hierarchy of random number generators. The kernel has a "Root" PRNG, from which all randomness is ultimately derived. The kernel then uses the Root PRNG to seed one PRNG per logical processor (so the PRNG state is [thread-local](https://en.wikipedia.org/wiki/Thread-local) and requires no locking). When a process launches, it requests random bytes from the kernel per-processor PRNG to seed its own Process PRNG. It then uses the Process PRNG to also seed one buffered PRNG per logical processor.[^o10]
- All userspace calls to fetch randomness, be it CryptGenRandom or RtlGenRandom, ultimately fall to ProcessPrng, which returns bytes from the process's per-processor PRNG. The PRNG always uses the AES-CTR-DRBG algorithm as specified by FIPS SP800-90. Although BCryptGenRandom accepts requests for older algorithms for [backward compatibility](https://en.wikipedia.org/wiki/Backward_compatibility), it only ever return random numbers from the per-processor PRNG.[^o10]
  - AES-CTR-DRBG, instead of FIPS 186, has been the default since Windows Vista and [Windows Server 2008](https://en.wikipedia.org/wiki/Windows_Server_2008).[^o11]
  - The removal of other algorithms happened in Windows 10.[^o11]
- The root RNG is periodically reseeded from the entropy pools.[^o10] At bootup when very little entropy is available, a special "initial seeding" procedure provides the seed from seed files, external entropy, [TPM](wikipedia://en/2936835) randomness, [RDRAND](https://en.wikipedia.org/wiki/RDRAND)/RDSEED instructions, ACPI-OEM0 table, [UEFI](https://en.wikipedia.org/wiki/UEFI) entropy, and the current time.[^o10]
- The kernel maintains multiple entropy pools. Multiple entropy sources append into pools, the main one being interrupt timing.[^o10] When a pool is used, the SHA-512 hash of its contents is taken as the output.[^o10] Windows does not estimate entropy.[^o10]

## Security {#Security}

The security of a cryptosystem's CSPRNG is crucial because it is the origin for dynamic key material. Keys needed "on the fly", such as the TLS [session keys](wikipedia://en/63941) that protect [HTTPS](wikipedia://en/13586) connections, originate from CSPRNGs. If these pseudorandom numbers are predictable, session keys are predictable as well. Because CryptGenRandom is the de facto standard CSPRNG in Win32 environments, its security is critical for Windows users.

### Cryptanalysis {#Cryptanalysis}

A [cryptanalysis](wikipedia://en/5715) of CryptGenRandom, published in November 2007 by Leo Dorrendorf and others from the [Hebrew University of Jerusalem](https://en.wikipedia.org/wiki/Hebrew_University_of_Jerusalem) and [University of Haifa](https://en.wikipedia.org/wiki/University_of_Haifa), found significant weaknesses in the [Windows 2000](https://en.wikipedia.org/wiki/Windows_2000) implementation of the algorithm.[^o14]

To take advantage of the vulnerability, an attacker would first need to compromise the program running the random number generator. The weaknesses in the paper all depend on an attacker siphoning the state bits out of the generator. An attacker in a position to carry out this attack would typically already be in a position to defeat any random number generator (for instance, they can simply sniff the outputs of the generator, or fix them in memory to known values). However, the Hebrew University team notes that an attacker only need steal the state bits once in order to persistently violate the security of a CryptGenRandom instance. They can also use the information they glean to determine past random numbers that were generated, potentially compromising information, such as credit card numbers, already sent.

The paper's attacks are based on the fact that CryptGenRandom uses the [stream cipher](wikipedia://en/49007) [RC4](wikipedia://en/25831), which can be run backwards once its state is known. They also take advantage of the fact that CryptGenRandom runs in [user mode](https://en.wikipedia.org/wiki/User_mode), allowing anyone who gains access to the operating system at user level, for example by exploiting a [buffer overflow](https://en.wikipedia.org/wiki/Buffer_overflow), to get CryptGenRandom's state information for that process. Finally, CryptGenRandom refreshes its seed from [entropy](https://en.wikipedia.org/wiki/Information_entropy) infrequently. This problem is aggravated by the fact that each Win32 process has its own instance of CryptGenRandom state; while this means that a compromise of one process does not transitively compromise every other process, it may also increase the longevity of any successful break.

Because the details of the CryptGenRandom algorithm were not public at the time, Dorrendorf's team used [reverse engineering](https://en.wikipedia.org/wiki/Reverse_engineering) tools to discern how the algorithm works. Their paper is the first published record of how the Windows cryptographic random number generator operates.

### Common Criteria {#Common_Criteria}

Windows 2000, XP and 2003 have all successfully undergone EAL4+ evaluations, including the CryptGenRandom() and FIPSGenRandom() implementations. The Security Target documentation is available at [the Common Criteria Portal](https://web.archive.org/web/20060718074701/http://www.commoncriteriaportal.org/), and indicates compliance with the EAL4 requirements. Few conclusions can be drawn about the security of the algorithm as a result; EAL4 measures products against best practices and stated security objectives, but rarely involves in-depth cryptanalysis.

### FIPS validation {#FIPS_validation}

Microsoft has obtained validation of its RNG implementations in the following environments:

- Windows Vista and Server 2008 RNG Implementation (certificate 435)[^o17]
- Windows Vista RNG implementations (certificate 321)[^o17]
- Windows 2003 Enhanced Cryptographic Provider (rsaenh.dll) (certificate 316)[^o17]
- Windows 2003 Enhanced DSS and Diffie-Hellman Cryptographic Provider (dssenh.dll) (certificate 314)[^o17]
- Windows 2003 Kernel Mode Cryptographic Module (fips.sys) (certificate 313)[^o17]
- [Windows CE](https://en.wikipedia.org/wiki/Windows_CE) and [Windows Mobile](https://en.wikipedia.org/wiki/Windows_Mobile) Enhanced Cryptographic Provider (rsaenh.dll) (certificate 292)[^o17]
- Windows CE and Windows Mobile Enhanced Cryptographic Provider (rsaenh.dll) (certificate 286)[^o17]
- Windows CE Enhanced Cryptographic Provider (rsaenh.dll) (certificate 66)[^o17]

These tests are "designed to test conformance to the various approved RNG specifications rather than provide a measure of a product’s security. \[...\] Thus, validation should not be interpreted as an evaluation or endorsement of overall product security." Few conclusions can be drawn about the security of the algorithm as a result; FIPS evaluations do not necessarily inspect source code or evaluate the way RNG seeds are generated.[^o18]

The RNG validation list carries the following notice: "As of January 1, 2016, in accordance with the SP800-131A Revision 1 Transitions: Recommendation for Transitioning the Use of Cryptographic Algorithms and Key Lengths, the use of RNGs specified in FIPS 186-2, \[X9.31\], and the 1998 version of \[X9.62\] is no longer approved. This list is provided for historical purposes only."[^o19]

## Alternatives {#Alternatives}

### API level {#API_level}

Windows developers have several alternative means of accessing the CryptGenRandom functionality; these alternatives invoke the same algorithm and share the same security characteristics, but may have other advantages.

#### Using RtlGenRandom {#Using_RtlGenRandom}

If backwards compatibility up to Windows XP is required for your program, the Windows API function RtlGenRandom (which resides in advapi32.dll[^o7]) can be called to generate secure random data, as shown below. If this is not an issue, the program should use the newer BCryptGenRandom call instead.

> Historically, we always told developers not to use functions such as rand to generate keys, nonces and passwords, rather they should use functions like CryptGenRandom, which creates cryptographically secure random numbers. The problem with CryptGenRandom is you need to pull in CryptoAPI (CryptAcquireContext and such) which is fine if you're using other crypto functions.
>
> On a default Windows XP and later install, CryptGenRandom calls into a function named ADVAPI32!RtlGenRandom, which does not require you load all the CryptAPI stuff. In fact, the new [Whidbey](https://en.wikipedia.org/wiki/Visual_Studio_2005) CRT function, rand\_s calls RtlGenRandom.[^o29]

#### Using RNGCryptoServiceProvider {#Using_RNGCryptoServiceProvider}

Programmers using [.NET](https://en.wikipedia.org/wiki/.NET_Framework) should use the RNGCryptoServiceProvider Class.[^o24]

#### Using Cryptography API: Next Generation (CNG) {#Using_Cryptography_API:_Next_Generation_(CNG)}

The CNG [^o26] is a long term replacement for the deprecated Crypto API. It provides an equivalent function **BCryptGenRandom**[^o27] as well as dedicated functions for key generation.

### Programming languages {#Programming_languages}

- the Microsoft C library function rand\_s uses RtlGenRandom to generate cryptographically secure random numbers.[^o29]
- the [Python](https://en.wikipedia.org/wiki/Python_%28programming_language%29) function *urandom* in the *os* module, which uses [/dev/urandom](https://en.wikipedia.org/wiki//dev/urandom) on [Unix-like](https://en.wikipedia.org/wiki/Unix-like) systems, calls CryptGenRandom on Windows systems.[^o30]
- the SunMSCAPI [JCA](https://en.wikipedia.org/wiki/Java_Cryptography_Architecture) provider available with [OpenJDK](https://en.wikipedia.org/wiki/OpenJDK) and Oracle distributions of the [JRE](https://en.wikipedia.org/wiki/Java_Runtime_Environment) on Windows provides a SecureRandom implementation with the algorithm name Windows-PRNG. This class forwards all queries for random or seed bytes as well as setting additional seed bytes to CryptGenRandom.[^o31]
