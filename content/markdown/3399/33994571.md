# TRESOR

::: {#o1 .subject cue=lead name="TRESOR"}

**TRESOR** ([recursive acronym](https://en.wikipedia.org/wiki/Recursive_acronym) for "TRESOR Runs Encryption Securely Outside RAM", and also the German word for a [safe](https://en.wikipedia.org/wiki/Safe)) is a [Linux kernel](https://en.wikipedia.org/wiki/Linux_kernel) patch which provides [encryption](wikipedia://en/10294) using only the [CPU](https://en.wikipedia.org/wiki/CPU) to defend against [cold boot attacks](wikipedia://en/15893148) on computer systems by performing encryption inside [CPU registers](https://en.wikipedia.org/wiki/CPU_register) rather than [random-access memory](https://en.wikipedia.org/wiki/Random-access_memory) (RAM). It is one of two proposed solutions for general-purpose computers. The other, called "frozen cache" uses the [CPU cache](https://en.wikipedia.org/wiki/CPU_cache) instead.[^o2] It was developed from its predecessor [AESSE](https://en.wikipedia.org/wiki/AESSE), presented at [EuroSec](https://en.wikipedia.org/wiki/EuroSec) 2010 and presented at [USENIX](https://en.wikipedia.org/wiki/USENIX) Security 2011.[^o3] The authors state that it allows RAM to be treated as untrusted from a security viewpoint without hindering the system.

:::

## Motivation {#Motivation}

In [computer security](https://en.wikipedia.org/wiki/Computer_security), a common problem for data security is how an intruder can access [encrypted data](https://en.wikipedia.org/wiki/Data_encryption) on a computer. Modern encryption algorithms, correctly implemented and with [strong passwords](wikipedia://en/4459886), are often unbreakable with current technology, so emphasis has moved to techniques that bypass this requirement, by exploiting aspects of data security where the encryption can be "broken" with much less effort, or else bypassed completely.

A [cold boot attack](wikipedia://en/15893148) is one such means by which an intruder can defeat encryption despite system security, if they can gain physical access to the running machine. It is premised on the physical properties of the circuitry within [memory devices](https://en.wikipedia.org/wiki/Random-access_memory) that are commonly used in computers. The concept is that when a computer system has encrypted data open, the [encryption keys](wikipedia://en/53039) themselves used to read or write that data are usually stored on a temporary basis in physical memory, in a plain readable form. (Holding these keys in "plain" form during use is hard or impossible to avoid with usual systems since the system itself must be able to access the data when instructed by the authorized user). Usually this is no benefit to an unauthorised intruder, because they cannot access or use those keys—for example due to security built into the software or system. However, if the memory devices can be accessed outside the running system without loss of contents, for example by quickly restarting the computer or removing the devices to a different device, then the current contents—including any encryption keys in use—can be plainly read and used. This can be important if the system cannot be used to view, copy or access that data—for example the system is locked, or may have [booby traps](https://en.wikipedia.org/wiki/Booby_trap) or other intrusion controls, or is needed in a guaranteed untouched form for [forensic](https://en.wikipedia.org/wiki/Forensic) or [evidentiary](https://en.wikipedia.org/wiki/Evidence) purposes.

Since this is a physical property of the hardware itself, and based on physical properties of memory devices, it cannot be defeated easily by pure software techniques, since all software running in memory at the point of intervention becomes accessible. As a result, any encryption software whose keys could be accessed this way is vulnerable to such attacks. Usually a cold boot attack involves cooling memory chips or quickly restarting the computer, and exploiting the fact that data is not immediately lost (or not lost if power is very quickly restored) and the data that was held at the point of intervention will be left accessible to examination.

Cold boot attacks can therefore be a means of unauthorized data theft, loss or access. Such attacks can be nullified if the encryption keys are not accessible at a hardware level to an intruder–i.e., the devices in which the keys are stored when in use are not amenable to cold boot attacks–but this is not the usual case.

## TRESOR's approach {#TRESOR's_approach}

TRESOR is a software approach that seeks to resolve this insecurity by storing and manipulating encryption keys almost exclusively on the [CPU](https://en.wikipedia.org/wiki/Central_processing_unit) alone, and in registers accessible at [ring 0](https://en.wikipedia.org/wiki/Ring_0_%28computer_security%29) (the highest privilege level) only—the exception being the brief period of initial calculation at the start of a session. This ensures that encryption keys are almost never available to [userspace](https://en.wikipedia.org/wiki/Userspace) code or following a cold boot attack. TRESOR is written as a [patch](https://en.wikipedia.org/wiki/Software_patch) to the [kernel](https://en.wikipedia.org/wiki/Kernel_%28operating_system%29) that stores encryption keys in the [x86 debug registers](https://en.wikipedia.org/wiki/X86_debug_register), and uses [on-the-fly](https://en.wikipedia.org/wiki/On-the-fly_encryption) [round key](https://en.wikipedia.org/wiki/Round_key) generation, [atomicity](https://en.wikipedia.org/wiki/Atomicity_%28programming%29), and blocking of usual [ptrace](https://en.wikipedia.org/wiki/Ptrace) access to the debug registers for security.

TRESOR was foreshadowed by a 2010 thesis by Tilo Muller which analyzed the cold boot attack issue. He concluded that modern [x86](https://en.wikipedia.org/wiki/X86) processors had two register areas where CPU-based kernel encryption was realistic: the [SSE](wikipedia://en/55365) registers which could in effect be made privileged by disabling all SSE instructions (and necessarily, any programs relying on them), and the debug registers which were much smaller but had no such issues. He left the latter for others to examine, and developed a [proof of concept](https://en.wikipedia.org/wiki/Proof_of_concept) distribution called *[Paranoix](https://en.wikipedia.org/wiki/Paranoix)* based on the SSE register method.[^o6]

Its developers state that "running TRESOR on a 64-bit CPU that supports [AES-NI](https://en.wikipedia.org/wiki/AES-NI), there is no performance penalty compared to a generic implementation of [AES](wikipedia://en/1260)",[^o7] and run slightly faster than standard encryption despite the need for key recalculation, a result which initially surprised the authors as well.[^o3]

## Potential vulnerabilities {#Potential_vulnerabilities}

section The authors' paper notes the following:

- Although they cannot rule out CPU data leaking into RAM, they were unable to observe any case this happened during formal testing. Any such case is expected to be patchable.
- [Root access](https://en.wikipedia.org/wiki/Root_access) to the encryption keys via the kernel of a running system is possible using [loadable kernel modules](https://en.wikipedia.org/wiki/Loadable_kernel_module) or virtual memory ([/dev/kmem](https://en.wikipedia.org/wiki/Kmem)) and physical memory (/dev/mem), if compiled to support these, but otherwise appears not to be accessible in any known way on a standard running system.
- [ACPI](https://en.wikipedia.org/wiki/Advanced_Configuration_and_Power_Interface) sleep and low power states: - on real processors registers are reset to zero during ACPI S3 states (suspend-to-ram) and S4 (suspend-to-disk) states since the CPU is switched off for these.
- Cold boot attacks on the CPU: - on real processors registers are cleared to zero on both hardware resets and software resets ("[Ctrl-Alt-Delete](https://en.wikipedia.org/wiki/Ctrl-Alt-Delete)"). However CPU registers are currently vulnerable on [virtual machines](https://en.wikipedia.org/wiki/Virtual_machine), since they are reset during simulated hardware resets but **not** during software resets. The authors deem this an apparent flaw in many implementations of virtual machines, but note that virtual systems would be inherently vulnerable even if this were rectified, since all registers on a virtual machine are likely to be accessible using the host system.
- TRESOR is resistant to [timing attacks](wikipedia://en/481813) and cache-based attacks by design of the AES-NI instruction, where the CPU supports [AES instruction set](wikipedia://en/23095336) extensions.[^o9] Processors capable of handling AES extensions as of 2011 are Intel [Westmere](https://en.wikipedia.org/wiki/Nehalem_%28microarchitecture%29#Westmere) and [Sandy Bridge](https://en.wikipedia.org/wiki/Sandy_Bridge) (some i3 excepted) and successors, [AMD Bulldozer](https://en.wikipedia.org/wiki/AMD_Bulldozer), and certain [VIA PadLock](https://en.wikipedia.org/wiki/VIA_PadLock) processors.
- In 2012 a paper called TRESOR-HUNT showed how a [DMA attack](https://en.wikipedia.org/wiki/DMA_attack) could break this system, by injecting code that would invisibly function at [ring 0](https://en.wikipedia.org/wiki/Ring_0_%28computer_security%29) (the highest privilege level). This code would bypass the "lockout" imposed by TRESOR, allowing it to read the keys from the debug registers and transfer them to usual memory. The paper also proposed ways to mitigate such attacks.[^o10]
