# Speck (cipher)

::: {#o4 .subject cue=lead name="Speck"}

**Speck** is part of a family of lightweight [block ciphers](wikipedia://en/4594) publicly released by the [National Security Agency](wikipedia://en/21939) (NSA) in June 2013.[^o5] Speck has been optimized for performance in software implementations, while its sister algorithm, [Simon](wikipedia://en/39994308), has been optimized for hardware implementations. Speck is an [add–rotate–xor](wikipedia://en/4594#Operations) (ARX) cipher.

:::

The NSA began working on the Simon and Speck ciphers in 2011. The agency anticipated some agencies in the US federal government would need a cipher that would operate well on a diverse collection of [Internet of Things](https://en.wikipedia.org/wiki/Internet_of_Things) devices while maintaining an acceptable level of security.[^o6]

## Cipher description {#Cipher_description}

Speck supports a variety of block and key sizes. A block is always two words, but the words may be 16, 24, 32, 48 or 64 bits in size. The corresponding key is 2, 3 or 4 words. The round function consists of two rotations, adding the right word to the left word, xoring the key into the left word, then xoring the left word into the right word. The number of rounds depends on the parameters selected, as follows:[^o5]

::: {#o8 .table cue=table}

| Block size (bits) | Key size (bits) | Rounds |
|---|---|---|
| 2×16 = 32 | 4×16 = 64 | 22 |
| 2×24 = 48 | 3×24 = 72 | 22 |
|  | 4×24 = 96 | 23 |
| 2×32 = 64 | 3×32 = 96 | 26 |
|  | 4×32 = 128 | 27 |
| 2×48 = 96 | 2×48 = 96 | 28 |
|  | 3×48 = 144 | 29 |
| 2×64 = 128 | 2×64 = 128 | 32 |
|  | 3×64 = 192 | 33 |
|  | 4×64 = 256 | 34 |

:::

The [key schedule](wikipedia://en/609603) uses the same round function as the main block cipher.

## Reference code {#Reference_code}

The following is the designers' reference implementation, written in [C](https://en.wikipedia.org/wiki/C_%28programming_language%29), of the Speck variant with a 128-bit block size and key, where key = (K\[1\], K\[0\]). It is adapted from their [IACR](wikipedia://en/87043) ePrint.[^o5]

```C
#include <stdint.h>

#define ROR(x, r) ((x >> r) | (x << (64 - r)))
#define ROL(x, r) ((x << r) | (x >> (64 - r)))
#define R(x, y, k) (x = ROR(x, 8), x += y, x ^= k, y = ROL(y, 3), y ^= x)
#define ROUNDS 32

void encrypt(uint64_t ct[2],
             uint64_t const pt[2],            
             uint64_t const K[2])
{
   uint64_t y = pt[0], x = pt[1], b = K[0], a = K[1];

   R(x, y, b);
   for (int i = 0; i < ROUNDS - 1; i++) {
      R(a, b, i);
      R(x, y, b);
   }

   ct[0] = y;
   ct[1] = x;
}
```

Note that this code computes the round keys ([key schedule](wikipedia://en/609603)) on-demand. In practice, as with other block ciphers it is common for implementations to compute the round keys just once and cache them, rather than recomputing them for every block encrypted or decrypted. Although, as the authors point out, "Given that small code size was a major goal of the design, it made sense to reuse the round function for round key generation. This approach enables on-the-fly round key generation for microcontroller implementations, using just the round function code, very little ROM, and no RAM beyond what is required to hold the key and plaintext."[^o10]

For 16-bit words (Speck32), the rotates are 7 bits right and 2 bits left; for all other word sizes, they are 8 and 3 as shown here.

If the key is more than 2 words long, there are 2 or 3 `a` values, which are used in rotation.

### Endianness {#Endianness}

The original Speck paper does not explicitly state the [endianness](https://en.wikipedia.org/wiki/Endianness) of bytes when the plaintext block is interpreted as the two words used in the cipher algorithm. The test vectors given in the paper suggest big-endian order. However, the authors of the algorithm have advised some implementers[^o12] that little-endian byte order is to be used for keys, plaintext, and ciphertext, and the practice was accepted by others.[^o13]

## Performance {#Performance}

According to [ECRYPT](wikipedia://en/1635837)'s stream cipher benchmarks (eBASC), Speck is one of the fastest ciphers available, both for long as well as short messages. Some median performances for long messages (128-bit, 128-block size version) are: 1.99 [cycles per byte](https://en.wikipedia.org/wiki/Cycles_per_byte) (cpb) on an AMD Ryzen 7 1700; 1.27 cpb on an Intel Core i5-6600; 15.96 cpb on a Broadcom BCM2836 Cortex A7.[^o15] For example, on the [ARMv7](https://en.wikipedia.org/wiki/ARMv7) platform, Speck is about 3 times faster than [AES](https://en.wikipedia.org/wiki/AES_%28cipher%29).[^o16]

When implemented on 8-bit AVR microcontroller, Speck encryption with 64-bit blocks and 128-bit key consumes 192 bytes of [flash memory](https://en.wikipedia.org/wiki/Flash_memory), temporary variables consume 112 bytes of RAM, and takes 164 cycles to encrypt each byte in the block.[^o17]

[Salsa20](wikipedia://en/2701329) is a [stream cipher](wikipedia://en/49007) with comparable performance, but it is difficult to use stream ciphers securely in some applications where block ciphers like Speck work well. This led Google to add an implementation of Speck in Linux kernel version 4.17, planning to offer it as an option for disk encryption on low-end [Android](https://en.wikipedia.org/wiki/Android_%28operating_system%29) devices that would otherwise be unencrypted due to slow AES performance on processors that lack [AES instructions](wikipedia://en/23095336).[^o18][^o19] Speck was later dropped from the Linux kernel due to backlash and concerns, and Google switched to the [Adiantum algorithm](wikipedia://en/59693398) instead.[^o20][^o21][^o22]

## Security {#Security}

### Cryptanalysis {#Cryptanalysis}

The designers claim that Speck, though a "lightweight" cipher, is designed to have the full security possible for each block and key size, against standard [chosen-plaintext (CPA)](wikipedia://en/63852) and [chosen-ciphertext (CCA)](wikipedia://en/103586) attacks. Resistance against [related-key attacks](wikipedia://en/1516144) was also stated as a goal, though a less crucial one as attacks in that model are not relevant for typical use cases.[^o25] No effort was made to resist attacks in the [known-key distinguishing attack](wikipedia://en/48235152) model, nor did the designers evaluate Speck for use as a [hash function](https://en.wikipedia.org/wiki/Hash_function).[^o5]

As of 2018, no successful attack on full-round Speck of any variant is known. Due to interest in Simon and Speck, about 70 cryptanalysis papers have been published on them.[^o25] As is typical for [iterated ciphers](wikipedia://en/4594#Iterated_block_ciphers), reduced-round variants have been successfully attacked. The best published attacks on Speck in the standard attack model (CPA/CCA with unknown key) are [differential cryptanalysis](wikipedia://en/8536) attacks; these make it through about 70–75% of the rounds of most variants, though these best attacks are only marginally faster than [brute-force](https://en.wikipedia.org/wiki/Brute-force_attacks).[^o2][^o3][^o25] The design team states that while designing Speck, they found differential attacks to be the limiting attacks, i.e. the type of attack that makes it through the most rounds; they then set the number of rounds to leave a security margin similar to [AES-128](wikipedia://en/1260)'s at approximately 30%.[^o25]

Speck has been criticized for having too small a security margin, i.e. too few rounds between the best attacks and the full cipher, in comparison to more conservative ciphers such as [ChaCha20](wikipedia://en/2701329#ChaCha_variant).[^o27] Ciphers with small security margins are more likely to be broken by future advances in [cryptanalysis](wikipedia://en/5715). Speck's design team counters that there is a real-world cost to unnecessarily large security margins, especially on lightweight devices, that cryptanalysis during the design phase allowed the number of rounds to be set appropriately, and that they targeted AES's security margin.[^o25]

Speck includes a round counter in the [key schedule](wikipedia://en/609603). The designers state this was included to block [slide](wikipedia://en/1821327) and [rotational cryptanalysis](wikipedia://en/26122724) attacks.[^o25] Still, rotational-XOR cryptanalysis has been used to find [distinguishers](wikipedia://en/11563117) against reduced-round versions of Speck.[^o28] Though the authors don't describe standard key-recovery attacks based on their distinguishers, their best distinguishers on Speck32 and Speck48 in the known-key distinguishing attack model for certain [weak key](wikipedia://en/719388) classes make it through slightly more rounds than the best differential distinguishers. One of the authors has said that his research was resource-constrained and that rotational-XOR distinguishers on more rounds are probably possible.[^o29] However, this type of cryptanalysis assumes the [related-key](wikipedia://en/1516144) or even the known-key attack models,[^o28] which are not a concern in typical cryptographic protocols and solutions.[^o30] The designers also state that Speck was not designed to resist known-key distinguishing attacks (which do not directly compromise the confidentiality of ciphers).[^o5]

The designers state that NSA cryptanalysis found the algorithms to have no weaknesses, and security commensurate with their key lengths.[^o6] The design team says that their cryptanalysis included linear and differential cryptanalysis using standard techniques such as Matsui's algorithm and SAT/SMT solvers, though a full list of techniques used is not given.[^o25] Speck's designers have been criticized for not providing more details on NSA cryptanalysis of the ciphers.[^o29]

The NSA has approved Simon128/256 and Speck128/256 for use in U.S. National Security Systems, though AES-256 is still recommended for non-constrained applications.[^o31]

### [Side-channel attacks](https://en.wikipedia.org/wiki/Side-channel_attacks) {#Side-channel_attacks}

Being an [ARX cipher](wikipedia://en/4594#ARX_%28add–rotate–XOR%29), Speck does not use [S-boxes](wikipedia://en/240991) or other lookup tables; it is therefore naturally immune to [cache-timing attacks](wikipedia://en/481813).[^o6] This contrasts with ciphers that use lookup tables such as [AES](wikipedia://en/1260), which have been shown to be vulnerable to such attacks. However, like most block ciphers (including AES) Speck is vulnerable to [power analysis](wikipedia://en/754362) attacks unless hardware countermeasures are taken.[^o33][^o6]

### Block and key sizes {#Block_and_key_sizes}

Although the Speck family of ciphers includes variants with the same block and key sizes as [AES](wikipedia://en/1260) (Speck128/128, Speck128/192, and Speck128/256), it also includes variants with block size as low as 32 bits and key size as low as 64 bits. These small block and key sizes are insecure for general use, as they can allow [birthday attacks](wikipedia://en/189369) and [brute-force attacks](wikipedia://en/53784), regardless of the formal security of the cipher.[^o35] The designers state that these block and key sizes were included for highly resource-constrained devices where nothing better is possible, or where only very small amounts of data are ever encrypted, e.g. in [RFID](https://en.wikipedia.org/wiki/Radio-frequency_identification) protocols.[^o6] Only the variant with a 128-bit block size and 256-bit key size is approved for use in U.S. National Security Systems.[^o31]

## Standardization efforts and controversies {#Standardization_efforts_and_controversies}

Initial attempts to standardise [Simon](wikipedia://en/39994308) and Speck through the [International Organization for Standardization](https://en.wikipedia.org/wiki/International_Organization_for_Standardization) (ISO) failed to meet the required super-majority vote, and the ciphers were not adopted.[^o29] Expert delegates to the ISO from several countries including Germany, Japan and Israel opposed the NSA's efforts to standardise the ciphers, citing concerns that the NSA is pushing for their standardisation with knowledge of exploitable weaknesses in the ciphers.[^o37] The position was based on partial evidence of weaknesses in the ciphers, lack of clear need for standardisation of the new ciphers, and the NSA's previous involvement in the creation and promotion of the backdoored [Dual\_EC\_DRBG](wikipedia://en/14259066) cryptographic algorithm.[^o38]

In response to concerns, the NSA stated that more than 70 security analysis papers from some of the world's leading cryptographers support NSA's conclusion that the algorithms are secure and NSA affirmed that it is not aware of any cryptanalytic techniques that would allow them or anyone else to exploit Simon or Speck.[^o39]

After initial attempts to standardise the ciphers failed, the ISO standardised Simon and Speck in other working groups. As of October 2018, the Simon and Speck ciphers have been standardized by ISO as a part of the [RFID](https://en.wikipedia.org/wiki/RFID) air interface standard, ISO standard 29167-21 (for Simon)[^o40] and ISO standard 29167-22 (for Speck)[^o41], making them available for use by commercial entities.

On August 7, 2018, Speck was removed from the [Linux kernel](https://en.wikipedia.org/wiki/Linux_kernel) 4.20 release completely.[^o22]

On February 7, 2023 NIST selected the [Ascon](wikipedia://en/73283196) authenticated cipher family as its Lightweight Cryptography Standard.[^o42]
