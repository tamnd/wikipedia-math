# Powersort

::: {#o1 .subject cue=lead name="Powersort"}

**Powersort** is an adaptive sorting algorithm designed to optimally exploit existing order in the input data with minimal overhead. Powersort is the default list-sorting algorithm in [CPython](https://en.wikipedia.org/wiki/CPython) since version 3.11[^o3][^o4] and is also used in [NumPy](https://en.wikipedia.org/wiki/NumPy)[^o5], [PyPy](https://en.wikipedia.org/wiki/PyPy), [AssemblyScript](https://en.wikipedia.org/wiki/AssemblyScript)[^o6], and Apple's [WebKit](https://en.wikipedia.org/wiki/WebKit)[^o7]. Powersort belongs to the family of [merge sort](wikipedia://en/20039) algorithms. More specifically, Powersort builds on [Timsort](https://en.wikipedia.org/wiki/Timsort); it is a drop-in replacement for Timsort's suboptimal heuristic merge policy. Unlike Timsort, Powersort is derived from first principles (see connection to nearly [optimal binary search trees](https://en.wikipedia.org/wiki/Optimal_binary_search_tree)) and offers strong performance guarantees.

:::

Like Timsort, Powersort is [stable](wikipedia://en/28442#Stability) and [comparison-based](wikipedia://en/3189304). This property is essential for many applications.[^o8] Powersort was proposed by J. Ian Munro and Sebastian Wild.[^o9]

## Overview {#Overview}

*Image: Merge Tree Powersort.png.* A merge policy is an order to do binary merges (one pair of adjacent runs in each step) that eventually produces a big sorted list. It can always be represented by a binary tree. The merge cost of an execution is the sum of all produced runs.

Powersort is a stable mergesort variant that adapts to existing *runs* in the input data, i.e., ranges in the input that are already in order. It maintains a stack of runs yet to be merged and alternates between finding the next run and merging adjacent runs near the top of the run stack. This non-recursive mode of operation is particularly [cache-friendly](https://en.wikipedia.org/wiki/Locality_of_reference).

*Image: Powersort in Action.gif.* Powersort in action. The “power” of a run boundary corresponds to how deep the blue line can sink down, connecting the midpoints of the two runs, before it “hits” a node of the imaginary, green perfectly balanced binary search tree. Illustration from PyCon US 2023 talk by Sebastian Wild.[^o11]

Like Timsort, it enforces a minimal run length by “filling up” short runs using insertion sort up to a chosen minimal run length. Each merge step combines two adjacent runs into a single one using a “galloping strategy”: exponential search is used to find the prefix of one run that precedes the minimum in the other run. This can save comparisons compared to a traditional linear merge.

Powersort improves Timsort in terms of the *merge policy*, i.e., the rule(s) that decides which runs on the run stack are merged before proceeding. Timsort's original policy used a suboptimal heuristic based solely on the lengths of runs; Powersort replaces this with a rule simulating Mehlhorn's algorithm for computing nearly optimal binary search trees with low overhead,[^o9] thereby achieving optimal adaptivity up to an additive linear term.

The pseudocode below shows a simplified Powersort implementation.

**algorithm** *PowerSort*(A\[0..n)) S := stack of runs // capacity ⌈lg(n)⌉ + 1 b<sub>1</sub> := 0; e<sub>1</sub> := *FirstRunOf*(A\[b<sub>1</sub>..n)) // A\[b<sub>1</sub>..e<sub>1</sub>) is leftmost run **while** e<sub>1</sub> \< n b<sub>2</sub> := e<sub>1</sub> + 1; e<sub>2</sub> := FirstRunOf(A\[b<sub>2</sub>..n)) // A\[b<sub>2</sub>..e<sub>2</sub>) next run P := *NodePower*(n, b<sub>1</sub>, e<sub>1</sub>, b<sub>2</sub>, e<sub>2</sub>) **while** S.top().power > P (b<sub>1</sub>, e<sub>1</sub>) := *Merge*(S.pop(), A\[b<sub>1</sub>..e<sub>1</sub>)) **end while** S.push((A\[b<sub>1</sub>, e<sub>1</sub>), P)); b<sub>1</sub> := b<sub>2</sub>; e<sub>1</sub> := e<sub>2</sub> **end while** // Now A\[b<sub>1</sub>..e<sub>1</sub>) is the rightmost run **while** ¬S.empty() (b<sub>1</sub>, e<sub>1</sub>) := *Merge*(S.pop(), A\[b<sub>1</sub>..e<sub>1</sub>)) **end while**

**algorithm** *NodePower*(n, b<sub>1</sub>, e<sub>1</sub>, b<sub>2</sub>, e<sub>2</sub>) n<sub>1</sub> := e<sub>1</sub> − b<sub>1</sub>; n<sub>2</sub> := e<sub>2</sub> − b<sub>2</sub>; a := (b<sub>1</sub> + n<sub>1</sub>/2)/n; b := (b<sub>2</sub> + n<sub>2</sub>/2)/n p := 0 **while** ⌊a · 2<sup>p</sup>⌋ == ⌊b · 2<sup>p</sup>⌋ p := p + 1 **end while** **return** p

The implementation of *Merge* is inherited from TimSort and includes the "galloping" heuristic.

## Adoption {#Adoption}

The implementation of Powersort in [CPython](https://en.wikipedia.org/wiki/CPython) began with version 3.11, replacing the older Timsort algorithm. The change was motivated by Powersort's superior performance and stability. The core implementation can be found in the CPython source code within the listobject.c file, where the list-sorting functions are defined. The detailed merge policies and algorithm are described in listsort.txt...[^o13][^o14] The transition to Powersort involved addressing issue #78742 in the CPython repository.[^o15]

The [PyPy](https://en.wikipedia.org/wiki/PyPy) project, known for its high-performance Just-In-Time (JIT) compiler for Python, also integrated Powersort. The relevant commit, identified as `6d2f7a78baa8d4d2f94f5fb709f697a560b45f4e`, details the inclusion of Powersort into PyPy's list-sorting functions.[^o16]

In [AssemblyScript](https://en.wikipedia.org/wiki/AssemblyScript), Powersort was integrated to enhance the performance of WebAssembly applications. The relevant pull request, #1904, and the implementation details can be found in the sort.ts file within the AssemblyScript standard library.[^o17][^o18] These implementations across different platforms highlight the adaptability and efficiency of Powersort in various programming environments.

## Comparison with Timsort {#Comparison_with_Timsort}

Timsort's original merge policy caused several problems before being replaced by Powersort.

First, as accidentally observed during the [formal verification of Timsort](https://en.wikipedia.org/wiki/Timsort#Formal_verification), Tim Peters's original formulation did not guarantee the desired height bound for the run stack, leaving both CPython and OpenJDK vulnerable to a [stack overflow](https://en.wikipedia.org/wiki/Stack_overflow). This was eventually fixed by adding a fourth rule to Timsort but required two major patches of OpenJDK.[^o24] While eventually successful, the correctness proof of Timsort's stack height and the run-time analysis are very complicated.

Further, it was discovered that Timsort's merge policy also has a performance blind spot: specific patterns of run lengths cause Timsort to repeatedly perform very unbalanced merges, resulting in asymptotically 50% overhead.[^o25]

Powersort simultaneously removes all of these limitations. Despite its advanced theoretical foundation, its analysis is much easier,[^o27] and it provably never uses more than $n\mathcal{H} +O(n)$ comparisons, where $\mathcal{H} = \sum_{i=1}^{r} \frac{\ell_i}{n} \log_2\left({\frac n{\ell_i}}\right)$, for $\ell_1,\ldots,\ell_r$ the lengths of the runs in the input.

Powersort has been shown to outperform Timsort by up to 30% on certain types of input data that contain long runs of sorted elements.[^o9] Powersort has further been extended to multiway merging, something that was not possible with Timsort.

## Multiway Powersort {#Multiway_Powersort}

*Image: Merge Tree Example for Powersort and Multiway Powersort.png.* Example merge tree for Powersort (top) and 4- way Powersort (bottom) for an input of size n = 16.

Multiway Powersort[^o27] is an extension of Powersort that generalizes the binary merging process to *k*-way merging. This approach can reduce the number of merge operations and hence reduces the amount of memory transfer. It was proposed by William Cawley Gelling, Markus E. Nebel, Benjamin Smith, and Sebastian Wild in 2023.

Multiway Powersort retains the stability and adaptiveness of the original Powersort algorithm,[^o27] and is just as easy to analyze.

The key differences to normal Powersort are:

- The computation of powers uses the basis *k* instead of 2.
- When merging runs, we have to pop *all* runs from the stack that are tied in power with the topmost run.

Details are shown in the pseudocode below.

**algorithms** *k-wayPowerSort*(A\[0..n)) S := empty stack // capacity (k − 1)⌈log<sub>k</sub>(n) + 1⌉ b<sub>1</sub> := 0; e<sub>1</sub> = *FirstRunOf*(A\[b<sub>\1..n</sub>)) **while** e<sub>1</sub> \< n b<sub>2</sub> := e<sub>1</sub>; e<sub>2</sub> := *FirstRunOf*(A\[b<sub>\2..n</sub>)) P := *Power<sub>k</sub>*(n, b<sub>1</sub>, e<sub>1</sub>, b<sub>2</sub>, e<sub>2</sub>) **while** S.top().power > P P':= S.top().power L := empty list; L.append(S.pop()) **while** S.top().power == P′ L.append(S.pop()) **end while** // merge runs in L with A\[b<sub>1</sub>..e<sub>1</sub>) (b<sub>1</sub>, e<sub>1</sub>) := *Merge*(L, A\[b<sub>1</sub>..e<sub>1</sub>)) **end while** S.push((A\[b<sub>1</sub>, e<sub>1</sub>), P)) b<sub>1</sub> := b<sub>2</sub>; e<sub>1</sub> := e<sub>2</sub> **end while** // Now A\[b<sub>1</sub>..e<sub>1</sub>) is the rightmost run **while** ¬S.empty() // pop (up to) k − 1 runs, merge with A\[b<sub>1</sub>..e<sub>1</sub>) (b<sub>1</sub>, e<sub>1</sub>) := *Merge*(S.pop(k − 1), A\[b<sub>1</sub>..e<sub>1</sub>)) **end while**

**algorithm** *Power<sub>k</sub>*(n, b<sub>1</sub>, e<sub>1</sub>, b<sub>2</sub>, e<sub>2</sub>) n<sub>1</sub> := e<sub>1</sub> − b<sub>1</sub>; n<sub>2</sub> := e<sub>2</sub> − b<sub>2</sub>; p := 0 a := (b<sub>1</sub> + n<sub>1</sub>/2)/n; b := (b<sub>2</sub> + n<sub>2</sub>/2)/n **while** ⌊a · k<sup>p</sup>⌋ == ⌊b · k<sup>p</sup>⌋ p := p + 1 **end while** **return** p
