# Opportunistic encryption

::: {#o1 .subject cue=lead name="Opportunistic encryption"}

**Opportunistic encryption** (**OE**) refers to any [system](https://en.wikipedia.org/wiki/Computer) that, when connecting to another system, attempts to [encrypt](wikipedia://en/10294) [communications channels](wikipedia://en/156700), otherwise falling back to unencrypted communications. This method requires no pre-arrangement between the two systems.

:::

Opportunistic encryption can be used to combat [passive wiretapping](https://en.wikipedia.org/wiki/Telephone_tapping).[^o2] (an *active* wiretapper, on the other hand, can disrupt encryption negotiation to either force an unencrypted channel or perform a [man-in-the-middle attack](wikipedia://en/144676) on the encrypted link.) It does not provide a strong level of [security](https://en.wikipedia.org/wiki/Computer_security) as authentication may be difficult to establish and secure communications are not mandatory. However, it does make the encryption of most [Internet traffic](https://en.wikipedia.org/wiki/Internet_traffic) easy to implement, which removes a significant impediment to the mass adoption of Internet traffic security.

Opportunistic encryption on the Internet is described in 4322 "Opportunistic Encryption using the Internet Key Exchange (IKE)", 7435 "Opportunistic Security: Some Protection Most of the Time", and in 8164 "Opportunistic Security for HTTP/2".

## Routers {#Routers}

The [FreeS/WAN](wikipedia://en/1658979) project was one of the early proponents of OE.[^o4] The effort is continued by the former freeswan developers now working on [Libreswan](https://en.wikipedia.org/wiki/Libreswan). Libreswan aims to support different authentication hooks for opportunistic encryption with [IPsec](https://en.wikipedia.org/wiki/IPsec). Version 3.16, which was released in December 2015, had support for Opportunistic IPsec using AUTH-NULL[^o5] which is based on [RFC 7619](https://datatracker.ietf.org/doc/html/rfc7619). The Libreswan Project is currently working on (forward) [Domain Name System Security Extensions](https://en.wikipedia.org/wiki/Domain_Name_System_Security_Extensions) (DNSSEC) and [Kerberos](wikipedia://en/16947) support for Opportunistic IPsec.

[Openswan](https://en.wikipedia.org/wiki/Openswan) has also been ported to the [OpenWrt](https://en.wikipedia.org/wiki/OpenWrt) project.[^o6] Openswan used reverse [DNS](https://en.wikipedia.org/wiki/Domain_name_system) records to facilitate the key exchange between the systems.

It is possible to use [OpenVPN](wikipedia://en/858492) and networking protocols to set up dynamic VPN links which act similar to OE for specific domains.[^o7]

## Linux and Unix-like systems {#Linux_and_Unix-like_systems}

The FreeS/WAN and forks such as Openswan and [strongSwan](https://en.wikipedia.org/wiki/StrongSwan) offer VPNs that can also operate in OE mode using IPsec-based technology. [Obfuscated TCP](https://en.wikipedia.org/wiki/Obfuscated_TCP) is another method of implementing OE.

## Windows OS {#Windows_OS}

[Microsoft Windows](https://en.wikipedia.org/wiki/Microsoft_Windows) platforms have an implementation of OE installed by default. This method uses IPsec to secure the traffic and is a simple procedure to turn on. It is accessed via the [MMC](https://en.wikipedia.org/wiki/Microsoft_Management_Console) and "IP Security Policies on Local Computer" and then editing the properties to assign the "(Request Security)" policy.[^o10] This will turn on optional IPsec in a Kerberos environment. Many systems also have problems when either side is behind a [NAT](https://en.wikipedia.org/wiki/Network_Address_Translation). This problem is addressed by [NAT traversal](https://en.wikipedia.org/wiki/NAT_traversal) (NAT-T) and is accomplished by editing a [registry](https://en.wikipedia.org/wiki/Windows_Registry) item.[^o11] Using the filtering options provided in MMC, it is possible to tailor the networking to require, request or permit traffic to various domains and protocols to use encryption.

## Email {#Email}

Opportunistic encryption can also be used for specific traffic like [e-mail](https://en.wikipedia.org/wiki/E-mail) using the [SMTP](https://en.wikipedia.org/wiki/SMTP) [STARTTLS](https://en.wikipedia.org/wiki/STARTTLS) extension for relaying messages across the Internet, or the [Internet Message Access Protocol](https://en.wikipedia.org/wiki/Internet_Message_Access_Protocol) (IMAP) STARTTLS extension for reading e-mail. With this implementation, it is not necessary to obtain a certificate from a [certificate authority](wikipedia://en/296370), as a [self-signed certificate](wikipedia://en/642850) can be used.

- 2595 Using TLS with IMAP, POP3 and ACAP
- 3207 SMTP Service Extension for Secure SMTP over TLS
- [STARTTLS and postfix](http://www.postfix.org/TLS_README.html#server_tls)
- [STARTTLS and Exchange](http://support.microsoft.com/default.aspx?scid=kb;en-us;829721)

Many systems employ a variant with third-party add-ons to traditional email packages by first attempting to obtain an encryption key and if unsuccessful, then sending the email in the clear. [PGP](wikipedia://en/23080), [p≡p](wikipedia://en/47794277), [Hushmail](https://en.wikipedia.org/wiki/Hushmail), and Ciphire, among others can all be set up to work in this mode.

In practice, STARTTLS in SMTP is often deployed with self-signed certificates,[^o13] which represents a minimal one-time task for a system administrator, and results in most email traffic being opportunistically encrypted.[^o14]

## VoIP {#VoIP}

Some [Voice over IP](https://en.wikipedia.org/wiki/Voice_over_IP) (VoIP) solutions provide for painless encryption of voice traffic when possible. Some versions of the [Sipura Technology](https://en.wikipedia.org/wiki/Sipura_Technology) and [Linksys](https://en.wikipedia.org/wiki/Linksys) lines of [analog telephony adapters](https://en.wikipedia.org/wiki/Analog_telephony_adapter) (ATA) include a hardware implementation of [SRTP](https://en.wikipedia.org/wiki/Secure_Real-time_Transport_Protocol) with the installation of a certificate from Voxilla, a VoIP information site. When the call is placed an attempt is made to use SRTP; if successful a series of tones is played into the handset; if not the call proceeds without using encryption. [Skype](https://en.wikipedia.org/wiki/Skype) and [Amicima](https://en.wikipedia.org/wiki/Amicima) use only secure connections and [Gizmo5](https://en.wikipedia.org/wiki/Gizmo5) attempts a secure connection between its clients. [Phil Zimmermann](wikipedia://en/23486), Alan Johnston, and [Jon Callas](https://en.wikipedia.org/wiki/Jon_Callas) have proposed a new VoIP encryption protocol called [ZRTP](https://en.wikipedia.org/wiki/ZRTP).[^o16] They have an implementation of it called [Zfone](https://en.wikipedia.org/wiki/Zfone) whose source and compiled binaries are available.

## Websites {#Websites}

For encrypting [WWW](https://en.wikipedia.org/wiki/WWW)/[HTTP](https://en.wikipedia.org/wiki/HTTP) connections, [HTTPS](wikipedia://en/13586) is typically used, which requires strict encryption and has significant administrative costs, both in terms of initial setup and continued maintenance costs for the [website](https://en.wikipedia.org/wiki/Website) operator. Most browsers verify the [webserver](https://en.wikipedia.org/wiki/Webserver)'s identity to make sure that an [SSL certificate](https://en.wikipedia.org/wiki/SSL_certificate) is signed by a trusted [certificate authority](wikipedia://en/296370) and has not expired, usually requiring the website operator to manually change the certificate every one or two years. The easiest way to enable some sort of opportunistic website encryption is by using self-signed certificates, but this causes [browsers](https://en.wikipedia.org/wiki/Web_browser) to display a warning each time the website is visited unless the user manually marks the website's certificate as trusted. Because unencrypted websites do not currently display any such warnings, the use of self-signed certificates is not well received.

In 2015, [Mozilla](https://en.wikipedia.org/wiki/Mozilla) started to roll out opportunistic encryption in [Firefox](https://en.wikipedia.org/wiki/Firefox) version 37.[^o18] This was quickly rolled back (in update 37.0.1) due to a serious [vulnerability](https://en.wikipedia.org/wiki/Vulnerability_%28computing%29) that could bypass [SSL certificate](https://en.wikipedia.org/wiki/SSL_certificate) verification.[^o19]

Browser extensions like [HTTPS Everywhere](https://en.wikipedia.org/wiki/HTTPS_Everywhere) and HTTPSfinder[^o20] find and automatically switch the connection to HTTPS when possible.

Several proposals were available for true, seamless opportunistic encryption of [HTTP/2](https://en.wikipedia.org/wiki/HTTP/2) protocol.[^o21] These proposals were later rejected. [Poul-Henning Kamp](https://en.wikipedia.org/wiki/Poul-Henning_Kamp), lead developer of [Varnish](https://en.wikipedia.org/wiki/Varnish_%28software%29) and a senior [FreeBSD](https://en.wikipedia.org/wiki/FreeBSD) kernel developer, has criticized the [IETF](https://en.wikipedia.org/wiki/IETF) for following a particular [political agenda](https://en.wikipedia.org/wiki/Political_agenda) with HTTP/2 for not implementing opportunistic encryption in the standard.[^o22][^o23]

## Weaknesses {#Weaknesses}

[STARTTLS](https://en.wikipedia.org/wiki/STARTTLS) implementations often used with [SMTP](https://en.wikipedia.org/wiki/SMTP) are vulnerable to [STRIPTLS](https://en.wikipedia.org/wiki/STRIPTLS) attacks when subject to [active wiretapping](https://en.wikipedia.org/wiki/Active_wiretapping).
