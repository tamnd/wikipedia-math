# HTTP Public Key Pinning

::: {#o1 .subject cue=lead name="HTTP Public Key Pinning"}

**HTTP Public Key Pinning** (**HPKP**) is an obsolete [Internet security](https://en.wikipedia.org/wiki/Internet_security) mechanism delivered via an [HTTP](https://en.wikipedia.org/wiki/Hypertext_Transfer_Protocol) [header](https://en.wikipedia.org/wiki/Header_%28computing%29) which allows [HTTPS](wikipedia://en/13586) websites to resist [impersonation](https://en.wikipedia.org/wiki/Impersonation) by attackers using misissued or otherwise fraudulent [digital certificates](wikipedia://en/223796).[^o2] A server uses it to deliver to the [client](https://en.wikipedia.org/wiki/Client_%28computing%29) (e.g. a [web browser](https://en.wikipedia.org/wiki/Web_browser)) a set of hashes of [public keys](https://en.wikipedia.org/wiki/Public_key) that must appear in the certificate chain of future connections to the same [domain name](https://en.wikipedia.org/wiki/Domain_name).

:::

For example, attackers might compromise a [certificate authority](wikipedia://en/296370), and then mis-issue certificates for a [web origin](https://en.wikipedia.org/wiki/Same-origin_policy). To combat this risk, the HTTPS web server serves a list of “pinned” public key hashes valid for a given time; on subsequent connections, during that validity time, clients expect the server to use one or more of those public keys in its certificate chain. If it does not, an error message is shown, which cannot be (easily) bypassed by the user.

The technique does not pin certificates, but [public key](https://en.wikipedia.org/wiki/Public_key) hashes. This means that one can use the [key pair](wikipedia://en/24222) to get a certificate from any certificate authority, when one has access to the private key. Also the user can pin public keys of [root](wikipedia://en/296362) or [intermediate certificates](https://en.wikipedia.org/wiki/Intermediate_certificate_authorities) (created by certificate authorities), restricting site to certificates issued by the said certificate authority.

Due to HPKP mechanism complexity and possibility of accidental misuse (potentially causing a lockout condition by system administrators), in 2017 browsers deprecated HPKP and in 2018 removed its support in favor of [Certificate Transparency](wikipedia://en/41061790).[^o3][^o4]

## Mechanism {#Mechanism}

The server communicates the HPKP policy to the user agent via an [HTTP](https://en.wikipedia.org/wiki/HTTP) response header field named `Public-Key-Pins` (or `Public-Key-Pins-Report-Only` for reporting-only purposes).

The HPKP policy specifies [hashes](wikipedia://en/439526) of the subject public key info of one of the certificates in the website's authentic X.509 [public key certificate](wikipedia://en/223796) chain (and at least one backup key) in `pin-sha256` directives, and a period of time during which the user agent shall enforce public key pinning in `max-age` directive, optional `includeSubDomains` directive to include all subdomains (of the domain that sent the header) in pinning policy and optional `report-uri` directive with URL where to send pinning violation reports. At least one of the public keys of the certificates in the certificate chain needs to match a pinned public key in order for the chain to be considered valid by the user agent.

At the time of publishing, 7469 only allowed the [SHA-256](wikipedia://en/1638777) hash algorithm. ([Appendix A. of RFC 7469](https://tools.ietf.org/html/rfc7469#appendix-A) mentions some tools and required arguments that can be used to produce hashes for HPKP policies.)

A website operator can choose to either pin the [root certificate](wikipedia://en/296362) public key of a particular root certificate authority, allowing only that certificate authority (and all intermediate authorities signed by its key) to issue valid certificates for the website's domain, and/or to pin the key(s) of one or more intermediate issuing certificates, or to pin the end-entity public key.

At least one backup key must be pinned, in case the current pinned key needs to be replaced. The HPKP is not valid without this backup key (a backup key is defined as a public key not present in the current certificate chain).[^o6]

HPKP is standardized in [RFC](https://en.wikipedia.org/wiki/Request_for_Comments) 7469.[^o2] It expands on static [certificate pinning](https://en.wikipedia.org/wiki/Certificate_pinning), which hardcodes public key hashes of well-known websites or services within web browsers and applications.[^o7]

Most browsers disable pinning for [certificate chains](wikipedia://en/223796) with private [root certificates](wikipedia://en/296362) to enable various corporate [content inspection](https://en.wikipedia.org/wiki/Deep_content_inspection) scanners[^o8] and web debugging tools (such as [mitmproxy](https://en.wikipedia.org/wiki/Mitmproxy) or [Fiddler](https://en.wikipedia.org/wiki/Fiddler_%28software%29)). The RFC 7469 standard recommends disabling pinning violation reports for "user-defined" root certificates, where it is "acceptable" for the browser to disable pin validation.[^o9]

## Reporting {#Reporting}

If the user agent performs pin validation and fails to find a valid SPKI fingerprint in the served certificate chain, it will POST a JSON formatted violation report to the host specified in the report-uri directive containing details of the violation. This URI may be served via [HTTP](https://en.wikipedia.org/wiki/HTTP) or [HTTPS](wikipedia://en/13586); however, the user agent cannot send HPKP violation reports to an HTTPS URI in the same domain as the domain for which it is reporting the violation. Hosts may either use HTTP for the `report-uri`, use an alternative domain, or use a reporting service.[^o11]

Some browsers also support the `Public-Key-Pins-Report-Only`, which only triggers this reporting while not showing an error to the user.

## Criticism and decline {#Criticism_and_decline}

During its peak adoption, HPKP was reported to be used by 3,500 of top 1 million internet sites, a figure that declined to 650 around the end of 2019.[^o13]

Criticism and concern revolved around malicious or human error scenarios known as HPKP Suicide and RansomPKP.[^o14][^o15] In such scenarios, a website owner would have their ability to publish new contents to their domain severely hampered by either losing access to their own keys or having new keys announced by a malicious attacker.
