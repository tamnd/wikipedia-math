# Concrete security

::: {#o1 .subject cue=lead name="Concrete security"}

In [cryptography](wikipedia://en/18934432), **concrete security** or **exact security** is a [practice-oriented approach](wikipedia://en/1182348#Practice-oriented_provable_security) that aims to give more precise estimates of the computational power and time of the [attackers](wikipedia://en/789126) tasks than [asymptotic security](wikipedia://en/159695) would allow.[^o2] It quantifies the security of a cryptosystem by bounding the [probability](wikipedia://en/22934) of success for an adversary running for a fixed amount of time.[^o3] [Security proofs](https://en.wikipedia.org/wiki/Security_proof) with precise analyses are referred to as *concrete*.[^o4]

:::

Traditionally, [provable security](wikipedia://en/1182348) is **asymptotic**: it classifies the hardness of computational problems using polynomial-time reducibility. Secure schemes are defined to be those in which the advantage of any [computationally bounded adversary](wikipedia://en/39275268) is [negligible](https://en.wikipedia.org/wiki/Negligible_function_%28cryptography%29). While such a theoretical guarantee is important, in practice one needs to know exactly how efficient a reduction is because of the need to instantiate the [security parameter](wikipedia://en/2290431) - it is not enough to know that "sufficiently large" security parameters will do. An inefficient reduction results either in the success probability for the adversary or the resource requirement of the scheme being greater than desired.

Concrete security parametrizes all the resources available to the adversary, such as running time and memory, and other resources specific to the system in question, such as the number of plaintexts it can obtain or the number of queries it can make to any [oracles](wikipedia://en/40705185) available. Then the advantage of the adversary is upper bounded as a function of these resources and of the problem size. It is often possible to give a lower bound (i.e. an adversarial strategy) matching the upper bound, hence the name exact security.

## Examples {#Examples}

Concrete security estimates have been applied to cryptographic algorithms:

- In 1996, schemes for [digital signatures](wikipedia://en/59644) based on the [RSA](https://en.wikipedia.org/wiki/RSA_%28cryptosystem%29) and [Rabin](https://en.wikipedia.org/wiki/Rabin_signature) cryptosystems were proposed, which were shown to be approximately as difficult to break as the original cryptosystems.[^o7]
- In 1997, some notions of concrete security (*left-or-right indistinguishability*, *real-or-random indistinguishability*, *find-then-guess security*, and *semantic-security*) for [symmetric encryption](https://en.wikipedia.org/wiki/Symmetric_encryption) algorithms were proved approximately equivalent in various [block cipher modes of operation](wikipedia://en/160202) such as CBC, CTR, and XOR (a stateless variant of CBC).[^o8]
- In 2017, a thesis showed that lattice point enumeration and lattice block reduction algorithms could be used to attack [lattice-based cryptography](wikipedia://en/18657553).[^o9]
- In 2021, "guess-and-determine" and "guess-and-decode"-type attacks were demonstrated against a proposed [pseudorandom generator](wikipedia://en/1812809) in [NC0](https://en.wikipedia.org/wiki/NC0), where instances with parameter values previously claimed to have 128-bit security were solved in about $2^{78}$ operations.[^o10]

In addition, a software tool named the "Foundational Cryptography Framework", which embeds into [Rocq](wikipedia://en/581974), is able to [formally verify](https://en.wikipedia.org/wiki/Formal_verification) proofs of concrete security.[^o11] For example, it is able to verify the concrete security of [ElGamal encryption](wikipedia://en/59458).[^o11]
