# Optimal asymmetric encryption padding

::: {#o1 .subject cue=lead name="Optimal asymmetric encryption padding"}

In [cryptography](wikipedia://en/18934432), **optimal asymmetric encryption padding** (**OAEP**) is a [padding scheme](wikipedia://en/592505) often used together with [RSA encryption](https://en.wikipedia.org/wiki/RSA_%28cryptosystem%29). OAEP was introduced by [Bellare](https://en.wikipedia.org/wiki/Mihir_Bellare) and [Rogaway](https://en.wikipedia.org/wiki/Phillip_Rogaway),[^o2] and subsequently standardized in [PKCS #1 v2](https://en.wikipedia.org/wiki/PKCS1) and RFC 2437.

:::

The OAEP algorithm is a form of [Feistel network](https://en.wikipedia.org/wiki/Feistel_network) which uses a pair of [random oracles](wikipedia://en/451286) G and H to process the plaintext prior to [asymmetric encryption](https://en.wikipedia.org/wiki/Asymmetric_encryption). When combined with any secure [trapdoor one-way permutation](https://en.wikipedia.org/wiki/Trapdoor_one-way_function) $f$, this processing is proved in the [random oracle model](https://en.wikipedia.org/wiki/Random_oracle_model) to result in a combined scheme which is [semantically secure](wikipedia://en/960585) under [chosen-plaintext attack](wikipedia://en/63852) [(IND-CPA)](wikipedia://en/2187252). When implemented with certain trapdoor permutations (e.g., RSA), OAEP is also proven to be secure against chosen-ciphertext attack. OAEP can be used to build an [all-or-nothing transform](wikipedia://en/2420120).

OAEP satisfies the following two goals:

1. Add an element of randomness which can be used to convert a [deterministic encryption](wikipedia://en/2343703) scheme (e.g., traditional [RSA](https://en.wikipedia.org/wiki/RSA_%28algorithm%29)) into a [probabilistic](wikipedia://en/1051442) scheme.
1. Prevent partial decryption of ciphertexts (or other information leakage) by ensuring that an adversary cannot recover any portion of the plaintext without being able to invert the trapdoor one-way permutation $f$.

The original version of OAEP (Bellare/Rogaway, 1994) showed a form of "[plaintext awareness](wikipedia://en/3790487)" (which they claimed implies security against [chosen-ciphertext attack](wikipedia://en/103586)) in the random oracle model when OAEP is used with any trapdoor permutation. Subsequent results contradicted this claim, showing that OAEP was only [IND-CCA1](https://en.wikipedia.org/wiki/IND-CCA1) secure. However, the original scheme was proved in the [random oracle model](https://en.wikipedia.org/wiki/Random_oracle_model) to be [IND-CCA2](https://en.wikipedia.org/wiki/IND-CCA2) secure when OAEP is used with the RSA permutation using standard encryption exponents, as in the case of RSA-OAEP.[^o3] An improved scheme (called OAEP+) that works with any trapdoor one-way permutation was offered by [Victor Shoup](wikipedia://en/3978418) to solve this problem.[^o4] More recent work has shown that in the [standard model](wikipedia://en/4488342) (that is, when hash functions are not modeled as random oracles) it is impossible to prove the IND-CCA2 security of RSA-OAEP under the assumed hardness of the [RSA problem](wikipedia://en/1544741).[^o5][^o6]

## Algorithm {#Algorithm}

*Image: OAEP encoding schema.svg.* OAEP encoding schema according to RFC 8017

In the diagram,

- *MGF* is the [mask generating function](wikipedia://en/53230626), usually MGF1,
- *Hash* is the chosen [hash function](wikipedia://en/439526),
- *hLen* is the length of the output of the hash function in bytes,
- *k* is the length of the [RSA](https://en.wikipedia.org/wiki/RSA_%28cryptosystem%29) modulus *n* in bytes,
- *M* is the message to be padded, with length *mLen* (at most $\mathrm{mLen}= k - 2 \cdot \mathrm{hLen} - 2$ bytes),
- *L* is an optional label to be associated with the message (the label is the empty string by default and can be used to authenticate data without requiring encryption),
- *PS* is a byte string of $k - \mathrm{mLen} - 2 \cdot \mathrm{hLen} - 2$ null-bytes.
- ⊕ is an [XOR](wikipedia://en/105979)-Operation.

### Encoding {#Encoding}

RFC 8017[^o10] for PKCS#1 v2.2 specifies the OAEP scheme as follows for encoding:

1. Hash the label *L* using the chosen hash function: $\mathrm{lHash} = \mathrm{Hash}(L)$
1. Generate a padding string *PS* consisting of $k - \mathrm{mLen} - 2 \cdot \mathrm{hLen} - 2$ bytes (0x00 and 0x01).
1. Concatenate *lHash*, *PS*, the single byte 0x01, and the message *M* to form a data block *DB*: $\mathrm{DB} = \mathrm{lHash} || \mathrm{PS} || \mathrm{0x01} || \mathrm{M}$. This data block has length $k - \mathrm{hLen} - 1$ bytes.
1. Generate a random seed of length *hLen*.
1. Use the mask generating function to generate a mask of the appropriate length for the data block: $\mathrm{dbMask} = \mathrm{MGF}(\mathrm{seed}, k - \mathrm{hLen} - 1)$
1. Mask the data block with the generated mask: $\mathrm{maskedDB} = \mathrm{DB} \oplus \mathrm{dbMask}$
1. Use the mask generating function to generate a mask of length *hLen* for the seed: $\mathrm{seedMask} = \mathrm{MGF}(\mathrm{maskedDB}, \mathrm{hLen})$
1. Mask the seed with the generated mask: $\mathrm{maskedSeed} = \mathrm{seed} \oplus \mathrm{seedMask}$
1. The encoded (padded) message is the byte 0x00 concatenated with the *maskedSeed* and *maskedDB*: $\mathrm{EM} = \mathrm{0x00} || \mathrm{maskedSeed} || \mathrm{maskedDB}$

### Decoding {#Decoding}

Decoding works by reversing the steps taken in the encoding algorithm:

1. Hash the label *L* using the chosen hash function: $\mathrm{lHash} = \mathrm{Hash}(L)$
1. To reverse step 9, split the encoded message *EM* into the byte 0x00, the *maskedSeed* (with length *hLen*) and the *maskedDB*: $\mathrm{EM} = \mathrm{0x00} || \mathrm{maskedSeed} || \mathrm{maskedDB}$
1. Generate the *seedMask* which was used to mask the *seed*: $\mathrm{seedMask} = \mathrm{MGF}(\mathrm{maskedDB}, \mathrm{hLen})$
1. To reverse step 8, recover the *seed* with the *seedMask*: $\mathrm{seed} = \mathrm{maskedSeed} \oplus \mathrm{seedMask}$
1. Generate the *dbMask* which was used to mask the data block: $\mathrm{dbMask} = \mathrm{MGF}(\mathrm{seed}, k - \mathrm{hLen} - 1)$
1. To reverse step 6, recover the data block *DB:* $\mathrm{DB} = \mathrm{maskedDB} \oplus \mathrm{dbMask}$
1. To reverse step 3, split the data block into its parts: $\mathrm{DB} = \mathrm{lHash'} || \mathrm{PS} || \mathrm{0x01} || \mathrm{M}$.
   1. Verify that:
      - *lHash**is equal to the computed*****lHash**
      - *PS* only consists of bytes 0x00
      - *PS* and *M* are separated by the 0x01 byte and
      - the first byte of *EM* is the byte 0x00.
   1. If any of these conditions aren't met, then the padding is invalid.

Usage in RSA: The encoded message can then be encrypted with RSA. The deterministic property of RSA is now avoided by using the OAEP encoding because the *seed* is randomly generated and influences the entire encoded message.

### Security {#Security}

The "[all-or-nothing](wikipedia://en/2420120)" security is from the fact that to recover *M*, one must recover the entire *maskedDB* and the entire *maskedSeed*; *maskedDB* is required to recover the *seed* from the *maskedSeed*, and the *seed* is required to recover the data block *DB* from *maskedDB*. Since any changed bit of a cryptographic hash completely changes the result, the entire *maskedDB*, and the entire *maskedSeed* must both be completely recovered.

### Implementation {#Implementation}

In the PKCS#1 standard, the random oracles are identical. The PKCS#1 standard further requires that the random oracles be [MGF1](https://en.wikipedia.org/wiki/MGF1) with an appropriate hash function.[^o15]
