# Security of cryptographic hash functions

::: {#o1 .subject cue=lead name="Security of cryptographic hash functions"}

In [cryptography](wikipedia://en/18934432), [cryptographic hash functions](https://en.wikipedia.org/wiki/Cryptographic_hash_functions) can be divided into two main categories. In the first category are those functions whose designs are based on mathematical problems, and whose security thus follows from rigorous mathematical proofs, [complexity theory](wikipedia://en/7543) and [formal reduction](wikipedia://en/848067). These functions are called *provably secure cryptographic hash functions*. To construct these is very difficult, and few examples have been introduced. Their practical use is limited.

:::

In the second category are functions which are not based on mathematical problems, but on an ad-hoc constructions, in which the bits of the message are mixed to produce the hash. These are then believed to be hard to break, but no formal proof is given. Almost all hash functions in widespread use reside in this category. Some of these functions are already broken, and are no longer in use. *See* [Hash function security summary](wikipedia://en/26774718).

## Types of security of hash functions {#Types_of_security_of_hash_functions}

Generally, the *basic* security of [cryptographic hash functions](https://en.wikipedia.org/wiki/Cryptographic_hash_functions) can be seen from different angles: pre-image resistance, second pre-image resistance, collision resistance, and pseudo-randomness.

- **Pre-image resistance**: given a hash $h$, it should be *hard* to find any message $m$ such that $h = \operatorname{hash}(m)$. This concept is related to that of the [one-way function](wikipedia://en/363890). Functions that lack this property are vulnerable to [pre-image attacks](https://en.wikipedia.org/wiki/Pre-image_attack).
- **Second pre-image resistance**: given an input $m_{1}$, it should be *hard* to find another input $m_{2} \ne m_{1}$ such that $\operatorname{hash}(m_{1}) = \operatorname{hash}(m_{2})$. This property is sometimes referred to as weak collision resistance. Functions that lack this property are vulnerable to [second pre-image attacks](https://en.wikipedia.org/wiki/Second_pre-image_attack).
- **Collision resistance**: it should be *hard* to find two different messages $m_{1}$ and $m_{2}$ such that $\operatorname{hash}(m_{1}) = \operatorname{hash}(m_{2})$. Such a pair is called a (cryptographic) hash collision. This property is sometimes referred to as strong collision resistance. It requires a hash value at least twice as long as what is required for pre-image resistance; otherwise, collisions may be found by a [birthday attack](wikipedia://en/189369).
- **Pseudo-randomness**: it should be *hard* to distinguish a pseudo-random number generator based on the hash function from true random number generator; for example, it passes usual [randomness tests](https://en.wikipedia.org/wiki/Randomness_tests).

### The meaning of *hard* {#The_meaning_of_hard}

The basic question is the meaning of *hard*. There are two approaches to answer this question. First is the intuitive/practical approach: "*hard* means that it is almost certainly beyond the reach of any adversary who must be prevented from breaking the system for as long as the security of the system is deemed important." The second approach is theoretical and is based on the [computational complexity theory](wikipedia://en/7543): if problem *A* is hard, then there exists a formal [security reduction](wikipedia://en/848067) from a problem which is widely considered unsolvable in [polynomial time](https://en.wikipedia.org/wiki/Polynomial_time), such as [integer factorization](wikipedia://en/15491) or the [discrete logarithm](wikipedia://en/181334) problem.

However, non-existence of a polynomial time algorithm does not automatically ensure that the system is secure. The difficulty of a problem also depends on its size. For example, [RSA public-key cryptography](https://en.wikipedia.org/wiki/RSA_public_key_cryptography) (which relies on the difficulty of [integer factorization](wikipedia://en/15491)) is considered secure only with keys that are at least 2048 bits long, whereas keys for the [ElGamal cryptosystem](wikipedia://en/59458) (which relies on the difficulty of the [discrete logarithm](wikipedia://en/181334) problem) are commonly in the range of 256–512 bits.

### Password case {#Password_case}

If the set of inputs to the hash is relatively small or is ordered by likelihood in some way, then a brute force search may be practical, regardless of theoretical security. The likelihood of recovering the preimage depends on the input set size and the speed or cost of computing the hash function. A common example is the use of hashes to store [password](wikipedia://en/24304) validation data. Rather than store the plaintext of user passwords, an access control system typically stores a hash of the password. When a person requests access, the password they submit is hashed and compared with the stored value. If the stored validation data is stolen, then the thief will only have the hash values, not the passwords. However, most users choose passwords in predictable ways, and passwords are often short enough so that all possible combinations can be tested if fast hashes are used.[^o5] Special hashes called [key derivation functions](wikipedia://en/449781) have been created to slow searches. *See* [Password cracking](wikipedia://en/477981).

## Cryptographic hash functions {#Cryptographic_hash_functions}

Most hash functions are built on an ad-hoc basis, where the bits of the message are nicely mixed to produce the hash. Various [bitwise operations](wikipedia://en/264399) (e.g. rotations), [modular additions](wikipedia://en/20087), and [compression functions](wikipedia://en/3851622) are used in iterative mode to ensure high complexity and pseudo-randomness of the output. In this way, the security is very hard to prove and the proof is usually not done. Only a few years ago, one of the most popular hash functions, [SHA-1](wikipedia://en/26672), was shown to be less secure than its length suggested: collisions could be found in only 2<sup>51</sup>[^o7] tests, rather than the brute-force number of 2<sup>80</sup>.

In other words, most of the hash functions in use nowadays are not provably collision-resistant. These hashes are not based on purely mathematical functions. This approach results generally in more effective hashing functions, but with the risk that a weakness of such a function will be eventually used to find collisions. One famous case is [MD5](wikipedia://en/18826).

## Provably secure hash functions {#Provably_secure_hash_functions}

In this approach, the security of a hash function is based on some hard mathematical problem, and it is proved that finding collisions of the hash function is as hard as breaking the underlying problem. This gives a somewhat stronger notion of security than just relying on complex mixing of bits as in the classical approach.

A cryptographic hash function has *provable security against collision attacks* if finding collisions is provably [polynomial-time reducible](wikipedia://en/159695) from a problem *P* which is supposed to be unsolvable in polynomial time. The function is then called provably secure, or just provable.

It means that if finding collisions would be feasible in polynomial time by algorithm *A*, then one could find and use polynomial time algorithm *R* (reduction algorithm) that would use algorithm *A* to solve problem *P*, which is widely supposed to be unsolvable in polynomial time. That is a contradiction. This means that finding collisions cannot be easier than solving *P*.

However, this only indicates that finding collisions is difficult in *some* cases, as not all instances of a computationally hard problem are typically hard. Indeed, very large instances of NP-hard problems are routinely solved, while only the hardest are practically impossible to solve.

### Hard problems {#Hard_problems}

Examples of problems that are assumed to be not solvable in polynomial time include

- [Discrete logarithm](wikipedia://en/181334)
- [Modular square roots](wikipedia://en/200091)
- [Integer factorization](wikipedia://en/15491)
- [Subset sum](wikipedia://en/36811)

### Downsides of the provable approach {#Downsides_of_the_provable_approach}

- Current collision-resistant hash algorithms that have provable security [reductions](wikipedia://en/848067) are too inefficient to be used in practice. In comparison to classical hash functions, they tend to be relatively slow and do not always meet all of criteria traditionally expected of cryptographic hashes. [Very smooth hash](wikipedia://en/24892363) is an example.
- Constructing a hash function with provable security is much more difficult than using a classical approach where one just hopes that the complex mixing of bits in the hashing algorithm is strong enough to prevent adversary from finding collisions.
- The proof is often a reduction to a problem with asymptotically hard [worst-case](https://en.wikipedia.org/wiki/Worst-case_complexity) or [average-case complexity](https://en.wikipedia.org/wiki/Average-case_complexity). Worst-case complexity measures the difficulty of solving pathological cases rather than typical cases of the underlying problem. Even a reduction to a problem with hard average-case complexity offers only limited security, as there still can be an algorithm that easily solves the problem for a subset of the problem space. For example, early versions of [Fast Syndrome Based Hash](https://en.wikipedia.org/wiki/Fast_Syndrome_Based_Hash) turned out to be insecure. This problem was solved in the latest version.

[SWIFFT](wikipedia://en/25702256) is an example of a hash function that circumvents these security problems. It can be shown that, for any algorithm that can break SWIFFT with probability $p$ within an estimated time $t$, one can find an algorithm that solves the *worst-case* scenario of a certain difficult mathematical problem within time $t'$ depending on $t$ and $p$.[^o12]

### Example of (impractical) provably secure hash function {#Example_of_(impractical)_provably_secure_hash_function}

Let $\operatorname{hash}(m) = x^{m} \bmod n$, where $n$ is a hard-to-factor composite number, and $x$ is some prespecified base value. A collision $x^{m_{1}} \equiv x^{m_{2}}\pmod{n}$ reveals a multiple $m_{1} - m_{2}$ of the [multiplicative order](wikipedia://en/344542) of $x$ modulo $n$. This information can be used to factor $n$ in polynomial time, assuming certain properties of $x$.

But the algorithm is quite inefficient because it requires on average 1.5 multiplications modulo $n$ per message-bit.

### More practical provably secure hash functions {#More_practical_provably_secure_hash_functions}

- [VSH](wikipedia://en/24892363)—Very Smooth Hash—a provably secure collision-resistant hash function assuming the hardness of finding nontrivial modular square roots modulo composite number $n$ (this is proven to be as hard as [factoring](wikipedia://en/15491) $n$).
- [MuHASH](https://en.wikipedia.org/wiki/MuHASH)
- [ECOH](wikipedia://en/25693976)—[Elliptic Curve Only hash function](wikipedia://en/25693976)—based on the concept of [elliptic curves](wikipedia://en/10225), the [subset sum problem](wikipedia://en/36811), and summation of polynomials. The security proof of the collision resistance was based on weakened assumptions, and eventually a second pre-image attack was found.
- [FSB](https://en.wikipedia.org/wiki/Fast_Syndrome_Based_Hash)—[Fast Syndrome-Based hash function](https://en.wikipedia.org/wiki/Fast_Syndrome_Based_Hash)—it can be proven that breaking FSB is at least as difficult as solving *regular syndrome decoding*, which is known to be NP-complete.
- [SWIFFT](wikipedia://en/25702256)—SWIFFT is based on the [fast Fourier transform](wikipedia://en/11512) and is provably collision resistant, under a relatively mild assumption about the worst-case difficulty of finding short vectors in cyclic/[ideal lattices](https://en.wikipedia.org/wiki/Ideal_lattice_cryptography).
- [Chaum, van Heijst, Pfitzmann hash function](https://en.wikipedia.org/wiki/Chaum,_van_Heijst,_Pfitzmann_hash_function)—a compression function where finding collisions is as hard as solving the [discrete logarithm problem](wikipedia://en/181334) in a finite group $F_{2p+1}$.
- [Knapsack-based hash functions](https://en.wikipedia.org/wiki/Knapsack-based_hash_functions)—a family of hash functions based on the [knapsack problem](wikipedia://en/16974).
- [The Zémor-Tillich hash function](https://en.wikipedia.org/wiki/The_Zémor-Tillich_hash_function)—a family of hash functions that relies on the arithmetic of the group of matrices [SL<sub>2</sub>](wikipedia://en/144823). Finding collisions is at least as difficult as finding factorization of certain elements in this group. This is supposed to be hard, at least [PSPACE-complete](wikipedia://en/54685). For this hash, an attack was eventually discovered with a time complexity close to $2^{n/2}$. This beat by far the birthday bound and ideal pre-image complexities, which are $2^{3n/2}$ and $2^{3n}$ for the Zémor-Tillich hash function. As the attacks include a birthday search in a reduced set of size $2n$, they indeed do not destroy the idea of provable security or invalidate the scheme but rather suggest that the initial parameters were too small.[^o15]
- [Hash functions from Sigma Protocols](https://en.wikipedia.org/wiki/Hash_functions_from_Sigma_Protocols)—there exists a general way of constructing a provably secure hash, specifically from any (suitable) [sigma protocol](https://en.wikipedia.org/wiki/Proof_of_knowledge#Sigma_protocols). A faster version of [VSH](wikipedia://en/24892363) (called VSH\*) could be obtained in this way.
