# Implicit certificate

::: {#o1 .subject cue=lead name="Implicit certificate"}

In [cryptography](wikipedia://en/18934432), **implicit certificates** are a variant of [public key certificate](wikipedia://en/223796). A subject's [public key](wikipedia://en/24222) is reconstructed from the data in an implicit certificate, and is then said to be "implicitly" verified. Tampering with the certificate will result in the reconstructed public key being invalid, in the sense that it is infeasible to find the matching private key value, as would be required to make use of the tampered certificate.

:::

By comparison, traditional public-key certificates include a copy of the subject's public key, and a [digital signature](wikipedia://en/59644) made by the issuing [certificate authority](wikipedia://en/296370) (CA). The public key must be explicitly validated, by verifying the signature using the CA's public key. For the purposes of this article, such certificates will be called "explicit" certificates.

Elliptic Curve Qu-Vanstone (ECQV) is one kind of implicit certificate scheme. It is described in the document *Standards for Efficient Cryptography 4 (SEC4)*.[^o2] This article will use ECQV as a concrete example to illustrate implicit certificates.

## Comparison of ECQV with explicit certificates {#Comparison_of_ECQV_with_explicit_certificates}

Conventional explicit certificates are made up of three parts: subject identification data, a [public key](https://en.wikipedia.org/wiki/Public_key) and a [digital signature](wikipedia://en/59644) which binds the public key to the user's identification data (ID). These are distinct data elements within the certificate, and contribute to the size of the certificate: for example, a standard [X.509](https://en.wikipedia.org/wiki/X.509) certificate is on the order of 1KB in size (~8000 bits).

An ECQV implicit certificate consists of identification data, and a single cryptographic value. This value, an [elliptic curve](wikipedia://en/9966) point, combines the function of public key data and CA signature. ECQV implicit certificates can therefore be considerably smaller than explicit certificates, and so are useful in highly constrained environments such as Radio-frequency Identification [RFID](https://en.wikipedia.org/wiki/RFID) tags, where not a lot of memory or bandwidth is available.

ECQV certificates are useful for any ECC scheme where the private and public keys are of the form ( *d*, *dG* ). This includes key agreement protocols such as [ECDH](https://en.wikipedia.org/wiki/ECDH) and [ECMQV](https://en.wikipedia.org/wiki/ECMQV), or signing algorithms such as [ECDSA](https://en.wikipedia.org/wiki/ECDSA). The operation will fail if the certificate has been altered, as the reconstructed public key will be invalid. Reconstructing the public key is fast (a single [point multiplication](wikipedia://en/28244303) operation) compared to ECDSA signature verification.

## Comparison with ID-based cryptography {#Comparison_with_ID-based_cryptography}

Implicit certificates are not to be confused with [identity-based cryptography](https://en.wikipedia.org/wiki/ID-based_cryptography). In ID-based schemes, the subject's identity itself is used to derive their public key; there is no 'certificate' as such. The corresponding private key is calculated and issued to the subject by a [trusted third party](wikipedia://en/584651).

In an implicit certificate scheme, the subject has a private key which is not revealed to the CA during the certificate-issuing process. The CA is trusted to issue certificates correctly, but not to hold individual user's private keys. Wrongly issued certificates can be [revoked](https://en.wikipedia.org/wiki/Certificate_revocation), whereas there is no comparable mechanism for misuse of private keys in an identity-based scheme.

## Description of the ECQV scheme {#Description_of_the_ECQV_scheme}

Initially the scheme parameters must be agreed upon. These are:

- The [elliptic curve parameters](wikipedia://en/9966#Domain_parameters), including a generating point $G \,$of order $n \,$.
- An encoding function $\textrm{Encode}(\gamma, ID)$ with a public key reconstruction data $\gamma$ and an identifying information $ID$ encodes its arguments as a byte-block, and a corresponding $\textrm{Decode}_{\gamma}( \cdot )$ which extracts the $\gamma$ value from an encoding.
- A [hash function](wikipedia://en/439526) $H_n( \cdot )$ which accepts a byte-block and yields a hash value as an integer in the range $[0, n-1]$

The [certificate authority](wikipedia://en/296370) CA will have private key $c \,$ and public key $Q_{CA} = cG$

### Certificate request protocol {#Certificate_request_protocol}

Here, Alice will be the user who requests the implicit certificate from the CA. She has identifying information $ID_A$.

1. Alice generates a random integer $\alpha \,$
1. Alice computes $A = \alpha\,G \,$ and sends $A$ and $ID_A$ to the CA.
1. CA selects a random integer $k \,$ from $[1, n-1] \,$ and computes $kG \,$.
1. CA computes $\gamma = A + kG \,$ (this is the public key reconstruction data)
1. CA computes $Cert= \textrm{Encode} ( \gamma , \textrm{ID}_A ) \,$
1. CA computes $e = H_n( Cert )$
1. CA computes $s = ek + c \pmod{n} \,$ ($s \,$ is the private key reconstruction data)
1. CA sends $(s, Cert) \,$ to Alice
1. Alice computes $e' = H_n (Cert)$ and her private key $a = e'\alpha + s \pmod{n} \,$
1. Alice computes $\gamma' = \textrm{Decode}_{\gamma} (Cert)$ and her public key $Q_A = e'\gamma' + Q_{CA} \,$
1. Alice verifies that the certificate is valid, i.e. that $Q_A = aG$

### Using the certificate {#Using_the_certificate}

Here, Alice wants to prove her identity to Bob, who trusts the CA.

1. Alice sends $Cert$ to Bob, and a ciphertext $C$ created using her private key $a$. The ciphertext can be a digital signature, or part of an [Authenticated Key Exchange](wikipedia://en/36103897) protocol.
1. Bob computes $\gamma'' = \textrm{Decode}_{\gamma} (Cert)$ and $e'' = H_n (Cert)$.
1. Bob computes Alice's alleged public key $Q_A' = e''\gamma'' + Q_{CA}$
1. Bob validates ciphertext $C$ using $Q_A'$. If this validation is successful, he can trust that the key $Q_A'$ is owned by the user whose identity information is contained in $Cert$.

::: {#o9 .proof cue=heading name="Proof of equivalence of private and public keys"}

### Proof of equivalence of private and public keys {#Proof_of_equivalence_of_private_and_public_keys}

Alice's private key is $a = e'\alpha + s = e\alpha + ek + c \pmod{n}$

The public key reconstruction value $\gamma = A + kG = (\alpha + k)G$

Alice's public key is $Q_A = e\gamma + Q_{CA} = e(\alpha + k)G + cG = (e\alpha + ek + c)G$

Therefore, $Q_A = aG$, which completes the proof.

:::
