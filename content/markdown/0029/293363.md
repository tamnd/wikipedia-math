# RSA SecurID

::: {#o2 .subject cue=lead name="RSA SecurID"}

**RSA SecurID** is a mechanism developed by [RSA](wikipedia://en/301240) for performing [two-factor authentication](https://en.wikipedia.org/wiki/Two-factor_authentication) for a user to a network resource.

:::

## Description {#Description}

*Image: RSA SecurID Token Old.jpg.* RSA SecurID token (older style, model SD600)

*Image: SecureID token new.JPG.* RSA SecurID token (model SID700)

*Image: RSA SecurID SID800.jpg.* RSA SecurID (new style, SID800 model with smartcard functionality)

The RSA SecurID authentication mechanism consists of a "[token](https://en.wikipedia.org/wiki/Security_token)"—either hardware (e.g. a [key fob](https://en.wikipedia.org/wiki/Key_fob)) or software (a [soft token](https://en.wikipedia.org/wiki/Software_token))—which is assigned to a computer user and which creates an authentication code at fixed intervals (usually 60 seconds) using a built-in clock and the card's factory-encoded almost random [key](wikipedia://en/53039) (known as the "seed"). The seed is different for each token, and is loaded into the corresponding RSA SecurID server (RSA Authentication Manager, formerly ACE/Server[^o4]) as the tokens are purchased.[^o5] On-demand tokens are also available, which provide a tokencode via email or SMS delivery, eliminating the need to provision a token to the user.

The token hardware is designed to be [tamper-resistant](https://en.wikipedia.org/wiki/Tamper_resistance) to deter [reverse engineering](https://en.wikipedia.org/wiki/Reverse_engineering). When software implementations of the same algorithm ("software tokens") appeared on the market, public code had been developed by the security community allowing a user to emulate RSA SecurID in software, but only if they have access to a current RSA SecurID code, and the original 64-bit RSA SecurID seed file introduced to the server.[^o6] Later, the 128-bit RSA SecurID algorithm was published as part of an open source library.[^o7] In the RSA SecurID authentication scheme, the seed record is the secret key used to generate [one-time passwords](wikipedia://en/1190077). Newer versions also feature a USB connector, which allows the token to be used as a [smart card](https://en.wikipedia.org/wiki/Smart_card)-like device for securely storing [certificates](wikipedia://en/223796).[^o8]

A user authenticating to a network resource—say, a dial-in server or a firewall—needs to enter both a [personal identification number](https://en.wikipedia.org/wiki/Personal_identification_number) and the number being displayed *at that moment* on their RSA SecurID token. Though increasingly rare, some systems using RSA SecurID disregard PIN implementation altogether, and rely on password/RSA SecurID code combinations. The server, which also has a real-time clock and a database of valid cards with the associated seed records, authenticates a user by computing what number the token is supposed to be showing at that moment in time and checking this against what the user entered.

On older versions of SecurID, a "duress PIN" may be used—an alternate code which creates a security event log showing that a user was forced to enter their PIN, while still providing transparent authentication.[^o9] Using the duress PIN would allow one successful authentication, after which the token will automatically be disabled. The "duress PIN" feature has been deprecated and is not available on currently supported versions.

While the RSA SecurID system adds a layer of security to a network, difficulty can occur if the authentication server's clock becomes out of sync with the clock built into the authentication tokens. Normal token clock drift is accounted for automatically by the server by adjusting a stored "drift" value over time. If the out of sync condition is not a result of normal hardware token clock drift, correcting the synchronization of the Authentication Manager server clock with the out of sync token (or tokens) can be accomplished in several different ways. If the server clock had drifted and the administrator made a change to the system clock, the tokens can either be resynchronized one-by-one, or the stored drift values adjusted manually. The drift can be done on individual tokens or in bulk using a command line utility.

RSA Security has pushed forth an initiative called "Ubiquitous Authentication", partnering with device manufacturers such as [IronKey](https://en.wikipedia.org/wiki/IronKey), [SanDisk](https://en.wikipedia.org/wiki/SanDisk), [Motorola](https://en.wikipedia.org/wiki/Motorola), [Freescale Semiconductor](https://en.wikipedia.org/wiki/Freescale_Semiconductor), Redcannon, [Broadcom](https://en.wikipedia.org/wiki/Broadcom), and [BlackBerry](https://en.wikipedia.org/wiki/BlackBerry) to embed the SecurID software into everyday devices such as USB flash drives and cell phones, to reduce cost and the number of objects that the user must carry.[^o10]

## Theoretical vulnerabilities {#Theoretical_vulnerabilities}

Token codes are easily stolen, because no mutual-authentication exists (anything that can steal a password can also steal a token code). This is significant, since it is the principal threat most users believe they are solving with this technology.

The simplest practical vulnerability with any password container is losing the special key device or the activated smart phone with the integrated key function. Such vulnerability cannot be healed with any single token container device within the preset time span of activation. All further consideration presumes loss prevention, e.g. by additional electronic leash or body sensor and alarm.

While RSA SecurID tokens offer a level of protection against password [replay attacks](wikipedia://en/614094), they are not designed to offer protection against [man in the middle](wikipedia://en/144676) type attacks when used alone. If the attacker manages to block the authorized user from authenticating to the server until the next token code will be valid, they will be able to log into the server. Risk-based analytics (RBA), a new feature in the latest version (8.0) provides significant protection against this type of attack if the user is enabled and authenticating on an agent enabled for RBA. RSA SecurID does not prevent [man in the browser](https://en.wikipedia.org/wiki/Man_in_the_Browser) (MitB) based attacks.

SecurID authentication server tries to prevent password sniffing and simultaneous login by declining both authentication requests, if two valid credentials are presented within a given time frame. This has been documented in an unverified post by John G. Brainard.[^o12] If the attacker removes from the user the ability to authenticate however, the SecurID server will assume that it is the user who is actually authenticating and hence will allow the attacker's authentication through. Under this attack model, the system security can be improved using encryption/authentication mechanisms such as [SSL](https://en.wikipedia.org/wiki/Secure_Sockets_Layer).

Although soft tokens may be more convenient, critics indicate that the [tamper-resistant](https://en.wikipedia.org/wiki/Tamper_resistance) property of hard tokens is unmatched in soft token implementations,[^o13] which could allow seed record secret keys to be duplicated and user impersonation to occur.

Hard tokens, on the other hand, can be physically stolen (or acquired via [social engineering](https://en.wikipedia.org/wiki/Social_engineering_%28security%29)) from end users. The small form factor makes hard token theft much more viable than laptop/desktop scanning. A user will typically wait more than one day before reporting the device as missing, giving the attacker plenty of time to breach the unprotected system. This could only occur, however, if the user's UserID and PIN are also known. Risk-based analytics can provide additional protection against the use of lost or stolen tokens, even if the user's UserID and PIN are known by the attackers.

Batteries go flat periodically, requiring complicated replacement and re-enrollment procedures.

## Reception and competing products {#Reception_and_competing_products}

As of 2003, RSA SecurID commanded over 70% of the two-factor authentication market[^o15] and 25 million devices have been produced to date. A number of competitors, such as [VASCO](https://en.wikipedia.org/wiki/VASCO_Data_Security_International,_Inc.), make similar [security tokens](https://en.wikipedia.org/wiki/Security_token), mostly based on the open [OATH HOTP](https://en.wikipedia.org/wiki/Initiative_For_Open_Authentication) standard. A study on OTP published by [Gartner](https://en.wikipedia.org/wiki/Gartner) in 2010 mentions OATH and SecurID as the only competitors.[^o16]

Other network authentication systems, such as [OPIE](https://en.wikipedia.org/wiki/OPIE_Authentication_System) and [S/Key](https://en.wikipedia.org/wiki/S/Key) (sometimes more generally known as [OTP](wikipedia://en/1190077), as S/Key is a trademark of [Telcordia Technologies](https://en.wikipedia.org/wiki/Telcordia_Technologies), formerly [Bellcore](https://en.wikipedia.org/wiki/Bellcore)) attempt to provide the "something you have" level of authentication without requiring a hardware token.

## March 2011 system compromise {#March_2011_system_compromise}

On 17 March 2011, RSA announced that they had been victims of "an extremely sophisticated cyber attack".[^o18] Concerns were raised specifically in reference to the SecurID system, saying that "this information could potentially be used to reduce the effectiveness of a current two-factor authentication implementation". However, their formal [Form 8-K](https://en.wikipedia.org/wiki/Form_8-K) submission[^o19] indicated that they did not believe the breach would have a "material impact on its financial results". The breach cost EMC, the parent company of RSA, \$66.3 million, which was taken as a charge against second quarter earnings. It covered costs to investigate the attack, harden its IT systems and monitor transactions of corporate customers, according to EMC Executive Vice President and Chief Financial Officer David Goulden, in a conference call with analysts.[^o20]

The breach into RSA's network was carried out by hackers who sent [phishing](https://en.wikipedia.org/wiki/Phishing) emails to two targeted, small groups of employees of RSA.[^o21] Attached to the email was a [Microsoft Excel](https://en.wikipedia.org/wiki/Microsoft_Excel) file containing [malware](https://en.wikipedia.org/wiki/Malware). When an RSA employee opened the Excel file, the malware exploited a vulnerability in [Adobe Flash](https://en.wikipedia.org/wiki/Adobe_Flash). The [exploit](https://en.wikipedia.org/wiki/Exploit_%28computer_security%29) allowed the hackers to use the [Poison Ivy](https://en.wikipedia.org/wiki/PoisonIvy_%28Trojan%29) [RAT](https://en.wikipedia.org/wiki/Remote_access_trojan) to gain control of machines and access servers in RSA's network.[^o22]

There are some hints that the breach involved the theft of RSA's database mapping token serial numbers to the secret token "seeds" that were injected to make each one unique.[^o23] Reports of RSA executives telling customers to "ensure that they protect the serial numbers on their tokens"[^o24] lend credibility to this hypothesis.

RSA stated it did not release details about the extent of the attack so as to not give potential attackers information they could use in figuring out how to attack the system.[^o25]

On 6 June 2011, RSA offered token replacements or free security monitoring services to any of its more than 30,000 SecurID customers, following an attempted cyber breach on defense customer [Lockheed Martin](https://en.wikipedia.org/wiki/Lockheed_Martin) that appeared to be related to the SecurID information stolen from RSA.[^o26] In spite of the resulting attack on one of its defense customers, company chairman Art Coviello said that "We believe and still believe that the customers are protected".[^o27]

### Resulting attacks {#Resulting_attacks}

In April 2011, unconfirmed rumors cited [L-3 Communications](https://en.wikipedia.org/wiki/L-3_Communications) as having been attacked as a result of the RSA compromise.[^o29]

In May 2011, this information was used to attack [Lockheed Martin](https://en.wikipedia.org/wiki/Lockheed_Martin) systems.[^o30][^o31] However Lockheed Martin claims that due to "aggressive actions" by the company's [information security](wikipedia://en/15036) team, "No customer, program or employee personal data" was compromised by this "significant and tenacious attack".[^o32] The [Department of Homeland Security](https://en.wikipedia.org/wiki/Department_of_Homeland_Security) and the [US Defense Department](https://en.wikipedia.org/wiki/US_Defense_Department) offered help to determine the scope of the attack.[^o33]
