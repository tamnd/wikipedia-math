# Common Scrambling Algorithm

::: {#o1 .subject cue=lead name="Common Scrambling Algorithm"}

The **Common Scrambling Algorithm** (**CSA**) is the [encryption algorithm](https://en.wikipedia.org/wiki/Encryption_algorithm) used in the [DVB](https://en.wikipedia.org/wiki/Digital_Video_Broadcasting) [digital television](https://en.wikipedia.org/wiki/Digital_television) broadcasting for encrypting [video streams](https://en.wikipedia.org/wiki/Video_coding).

:::

CSA was specified by [ETSI](https://en.wikipedia.org/wiki/ETSI) and adopted by the DVB consortium in May 1994. It is being succeeded by CSA3,[^o2] based on a combination of 128-bit [AES](wikipedia://en/1260) and a confidential block cipher, XRC. However, CSA3 is not yet in any significant use, so CSA continues to be the dominant cipher for protecting DVB broadcasts.

## History {#History}

CSA was largely kept secret until 2002. The patent papers gave some hints, but important details, like the layout of the so-called [S-boxes](wikipedia://en/240991), remained secret. Without these, free implementations of the algorithm was not possible. Initially, CSA was to remain implemented in hardware only, making it difficult to [reverse engineer](https://en.wikipedia.org/wiki/Reverse_engineering) existing implementations.

In 2002 FreeDec was released, implementing CSA in [software](https://en.wikipedia.org/wiki/Software). Though released as [binary](https://en.wikipedia.org/wiki/Executable) only, [disassembly](https://en.wikipedia.org/wiki/Disassembler) revealed the missing details and allowed reimplementation of the algorithm in higher-level [programming languages](wikipedia://en/23015).

With CSA now publicly known in its entirety, [cryptanalysts](https://en.wikipedia.org/wiki/Cryptanalyst) started looking for weaknesses.

## Description of the cipher {#Description_of_the_cipher}

The CSA algorithm is composed of two distinct ciphers: a block cipher and a stream cipher.

When used in encryption mode the data are first encrypted using the 64-bit block cipher in [CBC mode](https://en.wikipedia.org/wiki/Block_cipher_modes_of_operation), starting from packet end. The stream cipher is then applied from packet start.

### Block cipher {#Block_cipher}

The block cipher process 64-bit blocks in 56 rounds. It uses 8 bits from an expanded key on each round.

*Image: Dvbcsa block encrypt.svg.* Block cipher encryption

### Stream cipher {#Stream_cipher}

The first 32 round of the stream cipher are used for initialization and do not generate any output. The first 64 bits of data are used as [initialization vector](wikipedia://en/105971) during this phase and are left unchanged. The stream cipher then generates 2 bits of pseudo-random stream on each round which are xored starting at bit 64 of the packet.

## Weaknesses {#Weaknesses}

Were CSA to be broken, encrypted DVB transmissions would be decipherable, which would compromise paid digital television services, as DVB has been standardised for [digital terrestrial television](https://en.wikipedia.org/wiki/Digital_terrestrial_television) in Europe and elsewhere, and is used by many satellite television providers.

Most attacks on the pay-TV system have not targeted CSA itself, but instead the various [key exchange](wikipedia://en/578092) systems responsible for *generating* the CSA keys ([Conax](https://en.wikipedia.org/wiki/Conax), Irdeto, [Nagravision](https://en.wikipedia.org/wiki/Nagravision), [VideoGuard](wikipedia://en/1523933), etc.), either by reverse-engineering and breaking the algorithms altogether, or by intercepting the keys in real-time as they are generated on a legitimate decoder, and then distributing them to others (so-called [card sharing](https://en.wikipedia.org/wiki/Card_sharing)).

### Software implementations and bit slicing {#Software_implementations_and_bit_slicing}

The stream cipher part of CSA is prone to [bit slicing](https://en.wikipedia.org/wiki/Bit_slicing), a software implementation technique which allows decryption of many blocks, or the same block with many different keys, at the same time. This significantly speeds up a brute force search implemented in software, although the factor is too low for a practical real-time attack.

The block cipher part is harder to bit slice, as the [S-boxes](https://en.wikipedia.org/wiki/S-boxes) involved are too large (8x8) to be efficiently implemented using logical operations, a prerequisite for bit slicing to be more efficient than a regular implementation. However, as all operations are on 8-bit subblocks, the algorithm can be implemented using regular [SIMD](https://en.wikipedia.org/wiki/SIMD), or a form of “byteslicing”. As most SIMD instruction sets, (with the exception of [AVX2](https://en.wikipedia.org/wiki/AVX2)) do not support parallel look-up tables, the S-box lookups are done in a non-bytesliced implementation, but their integration into the rest of the algorithm is not hampered markedly by the byteslicing.

Both techniques are used in [libdvbcsa](https://www.videolan.org/developers/libdvbcsa.html), a free implementation of CSA.

### Cryptanalysis {#Cryptanalysis}

Cryptanalysis is made more difficult as most data is protected both by the block and the stream cipher. Adaption codes can result in packets with some data protected by only the block cipher or the stream cipher.[^o10]

### Brute force approach {#Brute_force_approach}

While the CSA algorithm uses 64-bit keys, most of the time, only 48 bits of the key are unknown, since bytes 3 and 7 are used as parity bytes in CA systems, and may be easily recalculated. This allows for possible [known-plaintext attacks](wikipedia://en/517019) when combined with knowledge of the underlying plaintext structure. As the first three bytes of the [PES](https://en.wikipedia.org/wiki/Packetized_elementary_stream) header are always 0x000001, it would be possible to launch a [brute force attack](https://en.wikipedia.org/wiki/Brute_force_attack). Such an attack would reveal millions of possible keys, but still few enough to make it practical to attempt decryption of other parts of the data with the same key in a second pass to recover the true key.

### Known-plaintext attack {#Known-plaintext_attack}

In 2011, a group of German researchers released an attack[^o13] on CSA as used in the DVB system. By noting that MPEG-2 padding frequently requires long series of zeroes, leading to entire 184-byte cells being encrypted with zeroes only, it is possible to build up a [rainbow table](wikipedia://en/2403284) recovering the key from such a known-zero block. (A block would be known to be zero if two blocks with the same ciphertext were found, since presumably both would be zero blocks.) The attack described would require about 7.9 TB of storage, and enable an attacker with a [GPU](https://en.wikipedia.org/wiki/GPU) to recover a key in about seven seconds with 96.8% certainty. However, the attack is only effective when such all-zero padding blocks are present (i.e., in scenes with very little movement or noise), and it would be easily mitigated by for instance sending such all-zero cells unencrypted.

This differs from the brute-force attack examples already mentioned, in that the plain-text contents of the entire cell is known before the attack, not just parts of a block, which enables the ahead-of-time computation of the rainbow table.

### Fault attack {#Fault_attack}

In 2004, a fault attack[^o15] was published on the block cipher. The basic idea was to introduce a few deliberate faults in the intermediate calculations, making it possible to deduce the last eight round keys. From this, the final key can be computed.

While very few faults are needed (on average two or three per round key recovered), fault attacks are usually impractical to carry out, in that it requires the ability to change bits at will inside the hardware of a decoder that already has the key in question.
