# Key encapsulation mechanism

*Image: KEM.svg.* A key encapsulation mechanism, to confidentially transport a *random secret key* $k$ from a sender to a receiver, consists of three algorithms: Gen, Encap, and Decap. Circles shaded blue—the receiver's public key $pk$ and the encapsulation $c$—can be safely revealed to an adversary, while boxes shaded red—the receiver's private key $sk$ and the encapsulated secret key $k$—must be kept secret. The secret key $k$ is chosen at random inside the logic of Encap, and the sender has no control over it.

::: {#o1 .subject cue=lead name="Key encapsulation mechanism"}

In [cryptography](wikipedia://en/18934432), a **key encapsulation mechanism** (**KEM**) is a [public-key cryptosystem](wikipedia://en/24222) that allows a sender to generate a short secret key and transmit it to a receiver confidentially, in spite of [eavesdropping](https://en.wikipedia.org/wiki/Network_eavesdropping) and [intercepting](wikipedia://en/144676) adversaries.[^o2][^o3][^o4] Modern standards for [public-key encryption](https://en.wikipedia.org/wiki/Public-key_encryption) of arbitrary messages are usually based on KEMs.[^o5]9180

:::

A KEM allows a sender who knows a public key to simultaneously generate a short random secret key and an **encapsulation** or **ciphertext** of the secret key by the KEM's **encapsulation algorithm**. The receiver who knows the private key corresponding to the public key can recover the same random secret key from the encapsulation by the KEM's **decapsulation algorithm**.[^o2][^o3][^o4]

The security goal of a KEM is to prevent anyone who *does not* know the private key from recovering any information about the encapsulated secret keys, even after eavesdropping or submitting other encapsulations to the receiver to study how the receiver reacts.[^o2][^o3][^o4]

## Difference from public-key encryption {#Difference_from_public-key_encryption}

*Image: PKE.svg.* A public-key encryption scheme, to confidentially transport an *arbitrary message* $m$ from a sender to a receiver. The message $m$ is chosen by the sender.

The difference between a [public-key encryption](https://en.wikipedia.org/wiki/Public-key_encryption) scheme and a KEM is that a public-key encryption scheme allows a sender to choose an arbitrary message from some space of possible messages, while a KEM chooses a short secret key at random for the sender.[^o2][^o3][^o4]

The sender may take the random secret key produced by a KEM and use it as a [symmetric key](https://en.wikipedia.org/wiki/Symmetric_key) for an [authenticated cipher](wikipedia://en/2244296) whose ciphertext is sent alongside the encapsulation to the receiver. This serves to compose a public-key encryption scheme out of a KEM and a symmetric-key authenticated cipher in a [hybrid cryptosystem](wikipedia://en/11756462).[^o2][^o3][^o4]9180

Most public-key encryption schemes such as [RSAES-PKCS1-v1\_5](wikipedia://en/16706008), [RSAES-OAEP](wikipedia://en/1579249), and [Elgamal encryption](https://en.wikipedia.org/wiki/Elgamal_encryption) are limited to small messages8017[^o7] and are almost always used to encrypt a short random secret key in a hybrid cryptosystem anyway.[^o8]48809180 And although a public-key encryption scheme can conversely be converted to a KEM by choosing a random secret key and encrypting it as a message, it is easier to design and analyze a secure KEM than to design a secure public-key encryption scheme as a basis. So most modern public-key encryption schemes are based on KEMs rather than the other way around.[^o9][^n1]

::: {#o11 .definition cue=heading name="Definition"}

## Definition {#Definition}

### Syntax {#Syntax}

A KEM consists of three algorithms:[^o2][^o3][^o4][^o13][^o14]

1. **Key generation**, $(\mathit{pk}, \mathit{sk}) := \operatorname{Gen}()$, takes no inputs and returns a pair of a public key $\mathit{pk}$ and a private key $\mathit{sk}$.
1. **Encapsulation**, $(k, c) := \operatorname{Encap}(\mathit{pk})$, takes a public key $\mathit{pk}$, randomly chooses a secret key $k$, and returns $k$ along with its encapsulation $c$.
1. **Decapsulation**, $k' := \operatorname{Decap}(\mathit{sk}, c')$, takes a private key $\mathit{sk}$ and an encapsulation $c'$, and either returns an encapsulated secret key $k'$ or fails, sometimes denoted by returning $\bot$ (called "[bottom](wikipedia://en/25016871)").

In the [asymptotic setting](wikipedia://en/641995) of theoretical cryptography, the algorithms are all [probabilistic polynomial-time](https://en.wikipedia.org/wiki/Probabilistic_polynomial-time) in a [security parameter](wikipedia://en/2290431) $\lambda$, and the length of the secret key $k$ is a function of the security parameter $\lambda$.[^o2][^o3]

In practical cryptography, the secret key $k$ is usually of a fixed length for each algorithm. For example, [ML-KEM](https://en.wikipedia.org/wiki/ML-KEM) always uses 256-bit secret keys,[^o5] while the algorithms in 9180 vary between 256-, 384-, and 512-bit secret keys;[^n1] secret keys of arbitrary length can be derived from $k$ by a [key derivation function](wikipedia://en/449781).[^o15][^n1]

#### Explicit *vs.* implicit rejection {#Explicit_vs._implicit_rejection}

Decapsulation can fail because its input $c'$ is not an encapsulation $c$ returned by Encap, but has been tampered with or maliciously crafted. KEMs which report failure by a distinguished symbol $\bot$ (implemented in practice by returning an error code or raising an exception) are said to use **explicit rejection**. A KEM may instead return a random secret key in this event, or a secret key derived [pseudorandomly](wikipedia://en/3454616) from $c'$ under the key $sk$; this is called **implicit rejection**.[^o17][^o14]

### Correctness {#Correctness}

A KEM is **correct** if, for any key pair $(\mathit{pk}, \mathit{sk})$ generated by $\operatorname{Gen}$, decapsulating an encapsulation $c$ returned by $(k, c) := \operatorname{Encap}(\mathit{pk})$ with high probability yields the same key $k$, that is, $\operatorname{Decap}(\mathit{sk}, c) = k$.[^o3][^o4][^o13][^o14]

### Security: IND-CCA {#Security:_IND-CCA}

**Security** of a KEM is quantified by its [indistinguishability against adaptive chosen-ciphertext attack](wikipedia://en/2187252), IND-CCA, which is loosely how much better an adversary can do than a coin toss to tell whether, given a random key and an encapsulation, the key is encapsulated by that encapsulation or is an independent random key.[^o3][^o4][^o13][^o14][^o2]

Specifically, in the IND-CCA game:

1. The [key generation](https://en.wikipedia.org/wiki/Key_generation) algorithm is run to generate $(\mathit{pk}, \mathit{sk}) := \operatorname{Gen}()$.
1. $\mathit{pk}$ is revealed to the adversary.
1. The adversary can query $\operatorname{Decap}(\mathit{sk}, c')$ for arbitrary encapsulations $c'$ of the adversary's choice.
1. The encapsulation algorithm is run to randomly generate a secret key and encapsulation $(k_0, c) := \operatorname{Encap}(\mathit{pk})$, and another secret key $k_1$ is generated independently at random.
1. A [fair coin](wikipedia://en/9597100) is tossed, giving an outcome $b \in \{0,1\}$.
1. The pair $(k_b, c)$ is revealed to the adversary.
1. The adversary can again query $\operatorname{Decap}(\mathit{sk}, c')$ for arbitrary encapsulations $c'$ of the adversary's choice, *except* for $c$.
1. The adversary returns a guess $b' \in \{0,1\}$, and wins the game if $b = b'$.

The **IND-CCA advantage** of the adversary is $\left|\Pr[b' = b] - 1/2\right|$, that is, the probability beyond a fair coin toss at correctly distinguishing an encapsulated key from an independently randomly chosen key.

## Applications {#Applications}

### Public-key encryption {#Public-key_encryption}

A key encapsulation mechanism can be used together with an [authenticated](wikipedia://en/2244296) [symmetric cipher](https://en.wikipedia.org/wiki/Symmetric-key_cryptography) to construct a [public-key encryption](https://en.wikipedia.org/wiki/Public-key_encryption) scheme for arbitrary messages. The security requirement for the symmetric cipher, called a **data encapsulation mechanism** or **DEM**, is [indistinguishability against chosen-ciphertext attack](wikipedia://en/2187252) for a *single* message encrypted by the sender.[^o39][^o13]9690

Given a secure KEM with algorithms Gen/Encap/Decap, and a secure DEM $E_k(m)$, the following [hybrid public-key encryption scheme](wikipedia://en/11756462) is also secure against adaptive chosen-ciphertext attack in the public-key setting:[^o2][^o3][^o15]

- Key generation: Same as the KEM.
- To encrypt a message $m$ for a public key $\mathit{pk}$:
  1. Let $(k, c) := \operatorname{Encap}(\mathit{pk})$.
  1. Let $\sigma := E_k(m)$.
  1. Send $(c, \sigma)$ as the ciphertext.
- To decrypt a ciphertext $(c', \sigma')$ with private key $\mathit{sk}$:
  1. Let $k' := \operatorname{Decap}(\mathit{sk}, c')$, or fail if it fails.
  1. Return the message $E_{k'}^{-1}(\sigma')$, or fail if it fails.

Note that—as with any public-key encryption on its own—this does not authenticate the sender: anyone with the public key can send a message to a recipient with the private key. Other cryptography, such as [digital signatures](https://en.wikipedia.org/wiki/Digital_signatures), must be used in a protocol for a sender to prove its identity to the receiver.[^o23]

The use of an *authenticated* symmetric cipher is nevertheless required in this *anonymous* public-key encryption scheme to meet IND-CCA security. If an *unauthenticated* cipher were used, secure only against chosen-plaintext attack (IND-CPA), an adversary could [selectively modify](wikipedia://en/87027) a message through its ciphertext in transit, which not only fails IND-CCA on a technicality[^o24] but also can compromise confidentiality in practice as in [EFAIL](https://en.wikipedia.org/wiki/EFAIL).[^o25]

### Key agreement protocols {#Key_agreement_protocols}

A KEM can also be used in an [authenticated key agreement](https://en.wikipedia.org/wiki/Authenticated_key_agreement) protocol such as [TLS](wikipedia://en/187813) with [forward secrecy](wikipedia://en/2191130) for an online session, by having the client and server generate KEM key pairs and exchange signed encapsulations using those key pairs, which they then erase at the end of the session.[^o15]

### Combining KEMs {#Combining_KEMs}

Different KEMs rely on different mathematical problems for their security. For example, the security of Rabin-KEM relies on the difficulty of [integer factorization](wikipedia://en/15491),[^o13] which has been studied for centuries, but is known to be vulnerable to [quantum computers](wikipedia://en/25220) capable of running [Shor's algorithm](wikipedia://en/42674). In contrast, the security of [ML-KEM](https://en.wikipedia.org/wiki/ML-KEM) relies on the difficulty of [learning with errors](wikipedia://en/23864530),[^o5] which has only been studied for decades, but is not known to be vulnerable even to an adversary with a Shor-capable quantum computer.

A **KEM combiner** is a scheme for combining two KEMs, KEM<sub>1</sub> and KEM<sub>2</sub> with respective encapsulation algorithms KEM<sub>1</sub>.Encap and KEM<sub>2</sub>.Encap and so on, into a combined KEM which is secure if *either* KEM<sub>1</sub> *or* KEM<sub>2</sub> is secure.[^o28]

A KEM that combines a quantum-vulnerable KEM such as DH-KEM using [X25519](https://en.wikipedia.org/wiki/X25519) with a [post-quantum](wikipedia://en/26605226) KEM such as [ML-KEM](https://en.wikipedia.org/wiki/ML-KEM) is sometimes called a [**hybrid**](wikipedia://en/26605226#Hybrid_encryption),[^o29][^o9][^o30] not to be confused with a [hybrid cryptosystem](wikipedia://en/11756462) which combines [public-key cryptography](wikipedia://en/24222) with [symmetric-key cryptography](https://en.wikipedia.org/wiki/Symmetric-key_cryptography).

:::

## Examples and motivation {#Examples_and_motivation}

### RSA {#RSA}

Traditional [RSA encryption](https://en.wikipedia.org/wiki/RSA_encryption), with $t$-bit moduli and exponent $e$, is defined as follows:[^o33][^o34][^o35]

- **Key generation**, $(\mathit{pk}, \mathit{sk}) := \operatorname{Gen}()$:

<!-- -->

1. Generate a $t$-bit [semiprime](wikipedia://en/339542) $n$ with $2^{t - 1} < n < 2^t$ at random satisfying $\gcd(e, \lambda(n)) = 1$, where $\lambda(n)$ is the [Carmichael function](wikipedia://en/1181756).
1. Compute $d := e^{-1} \bmod \lambda(n)$.
1. Return $\mathit{pk} := n$ as the public key and $\mathit{sk} := (n, d)$ as the private key. (Many variations on key generation algorithms and private key formats are available.[^o36])

<!-- -->

- **Encryption** of $(t - 1)$-bit message $m$ to public key $\mathit{pk} = n$, giving $c := \operatorname{Encrypt}(\mathit{pk}, m)$:

<!-- -->

1. Encode the bit string $m$ as an integer $r$ with $0 \leq r < n$.
1. Return $c := r^e \bmod n$.

<!-- -->

- **Decryption** of ciphertext $c'$ with private key $\mathit{sk} = (n, d)$, giving $m' := \operatorname{Decrypt}(\mathit{sk}, c')$:

<!-- -->

1. Compute $r' := (c')^d \bmod n$.
1. Decode the integer $r'$ as a bit string $m'$.

This naive approach is totally insecure. For example, since it is nonrandomized, it cannot be secure against even [known-plaintext attack](wikipedia://en/517019)—an adversary can tell whether the sender is sending the message `ATTACK AT DAWN` versus the message `ATTACK AT DUSK` simply by encrypting those messages and comparing the ciphertext.

Even if $m$ is always a random secret key, such as a 256-bit [AES](wikipedia://en/1260) key, when $e$ is chosen to optimize efficiency as $e = 3$, the message $m$ can be computed from the ciphertext $c$ simply by taking [real number](wikipedia://en/20646438) cube roots, and there are many other [attacks against plain RSA](https://en.wikipedia.org/wiki/RSA_%28cryptosystem%29#Attacks_against_plain_RSA).[^o33][^o34] Various [randomized padding schemes](https://en.wikipedia.org/wiki/RSA_%28cryptosystem%29#Padding_schemes) have been devised in attempts—sometimes failed, like [RSAES-PKCS1-v1\_5](wikipedia://en/16706008)[^o33][^o37][^o38]—to make it secure for arbitrary short messages $m$.[^o33][^o34]

Since the message $m$ is almost always a short secret key for a [symmetric-key](https://en.wikipedia.org/wiki/Symmetric-key) [authenticated cipher](wikipedia://en/2244296) used to encrypt an arbitrary bit string message, a simpler approach called **RSA-KEM** is to choose an element of $\mathbb Z/n\mathbb Z$ at random and use that to *derive* a secret key using a [key derivation function](wikipedia://en/449781) $H$, roughly as follows:[^o39][^o8]9690

- **Key generation**: As above.
- **Encapsulation** for a public key $\mathit{pk} = n$, giving $(k, c) := \operatorname{Encap}(\mathit{pk})$:

<!-- -->

1. Choose an integer $r$ with $0 \leq r < n$ uniformly at random.
1. Return $k := H(r)$ and $c := r^e \bmod n$ as its encapsulation.

<!-- -->

- **Decapsulation** of $c'$ with private key $\mathit{sk} = (n, d)$, giving $k' := \operatorname{Decap}(\mathit{sk}, c')$:

<!-- -->

1. Compute $r' := (c')^d \bmod n$.
1. Return $k' := H(r')$.

This approach is simpler to implement, and provides a tighter reduction to the [RSA problem](wikipedia://en/1544741), than padding schemes like [RSAES-OAEP](wikipedia://en/1579249).[^o39]

### Elgamal {#Elgamal}

Traditional [Elgamal encryption](https://en.wikipedia.org/wiki/Elgamal_encryption) is defined over a multiplicative subgroup of the [finite field](wikipedia://en/11615) $\mathbb Z/p\mathbb Z$ with generator $g$ of order $q$ as follows:[^o41][^o42]

- **Key generation**, $(pk, sk) := \operatorname{Gen}()$:

<!-- -->

1. Choose $x \in \mathbb Z/q\mathbb Z$ uniformly at random.
1. Compute $y := g^x \bmod p$.
1. Return $\mathit{sk} := x$ as the private key and $\mathit{pk} := y$ as the public key.

<!-- -->

- **Encryption** of a message $m \in \mathbb Z/p\mathbb Z$ to public key $\mathit{pk} = y$, giving $c := \operatorname{Encrypt}(\mathit{pk}, m)$:

<!-- -->

1. Choose $r \in \mathbb Z/q\mathbb Z$ uniformly at random.
1. Compute: $$\begin{aligned} t &:= y^r \bmod p \\ c_1 &:= g^r \bmod p \\ c_2 &:= (t \cdot m) \bmod p\end{aligned}$$
1. Return the ciphertext $c := (c_1, c_2)$.

<!-- -->

- **Decryption** of a ciphertext $c' = (c'_1, c'_2)$ for a private key $\mathit{sk} = x$, giving $m' := \operatorname{Decrypt}(\mathit{sk}, c')$:

<!-- -->

1. Fail and return $\bot$ if $(c'_1)^{(p - 1)/q} \not\equiv 1 \pmod p$ or if $(c'_2)^{(p - 1)/q} \not\equiv 1 \pmod p$, i.e., if $c'_1$ or $c'_2$ is not in the subgroup generated by $g$.
1. Compute $t' := (c'_1)^x \bmod p$.
1. Return $m' := t^{-1} c'_2 \bmod p$.

This meets the syntax of a public-key encryption scheme, restricted to messages in the space $\mathbb Z/p\mathbb Z$ (which limits it to message of a few hundred bytes for typical values of $p$). By validating ciphertexts in decryption, it avoids leaking bits of the private key $x$ through maliciously chosen ciphertexts outside the group generated by $g$.

However, this fails to achieve [indistinguishability against chosen-ciphertext attack](wikipedia://en/2187252). For example, an adversary having a ciphertext $c = (c_1, c_2)$ for an unknown message $m$ can trivially decrypt it by querying the decryption oracle for the distinct ciphertext $c' := (c_1, c_2 g)$, yielding the related plaintext $m' := m g \bmod p$, from which $m$ can be recovered by $m = m' g^{-1} \bmod p$.[^o41]

Traditional Elgamal encryption can be adapted to the elliptic-curve setting, but it requires some way to reversibly encode messages as points on the curve, which is less trivial than encoding messages as integers mod $p$.[^o43]

Since the message $m$ is almost always a short secret key for a [symmetric-key](https://en.wikipedia.org/wiki/Symmetric-key) [authenticated cipher](wikipedia://en/2244296) used to encrypt an arbitrary bit string message, a simpler approach—called **Elgamal-KEM** or **DH-KEM**—is to *derive* the secret key from $t$ and dispense with $m$ and $c_2$ altogether, as a KEM, using a [key derivation function](wikipedia://en/449781) $H$:[^o2]9180

- **Key generation**: As above.
- **Encapsulation** for a public key $\mathit{pk} = y$, giving $(k, c) := \operatorname{Encap}(\mathit{pk})$:

<!-- -->

1. Choose $r \in \mathbb Z/q\mathbb Z$ uniformly at random.
1. Compute $t := y^r \bmod p$.
1. Return $k := H(t)$ and $c := g^r \bmod p$ as its encapsulation.

<!-- -->

- **Decapsulation** of $c'$ with private key $\mathit{sk} = x$, giving $k' := \operatorname{Decap}(\mathit{sk}, c')$:

<!-- -->

1. Fail and return $\bot$ if $(c')^{(p - 1)/q} \not\equiv 1 \pmod p$, i.e., if $c'$ is not in the subgroup generated by $g$.
1. Compute $t' := (c')^x \bmod p$.
1. Return $k' := H(t')$.

When combined with an authenticated cipher to encrypt arbitrary bit string messages, the combination is essentially the [Integrated Encryption Scheme](wikipedia://en/3530076). Since this KEM only requires a one-way key derivation function to hash random elements of the group it is defined over, $\mathbb Z/p\mathbb Z$ in this case, and not a reversible encoding of messages, it is easy to extend to more compact and efficient elliptic curve groups for the same security, as in the [ECIES, Elliptic Curve Integrated Encryption Scheme](wikipedia://en/3530076#Formal_description_of_ECIES), or 9180 DHKEM(...) instances.
