# Opportunistic TLS

::: {#o1 .subject cue=lead name="Opportunistic TLS"}

**Opportunistic TLS** (Transport Layer Security) refers to extensions in plain text communication protocols, which offer a way to upgrade a plain text connection to an encrypted ([TLS](wikipedia://en/187813) or [SSL](https://en.wikipedia.org/wiki/Secure_Sockets_Layer)) connection instead of using a separate port for encrypted communication. Several protocols use a command named "**STARTTLS**" or "**Explicit TLS**" for this purpose. It is a form of [opportunistic encryption](wikipedia://en/4299490) and is primarily intended as a countermeasure to [passive monitoring](https://en.wikipedia.org/wiki/Passive_monitoring).

:::

The STARTTLS command for [IMAP](https://en.wikipedia.org/wiki/IMAP) and [POP3](https://en.wikipedia.org/wiki/POP3) is defined in 2595, for [SMTP](https://en.wikipedia.org/wiki/SMTP) in 3207, for [XMPP](https://en.wikipedia.org/wiki/XMPP) in 6120 and for [NNTP](https://en.wikipedia.org/wiki/NNTP) in 4642. For [IRC](https://en.wikipedia.org/wiki/IRC), the IRCv3 Working Group defined a STARTTLS extension, though it was later deprecated.[^o2] [FTP](https://en.wikipedia.org/wiki/FTP) uses the command "AUTH TLS" defined in 4217 and [LDAP](https://en.wikipedia.org/wiki/LDAP) defines a protocol extension [OID](https://en.wikipedia.org/wiki/Object_identifier) in 2830. [HTTP](https://en.wikipedia.org/wiki/HTTP) uses an [upgrade header](https://en.wikipedia.org/wiki/HTTP/1.1_Upgrade_header#Use_with_TLS).

## Layering {#Layering}

TLS is application-neutral; in the words of 5246:

One advantage of TLS is that it is application protocol independent. Higher-level protocols can layer on top of the TLS protocol transparently. The TLS standard, however, does not specify how protocols add security with TLS; the decisions on how to initiate TLS handshaking and how to interpret the authentication certificates exchanged are left to the judgment of the designers and implementors of protocols that run on top of TLS.[^o4]

The style used to specify how to use TLS matches the same layer distinction that is also conveniently supported by several library implementations of TLS. E.g., the 3207 SMTP extension illustrates with the following dialog how a client and server can start a secure session:[^o5]

S: \<waits for connection on TCP port 25> C: \<opens connection> S: 220 mail.example.org ESMTP service ready C: EHLO client.example.org S: 250-mail.example.org offers a warm hug of welcome S: 250 STARTTLS C: STARTTLS S: 220 Go ahead C: \<starts TLS negotiation> C & S: \<negotiate a TLS session> C & S: \<check result of negotiation> C: EHLO client.example.org[^o6] . . .

The last *EHLO* command above is issued over a secure channel. Note that authentication is optional in SMTP, and the omitted server reply may now safely advertise an *AUTH PLAIN* SMTP extension, which is not present in the plain-text reply.

## SSL ports {#SSL_ports}

Besides the use of opportunistic TLS, a number of TCP ports were defined for SSL-secured versions of well-known protocols. These establish secure communications and then present a communication stream identical to the old un-encrypted protocol. Separate SSL ports have the advantage of fewer [round-trips](https://en.wikipedia.org/wiki/Round-trip_delay_time); also less meta-data is transmitted in unencrypted form.[^o8] Some examples include:

::: {#o9 .table cue=table}

| Protocol | Purpose | Normal port | SSL variant | SSL port |
|---|---|---|---|---|
| [SMTP](https://en.wikipedia.org/wiki/SMTP) | Send email | 25/587 | [SMTPS](https://en.wikipedia.org/wiki/SMTPS) | 465 |
| [POP3](https://en.wikipedia.org/wiki/POP3) | Retrieve email | 110 | [POP3S](https://en.wikipedia.org/wiki/POP3S) | 995 |
| [IMAP](https://en.wikipedia.org/wiki/IMAP) | Read email | 143 | [IMAPS](https://en.wikipedia.org/wiki/IMAPS) | 993 |
| [NNTP](https://en.wikipedia.org/wiki/NNTP) | News reader | 119/433 | [NNTPS](https://en.wikipedia.org/wiki/NNTPS) | 563 |
| [LDAP](https://en.wikipedia.org/wiki/LDAP) | Directory Access | 389 | [LDAPS](https://en.wikipedia.org/wiki/LDAPS) | 636 |
| [FTP](https://en.wikipedia.org/wiki/FTP) | File transfer | 21 | [FTPS](https://en.wikipedia.org/wiki/FTPS) | 990 |
| [XMPP](https://en.wikipedia.org/wiki/XMPP) | Instant messaging | 5222 |  | 5223 |

:::

At least for the email related protocols, 8314 favors *Implicit TLS* (using separate SSL ports) instead of STARTTLS.

## Weaknesses and mitigations {#Weaknesses_and_mitigations}

Opportunistic TLS is an [opportunistic encryption](wikipedia://en/4299490) mechanism. Because the initial handshake takes place in plain text, an attacker in control of the network can modify the server messages via a [man-in-the-middle attack](wikipedia://en/144676) to make it appear that TLS is unavailable (called a **STRIPTLS attack**). Most SMTP clients will then send the email and possibly passwords in plain text, often with no notification to the user. In particular, many SMTP connections occur between mail servers, where user notification is not practical.

In September 2014, two ISPs in [Thailand](https://en.wikipedia.org/wiki/Thailand) were found to be doing this to their own customers.[^o19][^o20] In October 2014, [Cricket Wireless](https://en.wikipedia.org/wiki/Cricket_Wireless), a subsidiary of [AT&T](https://en.wikipedia.org/wiki/AT&T), was revealed to be doing this to their customers. This behavior started as early as September 2013 by [Aio Wireless](https://en.wikipedia.org/wiki/Aio_Wireless), who later merged with Cricket where the practice continued.[^o21][^o19]

STRIPTLS attacks can be blocked by configuring SMTP clients to require TLS for outgoing connections (for example, the [Exim](https://en.wikipedia.org/wiki/Exim) [Message transfer agent](https://en.wikipedia.org/wiki/Message_transfer_agent) can require TLS via the directive "hosts\_require\_tls"[^o22]). However, since not every mail server supports TLS, it is not practical to simply require TLS for all connections.

An example of a STRIPTLS attack of the type used in Thai [mass surveillance](https://en.wikipedia.org/wiki/Mass_surveillance) technology:[^o23]

220 smtp.gmail.com ESMTP mail.redacted.com - gsmtp ehlo a 250-smtp.gmail.com at your service, \[REDACTED SERVICE\] 250-SIZE 35882577 250-8BITMIME # The STARTTLS command is stripped here 250-ENHANCEDSTATUSCODES 250-PIPELINING 250 SMTPUTF8

220 smtp.gmail.com ESMTP - gsmtp ehlo a 250-smtp.gmail.com at your service 250-SIZE 35882577 250-8BITMIME 250-STARTTLS 250-ENHANCEDSTATUSCODES 250-PIPELINING 250 SMTPUTF8

Supposing the client side supports it (name resolution of the client and upstream DNS server of the client), this problem can be addressed by [DNS-based Authentication of Named Entities](wikipedia://en/38213001) (DANE), a part of [DNSSEC](https://en.wikipedia.org/wiki/DNSSEC), and in particular by 7672 for SMTP. DANE allows to advertise support for secure SMTP via a TLSA record. This tells connecting clients they should require TLS, thus preventing STRIPTLS attacks. The STARTTLS Everywhere project from the [Electronic Frontier Foundation](https://en.wikipedia.org/wiki/Electronic_Frontier_Foundation) works in a similar way. However, DNSSEC, due to deployment complexities and peculiar criticism,[^o24] faced a low adoption rate and a new protocol called SMTP MTA Strict Transport Security or MTA-STS has been drafted[^o25] by a group of major email service providers including Microsoft, Google and Yahoo. MTA-STS does not require the use of DNSSEC to authenticate DANE TLSA records but relies on the [certificate authority](wikipedia://en/296370) (CA) system and a trust-on-first-use (TOFU) approach to avoid interceptions. The TOFU model reduces complexity but without the guarantees on first use offered by DNSSEC. In addition, MTA-STS introduces a mechanism for failure reporting and a report-only mode, enabling progressive roll-out and auditing for compliance.

:::

## Popularity {#Popularity}

Following the revelations made by [Edward Snowden](https://en.wikipedia.org/wiki/Edward_Snowden) in light of the [global mass surveillance scandal](https://en.wikipedia.org/wiki/Global_surveillance_disclosures_%282013–present%29), popular email providers have bettered their email security by enabling STARTTLS.[^o27] [Facebook](https://en.wikipedia.org/wiki/Facebook) reported that after enabling STARTTLS and encouraging other providers to do the same, until Facebook discontinued its email service in February 2014, 95% of outbound email was encrypted with both [perfect forward secrecy](wikipedia://en/2191130) and strict certificate validation.[^o28]
