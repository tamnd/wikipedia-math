# Fast inverse square root

*Image: OpenArena-Rocket.jpg.* Lighting and reflection calculations, as in the [video game](https://en.wikipedia.org/wiki/Video_game) *[OpenArena](https://en.wikipedia.org/wiki/OpenArena)*, use the fast inverse square root code to compute [angles of incidence](https://en.wikipedia.org/wiki/Angle_of_incidence_%28optics%29) and reflection.

::: {#o1 .subject cue=lead name="Fast inverse square root"}

**Fast inverse square root**, sometimes referred to as **Fast InvSqrt()** or by the [hexadecimal](wikipedia://en/13263) constant **0x5F3759DF**, is an [algorithm](wikipedia://en/775) that estimates $1/\sqrt{x}$, the [reciprocal](wikipedia://en/229940) (or multiplicative inverse) of the [square root](wikipedia://en/29208) of a 32-[bit](https://en.wikipedia.org/wiki/Bit) [floating-point](https://en.wikipedia.org/wiki/Floating-point) number $x$ in [IEEE 754 floating-point format](https://en.wikipedia.org/wiki/Single-precision_floating-point_format#IEEE_754_standard:_binary32). The algorithm is best known for its implementation in the 1999 [video game](https://en.wikipedia.org/wiki/Video_game) *[Quake III Arena](https://en.wikipedia.org/wiki/Quake_III_Arena)*. With subsequent hardware advancements, especially the [x86](https://en.wikipedia.org/wiki/X86) [SSE](wikipedia://en/55365) instruction `rsqrtss`, this algorithm is not generally the best choice for modern computers,[^o57] though it remains an interesting historical example.[^o58]

:::

The algorithm accepts a 32-bit floating-point number as the input and stores a halved value for later use. Then, treating the bits representing the floating-point number as a 32-bit integer, a [logical shift](https://en.wikipedia.org/wiki/Logical_shift) right by one bit is performed and the result subtracted from the number [0x](wikipedia://en/13263#Representing_hexadecimal)5F3759DF, which is a floating-point representation of an approximation of $\sqrt{2^{127}}$.[^o62] This results in an initial guess of the inverse square root of the input. Treating the bits again as a floating-point number, it runs one iteration of [Newton's method](wikipedia://en/22145), yielding a more precise approximation.

## History {#History}

[William Kahan](wikipedia://en/303413) and K.C. Ng at Berkeley wrote an unpublished paper in May 1986 describing how to calculate the square root using [bit fiddling](https://en.wikipedia.org/wiki/Bit_fiddling) techniques followed by [Newton iterations](https://en.wikipedia.org/wiki/Newton_iterations).[^o52] In the late 1980s, [Cleve Moler](wikipedia://en/562706) at [Ardent Computer](https://en.wikipedia.org/wiki/Ardent_Computer) learned about this technique[^o53] and passed it along to his coworker [Greg Walsh](https://en.wikipedia.org/wiki/Greg_Walsh). Greg Walsh devised the now-famous constant and fast inverse square root algorithm. Gary Tarolli was consulting for Kubota, the company funding Ardent at the time, and likely brought the algorithm to [3dfx Interactive](https://en.wikipedia.org/wiki/3dfx_Interactive) circa 1994.[^o56][^o54]

[Jim Blinn](https://en.wikipedia.org/wiki/Jim_Blinn) demonstrated a simple approximation of the inverse square root in a 1997 column for *[IEEE Computer Graphics and Applications](https://en.wikipedia.org/wiki/List_of_Institute_of_Electrical_and_Electronics_Engineers_publications)*.[^n1] Reverse engineering of other contemporary 3D video games uncovered a variation of the algorithm in [Activision](https://en.wikipedia.org/wiki/Activision)'s 1997 [Interstate '76](https://en.wikipedia.org/wiki/Interstate_'76).[^o4]

*[Quake III Arena](https://en.wikipedia.org/wiki/Quake_III_Arena)*, a [first-person shooter](https://en.wikipedia.org/wiki/First-person_shooter) video game, was released in 1999 by [id Software](https://en.wikipedia.org/wiki/Id_Software) and used the algorithm. Brian Hook may have brought the algorithm from 3dfx to id Software.[^o56] A discussion of the code appeared on the Chinese developer forum CSDN in 2000,[^o61] and [Usenet](https://en.wikipedia.org/wiki/Usenet) and the gamedev.net forum spread the code widely in 2002 and 2003.[^n2] Speculation arose as to who wrote the algorithm and how the constant was derived; some guessed [John Carmack](https://en.wikipedia.org/wiki/John_D._Carmack).[^o54] *Quake III*'s full source code was released at [QuakeCon 2005](https://en.wikipedia.org/wiki/QuakeCon_2005), but provided no answers. The authorship question was resolved in 2006 when Greg Walsh, the original author, contacted Beyond3D after their speculation gained popularity on [Slashdot](https://en.wikipedia.org/wiki/Slashdot).[^o56]

In 2007 the [algorithm](wikipedia://en/775) was implemented in some dedicated hardware [vertex shaders](https://en.wikipedia.org/wiki/Vertex_shader) using [field-programmable gate arrays](https://en.wikipedia.org/wiki/Field-programmable_gate_array) (FPGA).[^o6][^n3]

## Motivation {#Motivation}

*Image: Surface\_normals.svg.* [Surface normals](https://en.wikipedia.org/wiki/Surface_normal) are used extensively in lighting and shading calculations, requiring the calculation of norms for vectors. A field of vectors normal to a surface is shown here.

*Image: Reflection for Semicircular Mirror.svg.* A two-dimensional example of using the normal $C$ to find the angle of reflection from the angle of incidence; in this case, on light reflecting from a curved mirror. The fast inverse square root is used to generalize this calculation to three-dimensional space.

[Computer graphics](https://en.wikipedia.org/wiki/Computer_graphics) frequently uses inverse [square roots](wikipedia://en/29208) for [transform, clipping](https://en.wikipedia.org/wiki/Transform,_clipping,_and_lighting), [lighting](https://en.wikipedia.org/wiki/Computer_graphics_lighting), and [shading](https://en.wikipedia.org/wiki/Shading) to compute [angles of incidence](https://en.wikipedia.org/wiki/Angle_of_incidence_%28optics%29) and [reflection](https://en.wikipedia.org/wiki/Reflection_%28computer_graphics%29). Programs such as Quake III: Arena must perform a large number of these calculations every second to simulate lighting.[^o62] In particular, the operation of scaling a vector to [length](wikipedia://en/18542) 1 to produce a [unit vector](wikipedia://en/167053) uses the inverse square root.[^n4]

Specifically, the length of the [vector](wikipedia://en/32533) is determined by calculating its [Euclidean norm](https://en.wikipedia.org/wiki/Euclidean_norm): the square root of the sum of squares of the [vector components](https://en.wikipedia.org/wiki/Vector_components). When each component of the vector is divided by that length, the new vector will be a unit vector pointing in the same direction. In a 3D graphics program, all vectors are in three-[dimensional](wikipedia://en/38267) space, so $\boldsymbol v$ would be a vector $(v_1, v_2, v_3)$. Then,

$$\|\boldsymbol{v}\| = \sqrt{v_1^2+v_2^2+v_3^2}$$

is the Euclidean norm of the vector, and the normalized (unit) vector is

$$\begin{aligned} \boldsymbol{\hat{v}} &= \frac{1}{\left\|\boldsymbol{v}\right\|}\boldsymbol{v}\\ &= \frac{1}\sqrt{v_1^2+v_2^2+v_3^2}\,\boldsymbol{v}, \end{aligned}$$

where the fraction term is the inverse square root of $v_1^2+v_2^2+v_3^2$.

When the fast inverse square root algorithm was developed in the early 1990s, most floating point processing power lagged the speed of integer processing.[^o54] In particular the [x87](https://en.wikipedia.org/wiki/X87) instruction set was very slow at the time compared to modern SSE operations.[^o57] The fast inverse square generates a good approximation through integer operations by adding and subtracting the integer form of floating-point numbers, and taking a square root by dividing by two (which is just a right-shift).[^o62]

Subsequent additions by hardware manufacturers have made this algorithm redundant for the most part. For example, on [x86](https://en.wikipedia.org/wiki/X86), Intel introduced the [SSE](wikipedia://en/55365) instruction `rsqrtss` in 1999. In a 2009 benchmark on the [Intel Core 2](https://en.wikipedia.org/wiki/Intel_Core_2), this instruction took 0.85ns per float compared to 3.54ns for the fast inverse square root algorithm, and had less error.[^o57]

## Overview of the code {#Overview_of_the_code}

The following [C](https://en.wikipedia.org/wiki/C_%28programming_language%29) code is the fast inverse square root implementation from *[Quake III Arena](https://en.wikipedia.org/wiki/Quake_III_Arena)*, stripped of [C preprocessor](https://en.wikipedia.org/wiki/C_preprocessor) directives, but including the exact original comment text:[^o55]

```c
float Q_rsqrt( float number )
{
	long i;
	float x2, y;
	const float threehalfs = 1.5F;

	x2 = number * 0.5F;
	y  = number;
	i  = * ( long * ) &y;                       // evil floating point bit level hacking
	i  = 0x5f3759df - ( i >> 1 );               // what the fuck?
	y  = * ( float * ) &i;
	y  = y * ( threehalfs - ( x2 * y * y ) );   // 1st iteration
//	y  = y * ( threehalfs - ( x2 * y * y ) );   // 2nd iteration, this can be removed

	return y;
}
```

At the time, the general method to compute the inverse square root was to calculate an approximation for $\frac{1}{\sqrt{x}}$, then revise that approximation via another method until it came within an acceptable error range of the actual result. [Common software methods](https://en.wikipedia.org/wiki/Methods_of_computing_square_roots) in the early 1990s drew approximations from a [lookup table](https://en.wikipedia.org/wiki/Lookup_table).[^n5] The key of the fast inverse square root was to directly compute an approximation by utilizing the structure of floating-point numbers, proving faster than table lookups. The algorithm was approximately four times faster than computing the square root with another method and calculating the reciprocal via floating-point division.[^n6] The algorithm was designed with the [IEEE 754-1985](https://en.wikipedia.org/wiki/IEEE_754-1985) 32-bit floating-point specification in mind, but investigation from Chris Lomont showed that it could be implemented in other floating-point specifications.[^n7]

The advantages in speed offered by the fast inverse square root trick came from treating the 32-bit floating-point word[^o15] as an [integer](https://en.wikipedia.org/wiki/Integer_%28computer_science%29#Long_integer), then subtracting it from a [magic constant](https://en.wikipedia.org/wiki/Magic_number_%28programming%29#Unnamed_numerical_constants), [0x](wikipedia://en/13263#Distinguishing_from_decimal)5F3759DF.[^o54][^n8][^n9][^n10] This integer subtraction and [bit shift](wikipedia://en/264399#C-family) results in a bit pattern which, when [re-defined](https://en.wikipedia.org/wiki/Type_conversion) as a floating-point number, is a rough approximation for the inverse square root of the number. One iteration of Newton's method is performed to gain some accuracy, and the code is finished. The algorithm generates reasonably accurate results using a unique first approximation for Newton's method; however, it is much slower and less accurate than using the [SSE](wikipedia://en/55365) instruction `rsqrtss` on x86 processors also released in 1999.

### Worked example {#Worked_example}

As an example, the number $x=0.15625$ can be used to calculate $\frac{1}{\sqrt{x}} \approx 2.52982$. The first steps of the algorithm are illustrated below:

0011\_1110\_0010\_0000\_0000\_0000\_0000\_0000 Bit pattern of both x and i 0001\_1111\_0001\_0000\_0000\_0000\_0000\_0000 Shift right one position: (i >> 1) 0101\_1111\_0011\_0111\_0101\_1001\_1101\_1111 The magic number 0x5F3759DF 0100\_0000\_0010\_0111\_0101\_1001\_1101\_1111 The result of 0x5F3759DF - (i >> 1)

Interpreting as [IEEE](wikipedia://en/405039) 32-bit representation:

0\_01111100\_01000000000000000000000 1.25 × 2<sup>−3</sup> 0\_00111110\_00100000000000000000000 1.125 × 2<sup>−65</sup> 0\_10111110\_01101110101100111011111 1.432430... × 2<sup>63</sup> 0\_10000000\_01001110101100111011111 1.307430... × 2<sup>1</sup>

Reinterpreting this last bit pattern as a floating point number gives the approximation $y=2.61486$, which has an error of about 3.4%. After one iteration of Newton's method, the final result is $y=2.52549$, an error of only 0.17%.

### Avoiding undefined behavior {#Avoiding_undefined_behavior}

According to the C standard, reinterpreting a floating point value as an integer by casting then dereferencing the pointer to it can cause [undefined behavior](https://en.wikipedia.org/wiki/Undefined_behavior) in case the sizes of integer and float do not match on the given architecture.[^o21] This can be avoided by using alternative [type punning](https://en.wikipedia.org/wiki/Type_punning) techniques such as C's unions[^o22] or [C++20](https://en.wikipedia.org/wiki/C++20)'s `std::bit_cast`.[^o23]

## Algorithm {#Algorithm}

The algorithm computes $\frac{1}{\sqrt{x}}$ by performing the following steps:

1. Alias the argument $x$ to an integer as a way to compute an approximation of the [binary logarithm](wikipedia://en/249992) $\log_{2}(x)$
1. Use this approximation to compute an approximation of $\log_{2}\left(\frac{1}{\sqrt{x}}\right) = -\frac{1}{2} \log_{2}(x)$
1. Alias back to a float, as a way to compute an approximation of the base-2 exponential
1. Refine the approximation using a single iteration of Newton's method.

### Floating-point representation {#Floating-point_representation}

Since this [algorithm](wikipedia://en/775) relies heavily on the bit-level representation of single-precision floating-point numbers, a short overview of this representation is provided here. To encode a non-zero [real number](wikipedia://en/20646438) $x$ as a single precision float, the first step is to write $x$ as a [normalized](wikipedia://en/1349666) binary number:[^n11]

$$\begin{aligned} x &= \pm 1.b_1b_2b_3\ldots \times 2^{e_x} \end{aligned}$$

where the exponent $e_x$ is an integer, and $1.b_1b_2b_3\ldots$ is the binary representation of the [significand](wikipedia://en/419250). Since the single bit before the point in the significand is always 1, it does not need be stored. The equation can be rewritten as:

$$\begin{aligned} x &= (-1)^{S_x} \cdot 2^{e_x} (1 + m_x) \end{aligned}$$

where $m_x$ means $0.b_1b_2b_3\ldots$, so $m_x \in [0, 1)$. From this form, three unsigned integers are computed:[^n12]

- $S_x$, the "sign bit", is $0$ if $x$ is positive and $1$ negative or zero (1 bit)
- $E_x = e_x + B$ is the "biased exponent", where $B = 127$ is the "[exponent bias](https://en.wikipedia.org/wiki/Exponent_bias)"[^o29] (8 bits)
- $M_x = m_x \times L$, where $L = 2^{23}$[^o30] (23 bits)

Thus: $e_x = E_x -B$ and $m_x = \frac{M_x}{L}$.

These fields are then packed, left to right, into a 32-bit container.[^n13]

As an example, consider again the number $x = 0.15625 = 0.00101_2$. Normalizing $x$ yields:

$$x = (-1)^{0} \cdot 2^{-3}(1 + 0.25) = +2^{-3}(1 + 0.25)$$

and thus, the three unsigned integer fields are:

- $$S = 0$$
- $$E = -3 + 127 = 124 = 0111\ 1100_2$$
- $$M = 0.25 \times 2^{23} = 2\ 097\ 152 = 0010\ 0000\ 0000\ 0000\ 0000\ 0000_2$$

these fields are packed as shown in the figure below:

*Image: Float w significand 2.svg.*

The number is represented in [binary](wikipedia://en/238686) as: $I_x = S_x \cdot 2^{31} + E_xL + M_x$

Also, since this algorithm works on real numbers, $\sqrt{x}$ is only defined for $x \geq 0$. The code thus assumes $x \geq 0$ and $S_x = 0$.

The number, given to calculate the square root, could be rewritten as:

$$I_x = E_xL +M_x$$

$$x = (-1)^0 \cdot 2^{e_x} (1 + m_x) = + 2^{e_x} (1 + m_x)$$

### Aliasing to an integer as an approximate logarithm {#Aliasing_to_an_integer_as_an_approximate_logarithm}

If $\frac{1}{\sqrt{x}}$ were to be calculated without a computer or a calculator, a [table of logarithms](https://en.wikipedia.org/wiki/Table_of_logarithms) would be useful, together with the identity $\log_b\left(\frac{1}{\sqrt{x}}\right) = \log_b\left(x^{-\frac{1}{2}}\right) = -\frac{1}{2} \log_b(x)$, which is valid for every base $b$. The fast inverse square root is based on this identity, and on the fact that aliasing a float32 to an integer gives a rough approximation of its logarithm. Here is how:

If $x$ is a positive [normal number](https://en.wikipedia.org/wiki/Normal_number_%28computing%29):

$$x = 2^{e_x} (1 + m_x)$$

then

$$\log_2(x) = e_x + \log_2(1 + m_x)$$

and since $m_x \in [0, 1)$, the logarithm on the right-hand side can be approximated by[^n14]

$$\log_2(1 + m_x) \approx m_x + \sigma$$

where $\sigma$ is a free parameter used to tune the approximation. For example, $\sigma = 0$ yields exact results at both ends of the interval, while $\sigma = \frac{1}{2} - \frac{1+\ln(\ln(2))}{2\ln(2)} \approx 0.0430357$ yields the [optimal approximation](wikipedia://en/1092713#Optimal_polynomials) (the best in the sense of the [uniform norm](wikipedia://en/349755) of the error). However, this value is not used by the algorithm as it does not take subsequent steps into account.

*Image: Log by aliasing to int.svg.* The integer aliased to a floating point number (in blue), compared to a scaled and shifted logarithm (in gray)

Thus there is the approximation

$$\log_2(x) \approx e_x + m_x + \sigma.$$

Interpreting the floating-point bit-pattern of $x$ as an integer $I_x$ yields[^o34]

$$\begin{aligned} I_x &= E_x L + M_x\\ &= L (e_x + B + m_x)\\ &= L (e_x + m_x + \sigma + B - \sigma)\\ &\approx L \log_2(x) + L (B - \sigma). \end{aligned}$$

It then appears that $I_x$ is a scaled and shifted piecewise-linear approximation of $\log_2(x)$, as illustrated in the figure on the right. In other words, $\log_2(x)$ is approximated by

$$\log_2(x) \approx \frac{I_x}{L} - (B - \sigma).$$

### First approximation of the result {#First_approximation_of_the_result}

The calculation of $y=\frac{1}{\sqrt{x}}$ is based on the identity

$$\log_2(y) = - \tfrac{1}{2}\log_2(x)$$

Using the approximation of the logarithm above, applied to both $x$ and $y$, the above equation gives:

$$\frac{I_y}{L} - (B - \sigma) \approx - \frac{1}{2}\left(\frac{I_x}{L} - (B - \sigma)\right)$$

Thus, an approximation of $I_y$ is:

$$I_y \approx \tfrac{3}{2} L (B - \sigma) - \tfrac{1}{2} I_x$$

which is written in the code as

```c
i  = 0x5f3759df - ( i >> 1 );
```

The first term above is the magic number

$$\tfrac{3}{2} L (B - \sigma) = \mathtt{0x5f3759df}$$

from which it can be inferred that $\sigma \approx 0.0450466$. The second term, $\frac{1}{2}I_x$, is calculated by shifting the bits of $I_x$ one position to the right.[^n15]

### Newton's method {#Newton's_method}

The number $y=\tfrac{1}{\sqrt{x}}$ is a solution of the equation $\tfrac{1}{y^2}-x=0$. The approximation yielded by the earlier steps can be refined by using a [root-finding method](https://en.wikipedia.org/wiki/Root-finding_method), a method that finds the [zero of a function](wikipedia://en/264210). The algorithm uses Newton's method: if there is an approximation, $y_n$ for $y$, then a better approximation $y_{n+1}$ can be calculated by taking $y_n - \tfrac{f(y_n)}{f'(y_n)}$, where $f'(y_n)$ is the [derivative](wikipedia://en/7921) of $f(y)$ at $y_n$.[^n16] Applied to the equation $\tfrac{1}{y^2}-x=0$, Newton's method gives

$$\begin{aligned} f(y) &= \frac{1}{y^2} - x\\ f'(y) &= -\frac{2}{y^3}\\ y_{n+1} &= y_n - \frac{f(y_n)}{f'(y_n)}\\ &= y_n + \frac{y_n^3}{2} \left(\frac{1}{y_n^2} - x\right)\\ &= y_n \left(\frac{3}{2} - \frac{x}{2}y_n^2\right), \end{aligned}$$

which is written in the code as

```c
y  = y * ( threehalfs - ( x2 * y * y ) );
```

.

By repeating this step, using the output of the function ($y_{n+1}$) as the input of the next iteration, the algorithm causes $y$ to [converge](wikipedia://en/999701) to the inverse square root.[^n17] For the purposes of the [*Quake III* engine](https://en.wikipedia.org/wiki/Id_Tech_3), only one iteration was used. A second iteration remained in the code but was [commented out](https://en.wikipedia.org/wiki/Comment_out).[^n10]

:::

## Subsequent improvements {#Subsequent_improvements}

### Magic number {#Magic_number}

It is not known precisely how the exact value for the magic number was determined. Chris Lomont developed a function to minimize [approximation error](wikipedia://en/640422) by choosing the magic number $R$ over a range. He first computed the optimal constant for the linear approximation step as 0x5F37642F, close to 0x5F3759DF, but this new constant gave slightly less accuracy after one iteration of Newton's method.[^n18] Lomont then searched for a constant optimal even after one and two Newton iterations and found 0x5F375A86, which is more accurate than the original at every iteration stage.[^n18] He concluded by asking whether the exact value of the original constant was chosen through derivation or [trial and error](https://en.wikipedia.org/wiki/Trial_and_error).[^n19] Lomont said that the magic number for 64-bit IEEE754 size type double is 0x5FE6EC85E7DE30DA, but it was later shown by Matthew Robertson to be exactly 0x5FE6EB50C7B537A9.[^o60]

Jan Kadlec reduced the relative error by a further factor of 2.7 by adjusting the constants in the single Newton's method iteration as well,[^o46] arriving after an exhaustive search at

```c
conv.i = 0x5F1FFFF9 - ( conv.i >> 1 );
conv.f *= 0.703952253f * ( 2.38924456f - x * conv.f * conv.f );
return conv.f;
```

A complete mathematical analysis for determining the magic number is now available for single-precision floating-point numbers.[^n20][^o48]
